AJO and RTCDP foundations

Adobe Journey Optimizer is built on Adobe Experience Platform. Platform provides the data foundation; AJO uses that foundation to orchestrate experiences and deliver messages.

Source systems→XDM schemas→Datasets→Identity + Profile→Audiences / events→AJO journeys→Channel actions
LayerQuestion answeredExamples
Data foundationWhat data is collected and how is it structured?XDM schemas, datasets, ingestion.
Identity / ProfileWhich records belong to the same person/entity?Namespaces, identity graph, profile fragments.
Audience / eventWho qualifies, and what just happened?Batch, streaming, edge audiences; unitary events.
OrchestrationWhat should happen next and when?Entry, conditions, waits, actions, exits.
Decisioning / contentWhich experience should be selected and rendered?Offers, decision policies, message personalization.
  • Event: a time-stamped occurrence, such as checkout completion.
  • Audience: profiles meeting defined criteria; not the same as an individual event.
  • Profile: a unified representation built from profile-enabled data and identity relationships.
  • Journey: workflow controlling sequence, timing, branching, and actions.
  • Action: operation performed by a journey, such as sending a message or calling a service.
  • Data source: configured source queried when additional data is needed at runtime.
Exam shortcut: occurrence → event; membership → audience; retrieve information → data source; cause an operation → action.

1. Administration and configuration 20%

1.1 Permissions, roles, and ABAC

Access is managed through users, roles, permissions, and product-level access. A role groups permissions; users receive access through role assignment. Apply least privilege: grant only the capabilities needed for the task.

TaskPermission area to verifyReasoning
Create/edit/publish journeysAJO journey authoring and management permissions; access to referenced objects/data.View permission does not imply edit or publish rights.
Configure channelsChannel administration and channel-specific permissions.Authoring a message is different from managing delivery infrastructure.
Manage offers/decisionsOffer and decisioning object permissions.Creating, approving, and using objects can be distinct capabilities.
Manage users/rolesAdmin Console / Platform access-control administration.Not every AJO author is a user administrator.
Use profile dataAccess to schemas, datasets, audiences, and profile resources.Journey permissions do not guarantee access to all underlying data.

Attribute-Based Access Control (ABAC) evaluates attributes associated with users, resources, and context against policies. Use roles for reusable permission sets; use ABAC when access must depend on attributes or data-use labels. Test using a least-privilege user rather than an administrator account.

1.2 Sandboxes and business-unit separation

A sandbox is a logical partition in an Experience Platform environment used to isolate assets and data for development, testing, or production. It is not merely a folder; assets and data should not be assumed to be automatically visible across sandboxes.

ScenarioDesign approach
Development before productionBuild and validate in development; promote supported assets/configuration through the approved release process.
Separate brands/business unitsDecide whether separation is needed at sandbox, schema/dataset, role, or governance level.
Shared enterprise profile foundationAgree on identity, schema, ownership, consent, and access patterns before sharing.
Production-like testingUse approved test data or controlled copies and preserve privacy/data-use restrictions.
Common trap: sandbox isolation and business-unit separation are related but not identical. Cross-sandbox asset promotion and data sharing depend on the supported feature/workflow; do not assume arbitrary cross-sandbox querying.

1.3 Channel administration

Channel administration establishes the infrastructure and identity configuration needed to deliver messages. Message authoring defines the content; a correct message can still fail if channel infrastructure is incomplete.

Email and subdomain delegation

  1. Choose the sending subdomain strategy and align it with the organization's DNS model.
  2. Choose the supported delegation approach (full or CNAME-based) according to who manages DNS.
  3. Publish the DNS records specified by the Adobe setup workflow.
  4. Complete verification and required authentication/deliverability configuration.
  5. Configure sender identity and channel surface.
  6. Test sends and monitor delivery, bounces, complaints, and reputation.

Full delegation gives the service provider broader DNS management for the subdomain. CNAME-based delegation leaves more DNS administration with the customer while pointing required records to Adobe-managed infrastructure. Follow the exact current setup wizard records; do not copy stale DNS examples.

SMS / MMS / RCS

  • Confirm the supported provider connection and credentials.
  • Validate sender type/number eligibility for each destination market.
  • Check registration, consent, opt-out keywords, and local regulations.
  • Understand encoding and segment counts; special characters may change SMS segmentation.
  • Do not assume an SMS sender supports MMS or RCS; verify provider, country, and device capability.
  • Test with representative carriers and devices.

1.4 Events, custom actions, custom data sources

ObjectUse whenDesign questions
EventA business occurrence should trigger or influence a journey.Event schema? Identity? Payload? Unitary or business event? Volume and duplicate handling?
Custom actionThe journey must call an external endpoint or perform an operation.Method, endpoint, auth, headers, mapping, timeout, response and error handling?
Custom data sourceThe journey must retrieve external/additional information at runtime.Lookup key, response schema, latency, unavailable-data fallback?

Unitary event configuration sequence

  1. Define the occurrence and exact trigger condition.
  2. Select/create the appropriate XDM Experience Event schema and include the required identity.
  3. Configure the event in AJO and select the fields required for orchestration.
  4. Generate/use the expected payload structure and endpoint contract.
  5. Send a test event and confirm acceptance.
  6. Validate journey entry with a test profile and inspect the event values.

A unitary event is associated with an individual profile and can trigger an individual journey. A business event represents a business-level occurrence not necessarily tied to one individual, such as a store closure or inventory change; it can trigger evaluation of eligible profiles using a supported pattern.

Custom action checklist

  • Use a stable secured endpoint; protect credentials.
  • Map only required fields and validate data types.
  • Plan authentication, credential rotation, timeouts, retries, and rate limits.
  • Define behavior for success, business errors, transient errors, timeout, malformed response, and throttling.
  • Design receiving services to tolerate duplicate calls where relevant; do not assume exactly-once execution.

2. Journey orchestration 22%

2.1 Choose a journey pattern

PatternUse whenCheck
Event-triggeredA real-time occurrence should start an individual journey.Identity, payload, volume, deduplication, re-entry.
Audience-triggered / read audienceA set of profiles should enter based on audience qualification or a scheduled evaluation.Audience freshness, cadence, qualification, re-entry.
Business-eventA business-level occurrence should cause profile evaluation/action.Event semantics, scale, supported journey pattern.

2.2 Journey build sequence

Objective→Entry→Re-entry→Activities→Test→Publish→Monitor
  1. Define customer outcome and success measure.
  2. Choose entry type and verify it matches the trigger requirement.
  3. Set profile entrance management: once, re-entry after completion, or configured recurrence.
  4. Define journey properties and execution settings.
  5. Add conditions, waits, actions, audience qualification, jumps, and channel messages.
  6. Design exits for completion, opt-out, invalid data, suppression, and failures.
  7. Test positive, negative, edge, and exception cases.
  8. Publish the intended version and monitor reports and provider feedback.

2.3 Activities and branching

ActivityPurposeExam cue
ConditionEvaluates profile/event/context data and branches.Next step depends on a rule.
WaitDelays the next step for a duration or supported condition.Timing, cooling-off, follow-up.
JumpMoves execution to another point where supported.Reuse/simplify logic; validate loops and limits.
Channel actionExecutes configured communication.Check content, consent, channel readiness and delivery.
Custom actionCalls an external service.Check auth, mapping, latency, response and errors.
End / exitStops execution for a profile.Objective completed or profile no longer eligible.

2.4 Multi-channel, multi-step design

Coordinate channels around customer state and preferences, not by blindly sending the same message everywhere. Example: on cart abandonment, wait, check for purchase, send email if consented and reachable, wait and re-check conversion, then consider push only if eligible. If no channel is eligible, exit or follow an approved non-marketing path.

Cart abandoned→Wait→Purchased?→No→Email eligible?→Email→Re-check→Push eligible?
  • Check consent and eligibility before sending.
  • Use purchase/conversion events to stop irrelevant reminders.
  • Respect caps and suppression lists.
  • Use preference and reachability; do not assume every profile has every channel.
  • Ensure fallback branches do not bypass governance.

2.5 Entrance, re-entry, and concurrency

Re-entry is a business rule. A cart journey may allow a new entry for a new cart after completion; onboarding may be one-time. Consider duplicate event delivery, repeated audience qualification, overlapping journeys, and concurrent execution. For duplicate sends, inspect entry event duplication, re-entry settings, audience cadence, concurrent journeys, and missing conversion exits.

2.6 Test mode, proof, and experimentation

Test typeProvesDoes not prove alone
Preview / proofRendering, personalization, links, fallback, layout.Journey entry, wait logic, provider delivery, production throughput.
Journey test modePath/activity behavior for test profiles under test rules.Production-scale throughput and deliverability.
ExperimentationComparison of configured variants against an objective.Correctness of unrelated data pipelines or consent.
End-to-endEvent ingestion through journey execution and provider outcome.Long-term performance without monitoring.

Minimum test matrix: eligible profile; missing optional attribute; missing required identity/address; no consent/opt-out; already converted; duplicate event; action success; action business error; timeout; rate limit; profile at cap or on suppression list.

2.7 Reporting and performance metrics

ObservationInspect
Few profiles enterTrigger ingestion, audience qualification, entry conditions, identity, schedule, re-entry.
Profiles enter but do not reach sendBranch conditions, waits, exits, missing attributes, caps, suppression, action errors.
Action executes but delivery is lowChannel setup, provider response, invalid addresses, consent, bounce, throttling.
High sends but low engagementAudience relevance, content, offer, timing, preference, frequency, measurement.
Duplicate messagesDuplicate events, re-entry, overlapping journeys, repeated audience entry, missing exit.

Read metrics as a funnel: eligible/entered → progressed → branched → action executed → accepted by provider → delivered/engaged where reporting supports it. A low send count is not automatically a provider failure; profiles may be filtered earlier.

3. Offer decisioning 16%

3.1 Core objects

ObjectMeaningQuestion
OfferExperience or proposition shown to a customer.What does the customer receive?
Representation / placementDefines how/where an offer is represented for a channel/location.Where and in what format does it appear?
Eligibility ruleDetermines whether profile/context qualifies.Who may receive it?
RankingOrders eligible candidates.Which eligible offer wins?
DecisionCombines placements and selection logic for a use case.What decision is requested at runtime?
FallbackSafe alternative if no personalized offer qualifies.What is returned on no match?

3.2 Offer creation workflow

  1. Define business objective and target placement/channel.
  2. Create offer content and required channel representations.
  3. Configure eligibility rules and required profile/context attributes.
  4. Set ranking/priority logic.
  5. Define fallback behavior.
  6. Associate offers with the relevant collection/decision configuration.
  7. Validate dates, status, rules, content, and representation.
  8. Simulate with representative test profiles.
  9. Publish/activate configuration and validate runtime response.

3.3 Eligibility vs ranking

Eligibility answers can this offer be shown? Ranking answers which eligible offer should be selected? An offer with the highest priority but a failed eligibility rule must not win. Ranking is not a substitute for compliance or eligibility.

Example: Offer A is for premium members and ranks first. Offer B is available to all and ranks second. A non-premium profile is not eligible for A, so B can be selected.

3.4 Test profiles and simulation

Simulation verifies candidate offers and the decision result for a selected profile/context. Use realistic attributes, identity, placement, and channel context. Test a profile expected to qualify for each offer; one expected to fail each rule; overlapping eligibility; no eligible offer/fallback; missing attributes; date/threshold boundaries; and the correct channel representation.

3.5 Offer Hub / Decisions Hub vs Edge Decisioning API

DimensionHub / authoring experienceEdge Decisioning API
PurposeCreate, manage, organize and configure offers/decisions.Request decision outcomes in an interactive edge context.
Typical userMarketer, decisioning author, administrator.Application/service developer.
InteractionConfiguration and lifecycle management.Runtime request/response decision retrieval.
Study focusOffer/decision object relationships and configuration.Request context, runtime requirements, response and fallback.

Your reading list also names the Decisions Hub API as a delivery path. Treat it as a distinct API family from Edge Decisioning; do not assume identical payloads, latency, or channel support. Learn the use case and exact contract for each from current Adobe docs.

3.6 Guardrails

  • Keep eligibility rules understandable and testable.
  • Configure a fallback for no-match outcomes.
  • Ensure required profile/context attributes are available and populated.
  • Confirm placement/representation compatibility with the delivery method.
  • Validate status, active dates, and publication state.
  • Check current guardrails for exact limits; do not memorize unverified limits from old material.

4. Content authoring 22%

4.1 Lifecycle

Channel→Template→Content→Personalize→Preview / proof→Validate→Approve→Publish

Content authoring includes channel-specific configuration, rendering, personalization, fallback behavior, compliance, link validation, and test-profile verification—not just copywriting.

4.2 Channel-specific considerations

ChannelConsiderationsCommon failure points
EmailHTML/text, subject/preheader, sender, links, images, responsive layout, unsubscribe/compliance.Broken markup, missing fallback, bad links, sender/domain, deliverability.
SMSConcise text, sender eligibility, encoding, character count, URLs, consent/opt-out.Extra segments, unsupported characters, provider/country restrictions.
MMS / RCSRich media and interactive features where provider, country and device support them.Unsupported destination/device, media constraints, fallback behavior.
PushApp registration, device token, title/body, deep link, platform payload.Invalid/stale token, app setup, notification permission, payload limits.
In-appApp surface, placement, display timing, app state, dismissal and frequency.Incorrect surface, SDK state, timing, app version, identity mismatch.

4.3 Templates

Templates standardize layout and approved patterns. Expose only intended editable regions; use naming/version conventions; separate reusable structure from campaign copy; test long content and missing values; and confirm the published message uses the expected template version. Understand whether the current authoring workflow uses a saved copy or a shared/linked template.

4.4 Personalization and helper functions

Personalization syntax accesses profile, event, and contextual data and applies expressions. Helper functions can support formatting, conditional logic, defaults, string manipulation, date/time operations, arithmetic, and collection handling. Exact functions and syntax vary by authoring context.

PatternPurposeValidate
Attribute lookupInsert profile/event value.Path, type, value availability for test profile.
ConditionalRender different content based on a condition.Boolean logic, null behavior, both branches.
Default/fallbackSafe content when value is missing/empty.Missing vs null vs empty vs false.
FormattingFormat date, number, or string.Locale, timezone, input type, output format.
IterationRender repeated content from a collection.Empty collection, item scope, size.
Syntax note: your outline does not provide exact expression examples or a helper-function inventory. This guide explains how to reason about expressions without inventing function signatures. Practice exact syntax from Adobe's current personalization documentation.

To evaluate an expression: identify its data source; trace the path and type; evaluate conditions; check missing/null/empty values; apply helpers in order; then determine the final rendered output including whitespace and fallback.

4.5 Preview, proof, validation, approval, publish, pause

StagePurposeChecks
PreviewRender content for a selected context/profile.Personalization, layout, images, dynamic blocks.
ProofShare a representative rendering for review.Brand, legal, copy, links, profile variants.
ValidateCheck configuration meets publishing requirements.Missing fields, channel settings, unsupported constructs.
ApproveComplete business review.Stakeholder and compliance sign-off.
PublishMake configured journey/message available for execution.Version, dependencies, schedule, audience, channel readiness.
PauseSuspend execution according to lifecycle behavior.In-flight profiles and restart/version implications.

Validation is not proof: validation checks configuration; proof checks what a person sees. A correct proof does not prove the journey can publish, and a successful validation does not guarantee every personalized rendering is correct.

4.6 Consent and suppression

A contact address or device token does not automatically grant permission to contact. Respect consent, channel eligibility, opt-out, suppression, and frequency policies. Ensure fallback branches cannot bypass those checks.

5. Data modeling 18%

5.1 XDM schemas and schema types

XDM schemas define structure and meaning. A schema combines a class and field groups, with custom fields where appropriate. Schemas create consistent data structures across source systems and Platform services.

TypePurposeExample
Individual ProfileAttributes about a person/customer over time.Name, preferences, loyalty tier, contact details.
Experience EventTime-stamped interaction or occurrence.Page view, product view, cart update, purchase.
Other/custom classOther business entities or structures.Product, store, account, custom entity.

Profile data describes relatively persistent/current customer attributes; event data describes what happened at a point in time. An event may contribute to profile updates, but the event record and profile record remain different data structures.

5.2 Datasets

A dataset stores records conforming to a schema. A schema defines structure; a dataset contains ingested records. One schema can be associated with multiple datasets for different sources or ingestion patterns. Not every dataset is automatically enabled for Real-Time Customer Profile; Profile enablement has schema and identity requirements.

5.3 Union schemas

A union schema is a system-generated combined view of schemas that share a compatible class and are enabled for Real-Time Customer Profile. It represents the fields available to Profile for that class; it is not a dataset to ingest into directly.

TermRemember
SchemaDefines structure and semantics.
DatasetStores ingested records conforming to a schema.
Union schemaCombined Profile view across Profile-enabled schemas of the same class.

5.4 Real-Time Customer Profile

Profile combines fragments from Profile-enabled datasets and identity relationships into a unified view. It is not simply a row-level join of every dataset. Merge policies determine how conflicting fragments are reconciled.

  • Profile attributes describe current profile state.
  • Experience Events provide behavioral history/context.
  • Namespaces and identity graphs connect identifiers.
  • Merge policies resolve competing values from sources.
  • Availability depends on ingestion, Profile enablement, identity configuration, and processing.

5.5 Identity, namespaces, and identity graph

An identity is an identifier for a person/entity. A namespace gives the identifier context, such as email, phone, CRM ID, or ECID. The same literal value in different namespaces does not necessarily identify the same entity.

ConceptDefinition / exam cue
Identity valueThe actual identifier value.
NamespaceContext/type of identifier, e.g. email, phone, ECID, CRM ID.
Primary identitySchema's designated identity for the record/profile use case.
Identity graphRelationships among identifiers believed to belong to the same person/entity.

Use stable identifiers where possible; choose the correct namespace; do not reuse namespaces for semantically different IDs; and do not assume a shared household email or phone always means one person. Identity graphs depend on supplied identity data and graph rules; they are not omniscient.

5.6 Ingestion patterns

PatternFitConsiderations
BatchScheduled files, historical data, periodic reference updates.File format, mapping, batch status, late data, retry/reconciliation.
StreamingFrequent event/profile updates requiring low latency.Payload contract, identity, throughput, schema validation, ordering, duplicates.

5.7 Segmentation Service: batch, streaming, edge

TypeGeneral behaviorBest fitWatch for
BatchEvaluates membership on a scheduled/batch basis.Large audiences where immediate membership updates are unnecessary.Freshness depends on evaluation schedule and data availability.
StreamingUpdates membership as qualifying events/data are processed for supported rules.Membership should respond quickly to customer behavior.Not every expression is supported for streaming.

Selection shortcut: scheduled/large-scale → batch; rapid response to qualifying behavior → streaming; immediate edge experience → edge, if the audience definition is supported.

5.8 Identity and segmentation guardrails

Guardrails can limit audience complexity, evaluation methods, data volume, identity graph behavior, and processing capacity. If an audience is not eligible for streaming or edge evaluation, inspect operators, data fields, event requirements, and supported profile attributes before redesigning the entire use case.

Incident handling sequence

  1. Capture journey version, profile ID/namespace, event timestamp, action/message ID, and provider response.
  2. Reproduce with a controlled test profile and known payload.
  3. Separate configuration, data-quality, permission, and capacity problems.
  4. Review recent changes to schemas, mappings, channel setup, templates, decision rules, and external APIs.
  5. Use monitoring/logs; do not rely only on final send count.
  6. After a fix, rerun the failed case and regression-test adjacent branches.

API revision framework

For each API family named in the outline—capping, throttling, suppression lists, object copy, and interactive message execution—prepare a reference sheet with these fields:

FieldQuestions to answer from current Adobe API documentation
AuthenticationSupported OAuth/service credential flow? Required scopes/permissions?
EndpointExact base URL, path, API version, HTTP method?
RequestRequired fields, types, allowed values, identifier formats?
ResponseSuccess response? Synchronous or asynchronous?
ErrorsValidation, auth, authorization, conflict, throttling, server error formats?
LimitsQuotas, request rate, payload size, concurrency restrictions?
OperationsIdempotency, retries, audit trail, rollback?

Do not confuse: capping limits exposure/frequency; throttling regulates processing rate; suppression excludes recipients. If the requirement is “never contact this address,” throttling is not the answer. If it is “no more than N messages in a period,” investigate frequency/capping. If it is “process at a controlled rate,” investigate throttling.

Scenario-based decision framework

  1. Classify the requirement: trigger, audience, lookup, action, content, offer, or governance?
  2. Identify the system of record: Platform data, AJO configuration, external service, or channel provider?
  3. Choose the right object: event vs audience vs data source vs action; schema vs dataset vs union schema; eligibility vs ranking.
  4. Apply constraints: identity, consent, permissions, sandbox, supported segmentation, API limits, channel readiness.
  5. Validate: test profile, payload, preview/simulation, journey test, report, provider response.

Common distractors

  • Audience when the requirement is a single real-time occurrence.
  • Event when the requirement is scheduled audience qualification.
  • Confusing schema (structure) with dataset (records).
  • Assuming a union schema is directly ingestible.
  • Confusing offer eligibility with ranking.
  • Assuming proof guarantees publish readiness.
  • Assuming an address means consent.
  • Using throttling for recipient suppression.
  • Assuming all audiences support streaming or edge.
  • Assuming view access implies edit/publish access.
