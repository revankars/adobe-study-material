Domain 1

Data Architecture

Design a consistent XDM model that supports profile unification, segmentation, personalization, and activation without unnecessary ingestion or operational complexity.

Core architect decisions

  1. Determine the XDM class that represents the entity and its behavior.
  2. Identify record keys and person/entity identities.
  3. Select standard identity namespaces and define primary/secondary identity behavior.
  4. Model entity relationships and cardinality.
  5. Decide which datasets require Real-Time Customer Profile and Identity Service.
  6. Plan merge policies and source-of-truth precedence.
  7. Design for segmentation and activation from the beginning.
  8. Document the model in an ERD and map source attributes to XDM.
Architect mindset: Start with the business entity and its grain, not the source table name. Ask whether a row is a person record, a time-stamped event, or a separate dimension/entity.

Primary keys, identities, and namespaces

Do not confuse a record key with a person identity. A record key identifies a row. An XDM identity designation tells Identity Service that a value can connect identity fragments across records and datasets.

  • Primary identity: identity under which a profile fragment is stored for a record. If multiple identity fields exist, one is designated primary.
  • Secondary identity: additional identity value(s) that can help link fragments in the identity graph.
  • Identity namespace: context/type that gives a value meaning, such as Email, Phone, ECID, or a custom namespace.
  • Identity map: flexible structure for namespaced identities where supported by the model and ingestion pattern.
Do not mark every identifier as an identity. False links can over-stitch profiles; missing links can fragment one person into multiple profiles.

Identity design checklist

  • Is the identifier stable and consistently populated?
  • Can multiple people share it, such as a household phone or shared email?
  • Is it a person identity or merely a transaction/record identifier?
  • Is the namespace consistent across systems?
  • Which identity is primary for this dataset, and why?
  • Have anonymous-to-known transitions and graph limits been considered?

Relationships, cardinality, and multi-entity design

Relationships connect separate entity schemas. They let related data be used in multi-entity segmentation without copying every dimension attribute into the person record.

CardinalityMeaningExampleDesign note
1:1One source record relates to at most one target record.One unique member record to one current enrollment.Use only if the business rule guarantees it.
M:1Many source records reference one target.Many members reference one plan.Common dimension relationship.
1:MOne source record relates to many targets.One account has many contacts.Often reverse perspective of M:1.
M:MMany records on both sides can relate.Patients and providers across care relationships.Often needs a bridge/relationship entity.
Important nuance: Relationship descriptors document the relationship and cardinality for query-time resolution. Cardinality guides modeling; it does not enforce referential integrity or reject bad foreign-key values during ingestion.

ERD planning workflow

  1. List entities and define grain (what one row represents).
  2. Identify candidate primary and foreign keys.
  3. Classify entities as profile, event, or dimension/reference data.
  4. Map entities to standard XDM classes and reusable field groups.
  5. Document relationship direction, cardinality, and optionality.
  6. Mark only datasets that need Profile or Identity Service.
  7. Overlay segmentation and activation use cases on the ERD.
  8. Validate data types, nullability, uniqueness, volume, and update patterns.

Profile enablement: decide deliberately

Enable a dataset for Real-Time Customer Profile when its records must contribute to unified profile attributes, identity stitching, or Profile-based audience use cases. Keep analytical/reference data in the Data Lake when Profile participation is not required. Avoid enabling services “just in case”; it can increase profile-store footprint and complicate identity/merge behavior.

Healthcare architect scenarios from your notes

1. Surface provider data in patient profile without inventing a new class

Recommended reasoning: Inspect the standard Healthcare XDM model and provider-related classes/field groups. The standard Provider class represents provider business entities; the standard Healthcare Member Details field group for XDM Individual Profile includes healthcare-member attributes and relationship-related information. Model the provider as a reusable entity and relate the patient/member schema using a provider identifier rather than duplicating the entire provider record on every patient.

If only a primary-care-provider reference is needed, use the standard healthcare member field group where it fits. If richer provider attributes are needed for segmentation, use a related Provider entity and multi-entity segmentation. A relationship does not automatically materialize every provider field as a physical profile attribute.

2. Plan-level data should appear in Profile, Event, or custom entity?

Choose based on grain and lifecycle. A member’s current plan enrollment belongs in the Individual Profile model using the standard Healthcare Member Details field group and a relationship to Plan where appropriate. A plan change/enrollment/renewal occurrence belongs in an ExperienceEvent. The reusable plan definition belongs in a Plan entity/schema—not duplicated in every event or person record.

Exam clue: “current state of this member” → Profile; “a change happened at this time” → Event; “shared description of the plan” → Plan dimension.

3. Why use standard XDM components?

Standard classes, field groups, and identity namespaces improve semantic consistency and compatibility with Adobe services, industry models, and downstream applications. They reduce custom mapping and make expected fields recognizable. Skipping them can create duplicate or semantically inconsistent attributes, weaker interoperability, more complex mappings, and missed opportunities to use standard identity, consent, or personalization fields. Correct configuration is still required.

4. How can future entities reuse attributes?

Use reusable standard or custom field groups when attributes share meaning and are compatible with the class. Reuse standard classes for standard entity types. Use consistent relationship descriptors and key conventions. A field group is reusable schema structure; it does not replace choosing the correct class or entity grain.

Data architecture exam traps

  • Using ExperienceEvent for a static current-state attribute—or Profile for an occurrence.
  • Confusing _id (record identifier) with a person identity.
  • Creating a custom class before checking standard XDM classes.
  • Duplicating dimension data instead of modeling a relationship.
  • Assuming cardinality enforces data integrity.
  • Enabling Profile/Identity on every dataset “just in case”.
  • Assuming union schemas span arbitrary related classes.
Domain 2

Segmentation and Audiences

Segmentation converts profile attributes, events, and related entity data into audience membership. The key exam skill is selecting evaluation method based on latency, query shape, data availability, and use case.

Core areas

Plan schedule/export jobs, dynamic personalization, guardrails, merge-policy impact, evaluation methods, relationship requirements, aggregates, sequential logic, segment membership, and profile counts.

Batch vs streaming vs edge

MethodPurposeTypical use caseExam clue
BatchEvaluate eligible profiles in a scheduled/on-demand job.Overnight eligibility, broad rich audience, periodic cohorts.Scheduled, large, not immediate. Broadest query eligibility.
StreamingContinuously evaluate eligible audiences as streaming data arrives.Near-real-time response to recent behavior.Incoming event, near real-time, but query eligibility constrained.
EdgeEvaluate at edge for same-page/next-page personalization.Immediate onsite experience.Same page/next page; edge-eligible query and edge-active merge policy.
Choose by response time: overnight/scheduled → Batch; qualifying events as they arrive → Streaming; same-page/next-page experience → Edge, if eligible.

Current eligibility nuance: Adobe’s streaming rules have evolved. Current docs state that new/edited definitions with a single event and a window longer than 24 hours, or a single event with no time window, are evaluated using batch rather than streaming/edge. A segment combining batch and streaming sources can also be evaluated as batch under current rules. Existing definitions may behave differently until edited. Check current eligibility documentation.

Multi-entity, sequential, dynamic segmentation

Multi-entity

Extends profile segment logic with related non-person dimension entities such as product, store, plan, or provider. Requires correctly modeled relationships.

Example: Patients whose related Plan entity has planType = Premium.

Sequential

Tests an ordered sequence of events or conditions. Order matters.

Example: Product viewed → added to cart → checkout abandoned.

Dynamic

Uses changing profile/event values or relative criteria so membership reflects current data. Distinguish dynamic audience membership from streaming evaluation.

Example: Current Gold members with qualifying recent activity.

Segment of segments

Combines reusable audiences. The resulting evaluation behavior depends on included segments and current eligibility rules.

Example: Eligible members AND recent purchasers, excluding opt-outs.

Multi-entity segmentation checklist

  1. Model dimension entity with appropriate schema/class.
  2. Define a valid relationship to the Profile schema.
  3. Ensure key fields have compatible types and valid values.
  4. Use the relationship path in Segment Builder.
  5. Verify evaluation method supports the resulting query.
A relationship descriptor does not automatically turn dimension attributes into profile attributes or guarantee streaming/edge eligibility. Relationship support and evaluation support are separate checks.

Aggregate functions and export jobs

Segment Builder supports numeric aggregations SUM, AVERAGE, MIN, and MAX.

FunctionQuestionExample
SUMTotal?Total purchase value exceeds $250.
AVERAGEMean?Average order value exceeds $75.
MINSmallest?Minimum basket value was above $20.
MAXLargest?At least one order exceeded $500.

For counts, recency, frequency, and sequence logic, use the appropriate event-counting and time constraints; do not assume a numeric aggregation function handles every requirement.

Segmentation job vs destination export schedule

  • Segment membership indicates whether a profile currently qualifies.
  • Batch evaluation is performed through segmentation jobs.
  • Destination export is a separate downstream operation.
  • Audience counts require completed evaluation and the correct sandbox, merge policy, identity graph, and data freshness.
  • Flexible batch schedules and on-demand evaluation are documented capabilities with availability caveats; destination cadence is configured separately.
Scenario: Is a custom-class attribute eligible for streaming?

Do not answer from “custom class” alone. Check whether the schema is related to Profile and whether the segment expression and referenced data meet current streaming rules. Multi-entity segmentation can use related dimension data, but adding dimension data can affect evaluation eligibility. If the definition is not eligible, it can be evaluated using batch. Verify the evaluation method shown in Audience Builder.

Scenario: real-time onsite personalization?

For same-page or next-page decisioning, choose Edge segmentation when the query and merge policy qualify. For near-real-time qualification from streaming events without the same-page requirement, Streaming may fit better.

Scenario: why does merge policy change audience count?

A merge policy determines identity stitching method and which profile dataset attributes construct the profile view. A different policy can change profile attributes, consolidation, and audience qualification/count. Choose the policy that reflects the trusted source and intended use case—not the one that simply produces the largest count.

Domain 3

Profile and Identity

Identity Service connects identity values into an identity graph. Real-Time Customer Profile uses that graph and profile fragments to construct a merged operational profile.

Source records/events → Identity Service → Identity graph → Profile fragments → Merged profile
  • Identity Service: resolves and links identity values across datasets.
  • Profile: retrieves fragments associated with identities in the graph and merges attributes/events according to the merge policy.
  • Union schema: aggregate structure from Profile-enabled record schemas sharing the same XDM class; not a separate dataset.
  • Profile fragment: data contributed by a particular dataset/identity context before the merged view is assembled.

Primary and secondary identities

Primary/secondary designation affects how profile fragments are stored and linked. Identity Service establishes links when records carry multiple fields marked as identities. The namespace and values form the graph nodes; do not interpret primary/secondary as a business ranking of identity quality.

Merge policies: conflict resolution

MethodHow it choosesBest fitNuance
Timestamp orderedMore recently ingested fragment takes precedence using system ingestion timestamp.Latest ingested fragment should win.Ingestion time is not necessarily source business-update time.
Dataset precedenceDatasets are selected and ordered; higher-priority dataset wins.A trusted source must be authoritative.Only selected datasets participate in the configured precedence order.

Example: Loyalty says Gold; CRM says Silver. Timestamp ordered may select whichever fragment was ingested most recently. Dataset precedence selects the configured higher-priority dataset regardless of arrival order.

Exam wording: “Which source is authoritative?” → Dataset precedence. “Most recently ingested update wins?” → Timestamp ordered.

Profile collapse, split, and identity graph changes

When identity updates remove an incorrect link and an over-stitched profile separates into distinct valid profiles, the concept being tested is profile collapse / graph recomputation (also described as profile un-stitching or identity graph split). Previously combined fragments no longer resolve to one person. Exact processing mechanics and timing depend on the identity update and platform services.

Hub profile vs Edge profile

HubEdge
Central Experience Platform environment where broader profile data and services are maintained.Distributed edge location used for low-latency personalization and edge decisioning.
Supports broader profile context and central processing.Optimized for immediate access to relevant profile/context; not every hub attribute or audience is automatically present at every edge.
Think: persistent central operational profile.Think: low-latency context for same-page/next-page experience.

Profile size and guardrails

  • Profile size is influenced by identity graph structure, number of fragments, event history, volume, and number of Profile-enabled datasets.
  • Do not store every historical fact as a current profile attribute if it belongs in an event dataset.
  • Avoid unnecessary identity links and excessive secondary identities.
  • Keep high-volume behavioral history in event data and plan retention/expiration.
  • Review current Profile and Identity Service guardrails and licensed entitlements.

Domain 4

Governance, DULE, ABAC, and Consent

Governance questions test whether you can distinguish the right to access data from the permitted use of data.

DULE framework: labels + policies + marketing actions

Apply data usage labels → Enable data usage policies → Associate marketing action with destination → Policy evaluation/enforcement
  • Data usage labels: classification tags applied to schema fields or datasets to describe use restrictions.
  • Data usage policies: rules that restrict or allow marketing actions based on labels.
  • Marketing actions: the action/purpose being performed, often associated with a destination (for example, export to a third party).
  • Policy enforcement: evaluates whether the proposed action violates an enabled policy.

Adobe labels commonly use categories such as identity (I), sensitive (S), and contractual (C), with more specific labels under these families. Check the current label taxonomy for exact codes.

Critical: A label alone does not necessarily block activation. The policy must be configured and enabled, and the relevant marketing action must be evaluated. Adobe documents core data usage policies as disabled by default until enabled.

Policy enforcement workflow

  1. Apply labels to relevant schema fields or datasets.
  2. Create/select a data governance policy combining a marketing action with restricted labels.
  3. Enable the policy.
  4. Configure the destination with applicable marketing action(s).
  5. Attempt activation or use Policy Service to test the action.
  6. Resolve a violation by changing the legitimate data use, destination purpose, or audience/attribute selection—not by removing a valid label just to bypass policy.

ABAC vs DULE

DimensionDULE / Data GovernanceABAC / Access Control
QuestionMay this data be used for this marketing purpose?May this user/role access this data or capability?
ControlsData usage labels, data usage policies, marketing actions.Labels/attributes on objects and access policies assigned to users/roles.
ExampleDo not export sensitive data to third-party advertising.Only privacy team can view a restricted schema field.
OutcomeActivation/data-use operation can be denied.User access to an object/field/segment can be restricted.

Consent

Consent is a customer preference/permission signal that can determine whether a profile is eligible for activation. It is distinct from DULE labels and ABAC permissions. Consent policy capabilities and automatic enforcement can depend on purchased Adobe Shield products and org configuration; do not assume universal availability.

Scenario: ethnicity-related field

Ethnicity is sensitive personal information. Apply the appropriate sensitive-data label(s) from the current Adobe taxonomy and the organization’s legal/privacy classification. Do not guess a label code without checking the current reference. Then evaluate the marketing action and policy.

Scenario: enabling ABAC on a field

  1. Identify the schema field requiring restricted access.
  2. Apply the appropriate access-control label/attribute.
  3. In Permissions, define/update the access policy for the relevant role/user group and resource attributes.
  4. Assign users to the intended role and test with a representative account.
  5. Verify restriction in the relevant UI/API experience.
Answer elimination: “Prevent marketers using data in a destination” → DULE. “Prevent a user seeing/editing a field” → ABAC.
Domain 5

Data Sources and Ingestion

Ingestion questions test source compatibility, batch vs streaming behavior, Profile enablement, identity mapping, data correction, monitoring, throughput, and latency.

Batch vs streaming ingestion

AspectBatchStreaming
DeliveryFiles or scheduled loads in discrete batches.Continuous records/messages from client or server systems.
FitCRM extracts, historical loads, periodic reference data.Web/app events, transactions, near-real-time profile updates.
ProcessingValidated/processed as a batch; failures and replay are batch-oriented.Records sent continuously; validation/processing as messages arrive.
CorrectionReplay or Profile upsert/patch patterns where supported.Send corrected events/updates using the supported streaming pattern; a new event does not automatically delete an old one.

Source connectors and ingestion modes are not interchangeable. Check the current Sources catalog for connector, formats, authentication, scheduling, and batch/streaming support.

Data flow and storage layers

Source / connector / API → Ingestion & validation → Data Lake → Profile / Identity processing (if enabled) → Segmentation / destinations

Streaming ingestion data is persisted to the Data Lake. If the dataset is configured for Profile and Identity, data is also processed for those services. Edge availability is separate and depends on configuration and supported use case.

Latency: documented expectations, not promises

Adobe’s current streaming ingestion overview lists expected latency targets of under 15 minutes at the 95th percentile for B2C Profile ingestion and under 30 minutes at the 95th percentile for B2B Profile ingestion; Data Lake availability is listed as under 60 minutes. These are expectations, not a guarantee every record appears in every service instantly. Source, validation, volume, queue depth, Profile processing, and destination cadence affect end-to-end timing.

What happens when incorrect data is ingested again?

Append / new event

A new ExperienceEvent is generally another event record. Re-ingesting a corrected event does not automatically mean the old event is overwritten. Design event IDs, deduplication, replay, and retention carefully.

Profile record update

Profile attributes can be updated by later fragments according to merge policy. For supported batch Profile updates, use the upsert/patch workflow with an upsert-enabled dataset and matching identity fields.

Batch replay: replaces an already ingested batch, equivalent to deleting the old batch and ingesting a new one. Profile upsert/patch: separate supported mechanism for updating Profile records; documented batch patch does not apply to ExperienceEvents.

Identity mapping during ingestion

  • Map source identifiers to correct XDM identity fields and namespaces.
  • Represent the same real-world identity consistently across datasets.
  • Choose one primary identity per record where multiple identity fields are present; other identities can be secondary.
  • Do not map transaction/session IDs or shared household values as person identities unless semantics support it.
  • Validate identity graph behavior with representative records before production.

Operational controls and monitoring

  • Monitor batch status, row-level validation errors, source flow runs, and throughput.
  • Check dataset Profile enablement and schema compatibility.
  • Review ingestion health checks and batch/volume guardrails.
  • Plan replay and correction procedures before historical loads.
  • Use secure connection configuration and connector-specific authentication requirements.
Guardrail reminder: Limits depend on org/license and change over time. Current Adobe ingestion guardrails include batch file/size recommendations, record-size limits, Profile batch frequency guidance, and streaming throughput guidance. Use the live guardrails page and Product Description/Sales Order for exact numeric entitlements.

Security and authentication

Authentication depends on ingestion path: source connector credentials, API credentials/OAuth or service-account mechanisms, and connection-specific methods. For exam answers, identify the connector/API and follow its documented authentication flow; there is no single universal authentication method for all sources.

Domain 6

Activation and Destinations

Activation sends qualified audience/profile data to an external destination. Destination setup, audience selection, attribute mapping, schedule, governance, and monitoring are separate decisions.

Destination patterns

PatternPurposeArchitect checks
Streaming / APISend audience qualification/profile updates to partner endpoints.Endpoint limits, identity mapping, governance/consent, payload contract, retries, monitoring.
Batch / fileExport audience membership/profile attributes as scheduled files.Full vs incremental, schedule, format, security, freshness.
Cloud dataset exportExport raw dataset records for warehouse, BI, data science, or archive.Dataset export is not audience activation; choose correct workflow.

Audience activation vs dataset export

Activate an audience when the requirement is to send profiles grouped by qualification. Export a dataset when the requirement is to send raw dataset records for analytics, warehousing, or data science. Some file destinations support both, but workflow and data shape differ.

Activation configuration checklist

  1. Confirm destination supports the data type: audiences, profiles, accounts, or datasets.
  2. Configure connection and authentication.
  3. Select audiences and/or profile attributes.
  4. Map correct identity fields and destination attributes.
  5. Configure full/incremental export and schedule as supported.
  6. Apply marketing action and verify governance/consent.
  7. Review activation summary, run status, export counts, errors, and partner receipt.

Guardrails and mapping limits

Limits vary by destination and partner. Attribute mapping maximums, audience counts, export frequency, file sizes, and throughput must be checked in the specific destination documentation and current guardrails. Do not memorize one universal maximum mapped-field number from an unverified note.

Multiple audiences on one destination

It is often possible to add multiple audiences to one destination dataflow, but mappings and settings depend on the destination/workflow. If audiences require different attributes or schedules, validate whether one dataflow supports it. For dataset exports, all datasets in one dataflow share the same schedule; create separate dataflows when schedules differ.

Exam rule: If valid governance blocks activation, choose a compliant data path or destination. Do not remove a label or disable a policy simply to make activation succeed.
Exam technique

How to break down a scenario question

  1. Identify the scenario: modeling, identity, segmentation, governance, ingestion, or activation.
  2. Find the hidden requirement: current state vs event, source of truth, response time, user access vs data use, raw export vs audience activation.
  3. Identify entity grain: person, event, provider, plan, product, account, transaction.
  4. Eliminate answers violating governance, identity semantics, or XDM standards.
  5. Check downstream implications: Profile enablement, merge policy, segmentation eligibility, destination support.
  6. Choose the simplest supported architecture that meets the requirement.

Profile clues

Current, preferred, member status, demographic, loyalty tier, contact preference.

Event clues

Clicked, purchased, booked, submitted, viewed, occurred, sequence.

Edge clues

Same page, next page, immediate browser personalization.

DULE vs ABAC

“Can this data be exported?” → DULE. “Can this user view this field?” → ABAC.

When two answers look similar: Compare entity grain, supported evaluation mode, identity validity, and governance. One answer may meet the business need but use the wrong platform construct.
Revision

Common pitfalls

  • Wrong merge policy: conflicts resolve from the wrong source.
  • Incorrect primary identity: profiles fragment or stitch incorrectly.
  • Profile not enabled: data lands in Data Lake but does not contribute to Profile.
  • Mapping issues: wrong XDM path, namespace, data type, or destination field.
  • Edge vs Hub confusion: assuming all hub attributes/audiences are immediately available at edge.
  • Wrong data type: numeric values stored as strings, inconsistent dates, incompatible relationship keys.
  • Governance violation: ignoring labels, policies, marketing actions, or consent.
  • TTL/retention assumptions: treating retention as universal instead of service/dataset specific.
  • Over-modeling: custom classes or duplicate data before checking standard XDM.
  • Over-enabling: Profile/Identity enabled on datasets that do not need it.
  • Evaluation/export confusion: audience job and destination dataflow are separate.
  • Assuming re-ingestion overwrites: events, upserts, batch replay, and append ingestion differ.
