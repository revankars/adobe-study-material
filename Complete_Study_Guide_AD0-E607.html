Journey Types & Entry Points

1. Unitary Event Journey
Trigger: Customer performs an action (click, purchase, form submission)
Timing: Real-time, immediate
Reentrance: 5-minute block (default)
Event payload limit: 64 KB

Best for: Immediate reactions, real-time personalization

Example: Customer abandons cart → email within 15 minutes
Key guardrails:
  • 5-minute reentrance block prevents duplicate messages
  • 64 KB event payload limit (exceeding drops event silently)
  • 1 MB journey instance limit (data accumulation during execution)
  • Cannot coexist with business events in same journey
2. Business Event Journey
Trigger: External system sends an event (not customer action)
Timing: Scheduled or batch
Best for: Aggregated data, scheduled sends
Example: Daily purchase summary email at midnight
Key guardrails:
  • Cannot coexist with unitary events in same journey
  • Cannot coexist with audience qualification
3. Read Audience Journey
Trigger: Scheduled batch read of an audience
Timing: Daily, weekly schedule or triggered by business event
Best for: Batch campaigns, audience-wide initiatives
Example: Every Monday 9 AM, read all VIP customers and send weekly digest
Key guardrails:
  • 5 concurrent instances max (organization-wide) - Stagger 5-10 minutes apart
  • 12-hour processing timeout
  • 20K profiles/sec sandbox throughput
  • One audience per journey
  • Cannot use with Campaign Standard activities
4. Audience Qualification Journey
Trigger: Customer enters or exits an audience in real-time
Timing: Real-time as they qualify/disqualify
Activation delay: Up to 10 minutes
Example: Churn score changes → immediately trigger retention journey

Journey Validation

What Gets Validated:
  • ✅ Activity configuration (required fields filled)
  • ✅ Event setup (correctly configured)
  • ✅ Expression syntax (valid, fields exist)
  • ✅ Audience references (exist and accessible)
  • ✅ Message content (valid)
  • ✅ Payload size (under 2 MB warning threshold)
  • ✅ Activity count (under 50)
  • ✅ Journey structure (no orphaned activities)
What Does NOT Get Validated:
  • ❌ Whether conditions make logical sense
  • ❌ Whether journey achieves business goals
  • ❌ Whether fallback offers are appropriate

Journey Entry Points (Critical Distinction)

1. Unitary Event Journey

Trigger: Customer performs an action (click, purchase, form submission) Timing: Real-time, immediate Reentrance: 5-minute block (default) Event payload limit: 64 KB Best for: Immediate reactions, real-time personalization Example: Customer views product → email within 15 minutes

Key guardrails:

  • 5-minute reentrance block prevents re-entry
  • 64 KB event payload limit
  • 1 MB journey instance limit
  • Cannot use with business events in same journey
2. Business Event Journey

Trigger: External system sends an event (not customer action) Timing: Can be scheduled or batch Reentrance: No automatic block Best for: Aggregated data, scheduled sends Example: Daily purchase summary email at midnight

Key guardrails:

  • Cannot coexist with unitary events
  • Cannot coexist with audience qualification
3. Read Audience Journey

Trigger: Scheduled batch read of an audience Timing: Runs on schedule (daily, weekly) or triggered by business event Reentrance: Based on audience evaluation schedule Best for: Batch campaigns, audience-wide initiatives, scheduled sends Example: Every Monday 9 AM, read all VIP customers and send weekly digest

Key guardrails:

  • 5 concurrent instances max (organization-wide)
  • 12-hour processing timeout
  • 20K profiles/sec sandbox throughput
  • One audience per journey
  • Cannot use with Campaign Standard activities
  • Batch audiences evaluated daily only
  • Streamed audiences always up-to-date

Data refresh timing:

  • At journey entry: Uses batch audience snapshot
  • At Wait activity: Automatically refreshes profile attributes from Unified Profile Service
4. Audience Qualification Journey

Trigger: Customer enters or exits an audience in real-time Timing: Real-time as they qualify/disqualify Best for: Dynamic, real-time audience changes Example: Churn score changes → immediately trigger retention journey

Key guardrails:

  • Cannot use with Campaign Standard activities
  • 10-minute activation delay
  • 300 max per sandbox (across all journeys)
  • Cannot use supplemental identifiers
  • Cannot change audience/namespace in versions

Journey Evaluation (After Running)

Key Metrics:

  • Entries: Total profiles who entered
  • Exits: Total who completed/exited
  • In Progress: Currently in journey
  • Errors: In error status (usually 1 MB limit)
  • Completion rate: (Exits / Entries) × 100
  • Drop-off by activity: Where profiles exit
  • Time to completion: Duration from entry to exit
  • Conversion rate: % who completed desired action

Common Issues:

  • High error rate → 1 MB instance limit breach
  • Low completion → Restrictive conditions or long waits
  • Stuck mid-journey → Condition not matching or system issue
  • Selective failures → Data accumulation for certain profiles
  • No entries → 64 KB event limit (events dropped at entry)

Core Difference

Aspect Journey Campaign
Trigger Event-driven OR scheduled audience read Scheduled send at specific time
Timing Real-time or ongoing Batch/one-time or scheduled
Duration Days, weeks, months Usually single or coordinated sends
Personalization Real-time per customer Pre-determined per segment
Complexity Multi-step, branching, conditions Usually linear
Use case React to customer action Send message to audience at time

When to Use Each

Use JOURNEY when:

  • Customer behavior triggers message (event-driven)
  • Need multi-step, sequential experience
  • Want real-time personalization
  • Need to wait and react to events

Use CAMPAIGN when:

  • Send at specific scheduled time
  • Send same message to entire audience
  • One-time or coordinated sends
  • Don't need event-triggered logic

Exam Scenarios

Journey Example: "Customer books flight → email at booking → 24-hour wait → reminder email before flight" → Why: Event-triggered, multi-step, sequential

Campaign Example: "Every Friday 2 PM, send newsletter to all subscribers" → Why: Scheduled time, audience-based, not event-triggered

Both Support Same Tools

  • Email, SMS, Push, In-app, Web messages
  • Personalization fields
  • Fragments (visual, expression)
  • Offer Decisioning
  • A/B testing
  • Asset Essentials

Difference is HOW they're triggered, not WHAT tools they use.

Core Concepts

1. Offer
An individual piece of content/promotion
Examples: "Get 20% off", "Free shipping", product recommendation
Contains: Name, channels, content, constraints, eligibility rules
2. Collection
Grouping of related offers
Example: "Summer Promotions" collection with 5 summer offers
Purpose: Organize offers logically, control scope
3. Decision
Logic that selects which offer to show
Specifies: Collection, eligibility rules, ranking/priority, capping, fallback offer
4. Placement
Where and how offer is delivered
Tied to channel: Email header, Web banner, SMS text, In-app popup
5. Decision Policy
Complete machine that brings it all together
Formula: Decision Policy = Collection + Decision Logic + Placements + Offers

The 4 Stages of Offer Decisioning

Stage 1: Create Offers
Define individual offers with content, channels, constraints
Set eligibility rules per offer
Status: Draft → Approved → Live
Stage 2: Organize Into Collections
Group related offers
Creates logical structure
Stage 3: Build Decisions
Create decision logic (ranking, capping, eligibility)
Select collection
Define fallback offers
Set up constraints
Stage 4: Deploy Decisions
Use decision in journey via Content Decision activity
System evaluates rules in real-time for each customer
Best matching offer selected and delivered

Static vs. Dynamic Offers

Aspect Static Offer Dynamic Offer
Definition Fixed content for all customers Content changes based on customer data
Example "Get 20% off your next purchase" "Get {{discountPercentage}}% off, {{firstName}}"
Personalization None (same for everyone) Uses profile attributes, dynamic fields
Complexity Simple, easy to manage More complex, needs data setup
Performance Faster (no data lookup needed) Slightly slower (evaluates expressions)
Exam Pattern: If scenario says "personalize based on customer data" → dynamic offer

Capping & Ranking Logic

How Capping Works
Capping is PER-OFFER, not decision-level
Example:
Offer A: "Robo-Advisor Service" (priority 1, capped at 3/month)
Offer B: "Managed Portfolio" (priority 2, capped at 3/month)
Offer C: "Self-Directed Trading" (priority 3, capped at 3/month)

Customer has received Offer A 3 times this month (capped)
System evaluates: A is capped, skip it
System evaluates: B hasn't reached cap → deliver B
(Does NOT deliver fallback)
Key Rule: When top-priority offer is capped → system selects next ranked uncapped offer. Does NOT fail decision.

Static vs. Dynamic Offers (detailed notes)

Static Offer

  • Fixed content for all customers
  • Example: "Get 20% off your next purchase"
  • No personalization
  • Faster performance

Dynamic Offer

  • Content changes based on customer data
  • Example: "Get {{discountPercentage}}% off, {{firstName}}"
  • Uses profile attributes, dynamic fields
  • More complex but personalized at scale

Exam pattern: If scenario says "personalize based on customer data" → dynamic offer

When to Use Offer Decisioning (detailed notes)

USE Offer Decisioning when:

  • Need to choose WHICH offer to show based on eligibility rules
  • Multiple offers available, system selects best one
  • Need frequency capping per offer
  • Need ranking/priority logic

DON'T use Offer Decisioning when:

  • Just personalizing email content (use personalization fields)
  • A/B testing different subject lines (use Content Experiments)
  • Sending same generic promo to all (simpler to send one email)

Personalized Fields

What They Are
Placeholders replaced with actual customer data at send time
Syntax
{{profile.attributes.firstName}} {{event.productName}} {{profile.segmentMembership.goldTier}} {{context.journeyName}}
Data Sources
  • Profile attributes: firstName, email, loyaltyTier, lastPurchaseDate
  • Event data: productViewed, cartValue, eventTime
  • Contextual data: journeyName, campaignId
Key Rules
  • ✅ Fields must exist in profile or event schema
  • ❌ Cannot reference non-existent fields (causes failure)
  • ✅ Can use conditional logic: {{if profile.attributes.loyaltyTier == "VIP" then "exclusive offer" else "standard offer"}}

Visual Fragments

What: Pre-designed HTML blocks (headers, footers, banners, images)
Size limit: 700 KB max
Channels: Email ONLY
Status required: Must be "Live" to use
Use Cases
  • Include branded footer in every email
  • Reuse logo + social links + unsubscribe + copyright
  • Static design blocks that don't change per customer
Benefits
  • ✅ Consistency across all emails
  • ✅ Update once, all messages update
  • ✅ Version control for shared content

Expression Fragments

What: Reusable personalization logic/expressions
Size limit: 700 KB max
Channels: Email, SMS, Push (NOT in-app)
Status required: Must be "Live" to use
Example
{{if profile.attributes.loyaltyTier == "GOLD" then "You get 30% off" else "You get 10% off"}}
Use Cases
  • Apply same loyalty tier logic to all messages
  • IF/THEN logic for different messages
  • Reusable business rules
Critical Rule
Expression fragments CANNOT be used in in-app messages
Use personalization fields for in-app instead

Content Experiments (A/B Testing) (detailed notes)

What You Can Test
  • Subject line variations
  • Email body copy variations
  • Call-to-action button text
  • Images/visual elements
  • Different offers
What You CANNOT Test
  • Different channels (email vs. SMS) in same experiment
  • Targeting/audience (applies to all qualified profiles)
Experiment Structure
Email Activity with Experiment
├── Control (A): Original subject "Save 30%"
├── Variant B: Alternative "Limited time: 30% off"
├── Variant C: Alternative "Your exclusive offer inside"
├── Traffic allocation: 33% each
└── Win criteria: Highest click rate
    └── Winner auto-sent to remaining profiles
    └── Results recorded
Setting Up Experiments (Critical)

Traffic Allocation

  • How many profiles get each variant?
  • Example: 33% control, 33% variant B, 33% variant C
  • Must total 100%

Test Duration

  • How long before declaring winner?
  • Depends on traffic volume (no fixed minimum)
  • Recommendation: Long enough to be statistically significant

Win Criteria

  • What metric defines "winner"?
  • Awareness campaign → track opens
  • Conversion campaign → track clicks or conversions

Holdout & Winner Assignment

  • Holdout: Profiles not in experiment (control sample)
  • Winner: Remaining traffic auto-gets winning variant
Interpreting Results (Exam-Critical)

Example Results:

Control: 35% open rate, 7% CTR
Variant B: 38% open rate ← Winner, 7.5% CTR
Variant C: 32% open rate, 6% CTR

What it tells you:

  • Variant B won (highest metrics)
  • Urgency language resonates better

What to test next:

  • If differences are small (1-2%) → test different variable (send time, not subject)
  • If differences are significant → declare winner, roll out
  • Don't keep testing same variable if already optimized

Statistical significance matters: Small differences with large sample might be noise

Common Exam Traps

Trap 1: Confusing fragments with templates

  • Fragments are blocks; templates are complete structures
  • Fragments go INSIDE templates

Trap 2: Thinking experiments test targeting

  • Experiments test MESSAGE VARIANTS, not audience segments
  • Use journey conditions for audience targeting

Trap 3: Using visual fragments for dynamic content

  • Visual fragments are static HTML
  • Use expression fragments for conditional logic

Trap 4: Using expression fragments in in-app

  • Expression fragments NOT supported in in-app
  • Use personalization fields instead

Trap 5: Ignoring statistical significance

  • Small differences might be random variation
  • Look at sample size and magnitude of difference

Schemas: Profile vs. Event

Memory Trick
PROFILE = "WHO is the customer?" (Static attributes)
EVENT = "WHAT did they do?" + "WHEN?" (Time-series actions)
Profile Schema (XDM Individual Profile)
Purpose: Stores customer attributes (WHO they are)
Data type: Personal info — name, email, age, preferences, loyalty tier
When enabled for profile: Profile data stored in Unified Profile Service (real-time access)
Example fields: firstName, lastName, email, phone, loyaltyTier, lastPurchaseDate
Event Schema (XDM ExperienceEvent)
Purpose: Stores what customers did (behavioral events)
Data type: Time-series events — purchase, click, view, search
When enabled for profile: Event data stored and linked to customer profiles
Example fields: eventType, timestamp, productViewed, purchaseAmount, pageURL

Datasets

Datasets Enabled for Profile
  • ✅ Data ingested into Unified Profile Service (real-time)
  • ✅ Available for real-time personalization in journeys
  • ✅ Can be referenced in journey conditions
  • ⚠️ Counts against engageable profile quota (costs money)
Datasets NOT Enabled for Profile
  • ❌ Data stays in Data Lake only (not real-time)
  • ❌ Cannot be accessed instantly in journeys
  • ❌ Can be queried/analyzed but not for real-time personalization
  • ✅ Does NOT count against engageable profile quota (no cost)
Exam Pattern
"Marketer wants to use purchase history in journey condition. Dataset enabled for profile?"
Answer: YES, must be enabled for profile

Identities

Authenticated Identities (Known Customers)
  • Email: john@example.com
  • CRM ID: CUST-12345
  • Mobile AAID/IDFA: Unique mobile device ID
  • Custom ID: Your proprietary customer ID
Pseudonymous Identities (Anonymous/Unknown Visitors)
  • ECID (Experience Cloud ID): Adobe's auto-generated ID for unknown browsers
  • Used for: Tracking anonymous website visitors
  • Gets merged: When visitor logs in, ECID + email link together
Identity Merging
Scenario:
Day 1, 2 PM: Anonymous visitor (ECID-12345) views products, adds to cart
Day 1, 3 PM: Same person logs in (email: john@example.com, CRM ID: CUST-54321)
System links: ECID-12345 + email + CRM ID → same profile
ALL historical data merges automatically

Journey condition "if customer viewed products + added to cart in last 24 hours"
System finds ALL merged data → triggers journey ✓
Engageable Profile Impact
  • ✅ Authenticated identities (email, CRM ID) = count as engageable
  • ✅ Pseudonymous identities (ECID) = count as engageable too
  • 💡 Solution: Set TTL (Time-To-Live) on pseudonymous profiles to auto-delete
  • 💡 Recommendation: 14-day TTL for pseudonymous profiles

Audiences

Segment Builder (Rule-Based Audiences)
  • How: Drag-and-drop conditions
  • Timing: Batch (daily) OR streamed (real-time)
  • Example: "Customers who spent > $500 in last 30 days"
Audience Composition (Orchestrated Audiences)
  • How: Combine multiple audiences with logic
  • Timing: Batch evaluation
  • Example: "(VIP customers) + (recently inactive) - (already contacted)"
  • Limit: Max 50 published compositions per sandbox

Real-time update? YES (immediately) NO (daily)

Use in journey Audience Qualification (real-time trigger) Read Audience (scheduled batch)

The Data Flow in AEP

1. Data ingestion ↓ 2. Schema defines structure ├── Profile Schema (WHO) └── Event Schema (WHAT + WHEN) ↓ 3. Dataset container based on schema ├── Enable for profile? (should be real-time?) ↓ 4. Identities link records to customer ├── Authenticated (email, CRM ID) └── Pseudonymous (ECID) ↓ 5. Unified Profile Service (if profile-enabled) ↓ 6. Audiences segment customers ├── Streamed (real-time) └── Batch (daily) ↓ 7. Journeys use audience + profile data └── Real-time personalization
GUARDRAILS

Schemas (The Data Blueprint)

Profile Schema (XDM Individual Profile)

Purpose: Stores customer attributes (WHO they are)

Data type: Personal info — name, email, age, preferences, loyalty tier

When enabled for profile: Profile data stored in Unified Profile Service (real-time access)

Real-time access: Can be accessed instantly in journeys

Example fields: firstName, lastName, email, phone, loyaltyTier, lastPurchaseDate

Key rule: Attributes that describe the customer

Event Schema (XDM ExperienceEvent)

Purpose: Stores what customers did (behavioral events)

Data type: Time-series events — purchase, click, view, search

When enabled for profile: Event data stored and linked to customer profiles

Real-time access: Events can trigger journeys in real-time

Example fields: eventType, timestamp, productViewed, purchaseAmount, pageURL

Key rule: Actions with timestamps, what happened WHEN

Schema Distinction Memory Trick
PROFILE = "WHO is the customer?" (Static attributes)
EVENT = "WHAT did they do?" + "WHEN?" (Time-series actions)

Datasets (The Data Containers)

Datasets Enabled for Profile
  • Data ingested into Unified Profile Service (real-time profile)
  • Available for real-time personalization in journeys
  • Can be referenced in journey conditions and personalization fields
  • Counts against engageable profile quota (costs money)
  • Example: Customer behavior, purchase history, preference updates
Datasets NOT Enabled for Profile
  • Data stays in Data Lake only (not real-time profile)
  • Cannot be accessed instantly in journeys
  • Can be queried/analyzed but not for real-time personalization
  • Does NOT count against engageable profile quota (no cost)
  • Example: Historical data for analysis, logs, archive

Exam pattern: "Marketer wants to use purchase history in journey condition. Dataset enabled for profile?" → YES

Identities (How We Know Who Customers Are)

Authenticated Identities (Known Customers)
  • Email: john@example.com
  • CRM ID: CUST-12345
  • Mobile AAID/IDFA: Unique mobile device ID
  • Custom ID: Your proprietary customer ID
Pseudonymous Identities (Anonymous/Unknown Visitors)
  • ECID (Experience Cloud ID): Adobe's auto-generated ID for unknown browsers
  • Used for: Tracking anonymous website visitors before login
  • Gets merged with authenticated ID: When visitor logs in, ECID + email link together
Identity Merging
Before login: Visitor is ECID (pseudonymous)
  └─ All behavior linked to ECID-12345

Login event: Visitor enters email john@example.com
  └─ ECID-12345 + Email + CRM ID all link to same profile
  └─ ALL historical data (clicks, views, carts) auto-merge

Journey condition runs: "If customer viewed products + added to cart"
  └─ System finds historical behavior from ECID time
  └─ Triggers journey with merged data

Engageable profile impact:

  • Authenticated identities (email, CRM ID) = count as engageable profiles
  • Pseudonymous identities (ECID) = count as engageable profiles too
  • Solution: Set TTL (Time-To-Live) on pseudonymous profiles to auto-delete inactive ones
  • Recommendation: 14-day TTL for pseudonymous profiles

Audience Types

Segment Builder (Rule-Based Audiences)
  • How: Drag-and-drop conditions (age > 25 AND location = CA AND purchase > $100)
  • Timing: Batch evaluation (typically daily) OR streamed (real-time)
  • Use case: Standard segmentation
  • Example: "Customers who spent > $500 in last 30 days"
Audience Composition (Orchestrated Audiences)
  • How: Combine multiple audiences with logic (Audience A + Audience B - Audience C)
  • Timing: Batch evaluation
  • Use case: Complex audience combinations
  • Example: "(VIP customers) + (recently inactive) - (already contacted)"
  • Limit: Max 50 published compositions per sandbox
Streamed vs. Batch Audiences
Aspect Streamed Batch
Real-time update? YES (immediately) NO (daily)
When evaluated? Real-time as rules change Once per day
Use in journey? Audience Qualification (real-time trigger) Read Audience (scheduled batch)
Recommendation Use for real-time logic Use for scheduled campaigns

Exam pattern: "Real-time journey trigger when audience changes" → streamed audience + Audience Qualification activity

Critical Exam Connections

Connection 1: Schemas → Datasets → Journeys

  • Attribute must be in profile schema
  • Schema used in profile-enabled dataset
  • Data ingested into dataset
  • Then accessible in journey

Connection 2: Identities → Profiles → Personalization

  • Anonymous visitor (ECID)
  • Becomes customer (email, CRM ID)
  • Identity merges automatically
  • All historical data accessible

Connection 3: Audiences → Journeys → Data Labels

What's the data pattern?

DECISION TREES

Tier 1: Most Tested Guardrails

1. The 50-Activity Limit
  • What: Maximum 50 activities per journey
  • When applied: At publish time
  • What fails: Publishing blocked with error
  • Solution: Split into sub-journeys using jump activities
  • Exam trigger: "Journey won't publish" or "Too many activities"
  • Key rule: Cannot increase limit; must split
2. The 5-Minute Reentrance Block (Unitary Events)
  • What: Profile cannot re-enter same unitary event journey for 5 minutes
  • Example: Event fires at 12:01 PM → journey starts. Same event at 12:03 PM → blocked until 12:06 PM
  • Why: Prevents duplicate messages
  • Exam trigger: "Why isn't customer getting second email?" or "Profile triggered twice but got one message"
  • Key rule: This is automatic; customer cannot bypass it
3. The 64 KB Event Payload Limit
  • What: Event entering journey cannot exceed 64 KB (uncompressed JSON)
  • When applied: When event enters journey (at start activity)
  • What happens: Event silently dropped → profile never enters → no log entry
  • Symptom: Zero profiles entering despite events being sent
  • Exam trigger: "Why are NO profiles entering the journey?"
  • Key rule: 64 KB applies ONLY at entry; different from 1 MB instance limit
4. The 1 MB Journey Instance Limit
  • What: All data accumulated during journey execution ≤ 1 MB
  • When applied: During journey execution (mid-journey)
  • What happens: Profile marked ERROR status → exits journey
  • Symptom: SOME profiles error (usually those with more data), SOME complete
  • Data that counts: Event payload + profile attributes + API responses + email content
  • Recommendation: Keep initial event < 800 KB for buffer
  • Exam trigger: "500 of 10,000 profiles errored. All errors are high-value accounts" → 1 MB limit
  • Key rule: Selective profile failures point to this limit
5. The 200 Active Journeys Limit (Production) / 100 (Development)
  • What: Maximum 200 live/paused/closed journeys in production
  • When applied: At publish time
  • Solution: Pause or delete old journeys
  • Exam trigger: "Cannot publish journey" or "Active journey limit reached"
6. The 5 Concurrent Read Audience Instances
  • What: Only 5 Read Audience journeys running simultaneously across entire organization
  • When applied: At publish time
  • Solution: Stagger start times 5-10 minutes apart
  • Exam trigger: "Why does Team 6's Read Audience journey fail to publish when Teams 1-5 succeeded?"
  • Key rule: Organization-wide limit, not per-sandbox
7. The 12-Hour Read Audience Processing Timeout
  • What: Read Audience jobs must complete within 12 hours
  • What happens: Jobs not processed in 12 hours auto-deleted → journey doesn't run
  • Solution: Ensure audience size processes within 12 hours; split if needed
  • Exam trigger: "Read Audience job didn't execute" or "Journey ran but no profiles"
8. The 2 MB Email Message Content Size
  • What: Final email content (after backend processing) ≤ 2 MB
  • Recommendation: Keep authored content < 1 MB to allow 300-400 KB processing buffer
  • When applied: At publish time
  • What fails: Journey publication blocked if exceeded
  • Exam trigger: "Journey won't publish due to content size"
9. Custom Action Capping: 300K calls/min or 150K calls/30 sec
  • Fast endpoints (< 0.75 sec response): 300,000 calls per minute
  • Slow endpoints (> 0.75 sec response): 150,000 calls per 30 seconds
  • Sliding window applied per sandbox, per endpoint
  • Exam trigger: "Company has 500K profiles wanting to call endpoint" → must throttle
10. Fragment Size Limits
  • Any fragment (visual or expression): 700 KB max
  • Count: up to 60 unique fragments per content variant (warning at 45); 120 across all variants of a message
  • Exam trigger: "Fragment won't save, exceeds size limit"
11. Business Events Cannot Coexist with Unitary Events
  • Rule: Same journey cannot have both business event AND unitary event triggering
  • BUT: Different journeys CAN have different event types
  • Exam trigger: "Can we use business event in Journey A and unitary in Journey B?" → YES
12. Audience Qualification: 10-Minute Activation Delay
  • What: Up to 10 minutes for audience qualification to start listening
  • Exam trigger: "Audience activated but journey didn't start immediately"
13. Audience Compositions: 50 Max Per Sandbox
  • What: Up to 50 published audience compositions per sandbox (Federated compositions are not counted)
  • Solution: Delete old ones to create new ones
14. Event Reference Limit: 1 Event → 25 Journeys Max
  • What: Single event can be used by maximum 25 journeys simultaneously
  • When exceeded: Cannot publish additional journeys using that event
15. Schema Reference Limit: 1 Schema → 100 Events Max
  • What: Single XDM schema can be referenced by maximum 100 events
  • When exceeded: Cannot publish journeys with events using that schema

│  └─ CAMPAIGN
│
├─ External system sends event?
│  └─ JOURNEY (Business Event)

   └─ JOURNEY (Audience Qualification)
