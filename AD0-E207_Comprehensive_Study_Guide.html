How to use this guide

This guide is written so that anyone preparing for AD0-E207 can use it. Each section states what Adobe’s documentation says, notes where that differs from older material, and points to the source.

Ground rules for this guide

  1. Statements marked [Verified] were checked against Adobe’s documentation pages listed in Section 13. Statements marked [Verify] are general guidance or are not yet confirmed, so check them before relying on them.
  2. The practice questions in Section 12 are original, written for this guide. They do not reproduce any live or third-party exam items. Do not add recalled live exam questions to this document. Adobe’s candidate agreement prohibits sharing exam content.
  3. Do not use AI assistants or unauthorized materials during the exam. Adobe’s proctoring rules prohibit unauthorized materials and devices.

2. Discovery (18%)

2.1 Auditing a site

A site audit confirms what is already being collected before any new tracking is designed. Check:

  • Which report suites receive data, and whether they are global, individual, or virtual.
  • Which variables and events are set on each page type (home, product, cart, checkout, confirmation, search results).
  • Whether the page name, page URL, and campaign variables are populated and consistent.
  • Whether the debugger and network requests show the expected values on each page [General guidance, Verify against your organization’s setup].

2.2 Business requirements to measurement

  1. Start with the business goal. Example: “Grow online revenue from returning customers.”
  2. Define KPIs. Example: revenue per visit, return visit rate, conversion rate.
  3. Map each KPI to a metric or dimension. Example: revenue per visit uses the Revenue metric divided by Visits.
  4. Map each metric to a variable or event. Example: “Return visit” needs a visitor-level definition, and “conversion” needs a success event.
  5. Document the measurement framework so the tagging engineer and the developer can implement it.

2.3 Measurement frameworks

A measurement framework links each business objective to KPIs, dimensions, metrics, variables, and the data collection method. Keep it in one table so every stakeholder can review it.

3. Solution design (54%)

3.1 Adobe Analytics architecture and report suites

Global versus individual report suites [General guidance, Verify]

  • A global report suite collects data from several sites or apps into one place.
  • Individual report suites keep each site separate.
  • Rollups combine several report suites for reporting without changing collection.

Virtual report suites [Verified]

  • A virtual report suite is a segment applied to a parent report suite.
  • It inherits most settings from the parent, including eVar settings, processing rules, and classifications. You change those settings on the parent, not on the virtual report suite.
  • It has its own name, components, and permissions, and can be assigned to permission groups.
  • You can change the visit timeout on a virtual report suite. The change is non-destructive and applies in Analysis Workspace only.
  • You cannot upload data to a virtual report suite.
  • Virtual report suites do not delete data. Deletion is handled through data governance (Section 6).

Choosing global versus virtual [General guidance, Verify]

Use one global report suite with virtual report suites when several teams need different slices of the same data. Use separate report suites when the sites need independent settings, such as different eVar definitions or time zones.

3.2 Variables and metrics

Variable types

Variable Scope Typical use
eVar (conversion variable) Persists across hits according to allocation and expiration Campaign, search term, logged-in status, customer segment
prop (traffic variable) Per hit, no persistence by default Page section, content type, pathing
Success event Counts occurrences Purchase, add to cart, form submission, newsletter sign-up
List prop or list eVar Several values in one hit, each reported separately Multiple newsletters, multiple categories, multiple colors
Merchandising eVar Binds to product line items (product syntax) or to the event or order (conversion syntax) Product-level attribution such as search term to cart addition
Counter Counts occurrences of a value Number of search results, number of pages viewed

eVar settings

  • Allocation: Most Recent credits the last value before the success event. Original Value credits the first value set.
  • Expiration: hit, visit, visitor, a specific event, or a time period. Choose expiration to match the business question.
  • Allocation changes affect how data is interpreted. Check Adobe’s current guidance before changing allocation on a live report suite [Verify].

Success events and serialization [Verified]

  • Event serialization prevents duplicate events from being counted. Enable it in the report suite’s success event settings, then send an ID with the event.
  • Each event has its own table. event1:ABC and event2:ABC are both counted.
  • Deduplication is global across visitors. If visitor A sends event1:ABC and visitor B later sends the same ID, B’s event is ignored.
  • Deduplication does not expire.
  • If an event has serialization enabled but no ID, the event is always counted.
  • Serialization IDs must be alphanumeric and up to 20 bytes. Longer values are truncated to 20 bytes.
  • Data sources do not support event serialization.

For the purchase event, use the purchaseID variable instead of event serialization.

purchaseID [Verified]

  • Prevents hits with the same purchase from inflating reports (for example, a page refresh on the confirmation page).
  • Purchase IDs apply to all visitors and expire after 37 months.
  • When a purchase is recognized as a duplicate, conversion data (eVars and events) does not appear in reporting. In data feeds, the duplicate_purchase column is set to 1.
  • Use only alphanumeric characters. Values longer than 20 bytes are truncated, and truncated duplicates are also deduplicated.
  • Do not generate purchase IDs with a random function.

Campaign tracking [General guidance, Verify]

  • s.campaign stores the tracking code. Use s.Util.getQueryParam() or the getQueryParam plug-in to read it from the URL.
  • Campaign persistence (once per visit or once per visitor) controls instance counts. Confirm the persistence setting in your report suite before answering questions about counts.

3.3 Product strings (s.products)

Structure: category;product;quantity;price;events;merchandising eVars, with a comma between products.

  • Each field is separated by a semicolon. Keep the delimiter even when a field is empty.
  • Multiple products are separated by a comma.
  • Merchandising eVars use product or conversion syntax. Product syntax binds to the product line item. Conversion syntax binds to the order or event.
  • Adobe does not support setting the products variable with processing rules [Verified].

Example (illustrative)

s.products = ";Running Shoes;1;120.00,;Socks;2;15.00";

Use the documented structure for your implementation. Confirm exact syntax for merchandising eVars and events against the Implementation Guide [Verify].

3.4 Data collection methods

Adobe Experience Platform Tags (formerly Adobe Launch)

  • Place one single asynchronous embed code in the <head> of each page that loads the property [Verified].
  • The asynchronous embed is the default. The synchronous version uses two embed codes (one in the head and one before </body>) [Verified].
  • Data elements are referenced with %name% syntax [General guidance, Verify].
  • _satellite.track() sends a custom event from code [General guidance, Verify].
  • If a data element returns [object Object], the data element is reading an object. Read a specific property instead of the whole object [General guidance, Verify].

AppMeasurement versus Web SDK [Verified, summary]

AppMeasurement Adobe Experience Platform Web SDK
Data path Sends directly to Adobe Analytics Sends to the Adobe Experience Platform Edge Network, which can forward to Analytics
Variable mapping Variables such as s.eVar1 XDM and data object mapping (for example, xdm.commerce.order.purchaseID and data.__adobe.analytics.purchaseID)
Typical use Existing implementations Newer implementations and Edge Network architectures

Adobe describes both as client-side collection methods that feed the processing pipeline. The processing order described in Section 5 applies to both.

Cross-domain tracking [Verified]

  • When browsers block third-party cookies, the ID service cannot recognize a visitor who moves to a different domain.
  • Visitor.appendVisitorIDsTo(url) appends the Experience Cloud Visitor ID (MID) to a link, so the destination domain can recognize the visitor.
  • You must own both the source and destination domains and have implemented the ID service.
  • Cross-domain tracking does not work if the ECID was rejected earlier.

Asynchronous content [General guidance, Verify]

Content that loads after the page load should be tracked by listening for a specific JavaScript event (for example, a custom event raised when the content is inserted). Do not rely on a single page-load call at the bottom of the page.

Single-page applications (SPA) [General guidance, Verify]

Route changes do not reload the page, so the page view tag does not fire. Track each virtual page view with a custom event or a page view call triggered by the route change. Set the page name and page URL for each route.

Mobile apps [General guidance, Verify]

Mobile apps use the Adobe Mobile SDK. Visit definition settings (background hits, start a new visit on app launch) control how sessions are counted.

3.5 Technical specifications

A technical specification gives the tagging engineer and the developer what they need to implement and test the tracking. Each specification should include:

  1. Business requirement: what the business needs to measure and why.
  2. Tracking requirement: the metric, dimension, or event to capture.
  3. Data layer definition: the field names, data types, and where the value comes from.
  4. Variable mapping: which Analytics variable receives each data layer field, and the variable type and allocation.
  5. Trigger condition: the page load, link click, or event that fires the tracking.
  6. Expected values: sample values for each variable.
  7. Implementation instructions: where in the tag property or code the change goes.
  8. Acceptance criteria: what must be true for the implementation to be accepted.
  9. QA steps: how to test in development, staging, and production.

Example specification row (illustrative)

Requirement Trigger Data layer field Variable Type Expected value
Track search term Search results page load digitalData.search.term eVar2 Text string, Most Recent “running shoes”
Count search results Search results page load digitalData.search.resultCount Counter eVar or custom event Counter 25
Track newsletter sign-ups (each newsletter) Sign-up confirmation digitalData.newsletters (array) List prop List “Weekly Deals”

4. Report suite administration [Verified where noted]

4.1 Processing rules [Verified]

  • Processing rules modify data as it is collected, before it is written to the report suite.
  • They run in order, from rule 1. Every hit runs through every rule. There are no early exits, so the conditions must cover every hit.
  • A report suite can contain up to 150 rules. Each rule can contain up to 30 conditions.
  • Rules apply on save. They do not apply retroactively to data already collected.
  • Rules apply to one report suite. You can copy them to other report suites after they are created.
  • String comparisons are not case-sensitive.
  • A later rule can overwrite the result of an earlier rule. A value overwritten in rule 1 is not available to later rules.
  • Excluding data is not an intended feature of processing rules. Use bot rules, IP exclusion, or VISTA rules instead [Verified].
  • Context data variables that are not mapped to another variable are permanently lost.
  • Test in a development report suite before enabling rules in production.

4.2 VISTA rules [Verified]

  • VISTA rules are a form of custom data modification that runs between data collection and processing.
  • VISTA rules can copy a hit from one report suite to another, and can modify variables conditionally.
  • VISTA rules require a paid engagement with Adobe Professional Services to create and maintain.
  • Adobe recommends VISTA only as a last resort. Use processing rules, bot rules, virtual report suites, or implementation changes first.
  • VISTA rules only affect data as it is collected. They do not change existing data.

4.3 Processing order [Verified]

Use this order to decide where a fix should go and why data looks the way it does:

  1. Dynamic variables are resolved.
  2. IP obfuscation (last octet) is applied.
  3. Lookup tables (for example, Browser) are matched.
  4. IP exclusion is applied.
  5. Bot rules are applied.
  6. Geolocation dimensions (for example, Countries) are populated.
  7. Processing rules are applied, including mapping of context data variables.
  8. VISTA rules run (usually after processing rules, but this depends on the organization).
  9. Currency conversion uses the current day’s exchange rate if the hit’s currency differs from the report suite currency.
  10. Zip code is populated based on report suite settings.
  11. Visit and visitor definition is applied. Visit number is calculated.
  12. Event deduplication checks purchase IDs and event serialization IDs.
  13. Visit-level marketing channel rules populate the marketing channel dimensions.
  14. Variable persistence (eVar expiration and allocation) is determined.
  15. Transaction ID snapshot is stored when a new transaction ID is present.
  16. IP obfuscation (remove IP) is applied after all other processing.

What this means for exam questions

  • Processing rules run after bot rules and IP exclusion, so bot traffic can be excluded before a rule changes the data.
  • Currency conversion happens after processing rules.
  • Full IP removal happens last.
  • Marketing channel rules are applied after processing rules at the visit level.

4.4 Marketing channels [Verified]

  • Marketing channel rules are evaluated at the visit level, and each hit is checked against them.
  • Changing the order of marketing channel processing rules affects new data from the time you save the change. It does not reprocess historical data.

4.5 Currency [Verified]

  • If a hit’s currency differs from the report suite’s base currency, currency variables are converted using the current day’s exchange rate.

4.6 Time zones and IP settings [General guidance, Verify]

Set the report suite time zone before back-filling data. Check bot rules and IP exclusion lists whenever you launch a new site.

5. Segments and calculated metrics [General guidance, Verify unless noted]

5.1 Segment containers

  • Hit container: matches individual hits (for example, a page view of a specific page).
  • Visit container: matches all hits within a visit. Use this for “visited X and then Y in the same visit.”
  • Visitor container: matches all hits for a visitor across visits. Use this for “visited X at any time.”
  • Choose the container that matches the business question. A hit-level segment cannot answer a visit-level question.

5.2 Sequential segments

Sequential segments require events in a specific order (for example, a search followed by a product view within the same visit). Set the container and the sequence in the segment builder.

5.3 Calculated metrics

  • A calculated metric uses a formula over standard metrics (for example, Orders divided by Visits).
  • Percentages of return visits or conversion rates are calculated metrics, usually one count divided by another.
  • Use the same segment logic on the numerator and denominator when building a percentage. Otherwise the result is not a true rate.
  • Use unique (distinct) counts for “how many different X,” not row counts.

6. Data governance and privacy [Verified where noted]

6.1 Data labels [Verified]

Adobe Analytics has three label groups for variables:

  • Identity labels (I1, I2): categorize data that can identify or contact a specific person. Use I labels on eVars that store personal identifiers.
  • Sensitive data labels (S1, S2): categorize sensitive data, such as precise geographic location (S1) or broad geographic data (S2).
  • Data governance labels: support privacy requests and contractual conditions. Some labels require an ID-PERSON label set on a variable in the same report suite. They cannot be set on events, sales eVars, or classifications.
  • Access and delete labels: indicate whether a variable’s data is returned in an access request or anonymized in a delete request.

6.2 Privacy Service [Verified]

  • Privacy Service provides an API and a user interface for access, delete, and opt-out requests.
  • Each request must include at least one unique identity value for the customer.
  • Adobe Analytics requests are processed through Privacy Service. Integrated applications respond within 30 days.
  • The Privacy Service UI supports access and delete requests. Opt-out requests must be made through the API.

6.3 Consent and opt-in [General guidance, Verify]

Block data collection until consent is given. Confirm the current consent mechanism in Adobe’s documentation for your Experience Cloud setup before implementing.

6.4 PII in URLs [General guidance, Verify]

Personal data in query strings (for example, an email address) is captured in the page URL. Overwrite or rewrite the page URL variable to remove it before the hit is sent.

6.5 Data minimization and retention [General guidance, Verify]

Collect only the variables the business requires. Set retention and deletion processes with the privacy team.

7. Data extraction, sources, and connectors

7.1 Choosing an export or ingestion tool [Verified, summary]

Need Recommended tool Notes
Hit-level data with visitor ID and hit granularity, delivered on a schedule Analytics Data Feed Most granular raw export [Verified]
Hidden variables (IP address, Experience Cloud ID, Analytics visitor ID, page URL) and denormalized table access Data Warehouse Adobe lists these as the reasons to use Data Warehouse [Verified]
Near-real-time hit-level stream (within about 30 seconds) Livestream API Partially processed hit-level data [Verified]
Summarized data for a pivot table or third-party visualization tool Report Builder or Reporting API Summarized, not hit-level [Verified for Report Builder]
Offline data permanently added to Analytics (for example, returns, call center records) Data Sources Summary or transaction ID type [Verified]
Loosely tied user or offline data (impressions, cost) Customer Attributes Adobe describes this as a less permanent option than Data Sources [Verified]
Server-side upload of event data, one event per row Bulk Data Insertion API Recommended by Adobe for server-side code [Verified]

7.2 Data Sources [Verified]

  • Data sources import online or offline data. The file is tab-delimited and uploaded to Adobe’s FTP site with a .fin file.
  • Summary data sources add data by day or by a limited set of dimensions.
  • Transaction ID data sources join offline rows to online hits that share the same transaction ID.
  • Full processing data sources are no longer offered (discontinued March 25, 2021).
  • Data sources do not support event serialization.

7.3 Transaction ID data sources [Verified]

  • An online hit must include the transactionID variable. The online data must be processed before the data source row is uploaded. If the upload arrives first, it is treated as a summary data source.
  • Transaction IDs expire after 25 months. Rows uploaded with an expired ID are treated as if they had no transaction ID.
  • If the same transaction ID appears on several online hits, only the first snapshot is used.
  • The snapshot is fixed until the ID expires.
  • If a dimension appears in both the online and offline row, the offline value is used.

7.4 Data Warehouse and Data Feeds [Verified, summary]

  • Data Warehouse exposes variables hidden in the interface, such as IP address and Experience Cloud ID.
  • Data Feeds provide raw hit-level data that you process yourself.
  • Choose based on whether you need hidden variables (Data Warehouse) or the most granular raw data (Data Feed).

7.5 Customer Attributes [Verified]

Use Customer Attributes to bring CRM profile data into Analytics. Adobe describes Customer Attributes as a way to loosely tie user inputs or offline data to Analytics data, and recommends Data Sources for a more permanent link.

8. Experience Cloud users, groups, and permissions [General guidance, Verify]

  • Product profiles define what a user can do (for example, access to processing rules, admin tools).
  • Permission groups assign report suites or virtual report suites to users.
  • Give each team access to the virtual report suite or segment that contains only its data, not the full global report suite.
  • Assign administrator roles to a small group. Review access regularly.

9. Architecture scenarios

For each scenario, the business requirement, architecture decision, recommended solution, implementation considerations, and risks are listed.

Scenario 1: Enterprise website with several brands

  • Requirement: a global view of all brands, plus brand-level access for each team.
  • Decision: one global report suite with a brand prop or eVar, and one virtual report suite per brand.
  • Solution: send all brands to the global report suite. Build a segment per brand and assign each virtual report suite to the matching permission group.
  • Considerations: virtual report suites inherit settings from the parent, so brand-specific eVar changes must be made on the parent.
  • Risks: segments on very large data sets can be slow. Test the segment performance before rollout.

Scenario 2: E-commerce measurement framework

  • Requirement: measure revenue, product views, cart additions, and purchases, and attribute cart additions to search terms.
  • Decision: product syntax for product data, a merchandising eVar for search term attribution, a purchase event, and a purchaseID.
  • Solution: set a merchandising eVar with product binding for the search term, and set purchaseID on the confirmation page.
  • Considerations: purchaseID must be alphanumeric and at most 20 bytes. Product strings must keep their delimiters.
  • Risks: a refresh on the confirmation page inflates purchases unless purchaseID is set.

Scenario 3: Single-page application

  • Requirement: count each screen view and track the search term on each route.
  • Decision: track each route change as a virtual page view with a custom event or a page view call.
  • Solution: trigger the tracking on the router’s route-change event. Set the page name and page URL for each route.
  • Considerations: the page view tag does not fire on route changes unless it is triggered.
  • Risks: duplicate page views if the route-change event fires twice. Test each route.

Scenario 4: Cross-domain tracking

  • Requirement: keep the same visitor identity when a customer moves from a booking site to a payment site.
  • Decision: share the Experience Cloud Visitor ID with Visitor.appendVisitorIDsTo.
  • Solution: append the ID to outbound links to domains you own.
  • Considerations: both domains must be owned and implemented with the ID service.
  • Risks: the ID is not shared if the browser has rejected the ECID.

Scenario 5: Privacy request and consent

  • Requirement: block collection until consent, and delete a customer’s data on request.
  • Decision: consent gating before any tag fires, identity labels on personal identifier eVars, and Privacy Service for access and delete requests.
  • Solution: label PII eVars with I labels. Submit delete requests through the Privacy Service API.
  • Considerations: labels apply only if the identifier is used in privacy requests.
  • Risks: personal data in query strings is captured in the page URL unless overwritten.

Scenario 6: Online and offline data integration

  • Requirement: combine online sales with returns and call-center records.
  • Decision: transaction ID data sources.
  • Solution: send transactionID on the online purchase hit. Upload offline rows with the matching transaction ID.
  • Considerations: the online data must process before the upload, or the row is treated as a summary row.
  • Risks: transaction IDs expire after 25 months.

Scenario 7: Near-real-time data to an internal data lake

  • Requirement: send hit-level news page view data to the company’s data lake within seconds.
  • Decision: Livestream API.
  • Solution: connect to the Livestream API and write the stream to the data lake.
  • Considerations: Livestream data is partially processed, so it does not include all fully processed features.
  • Risks: fully processed reporting (visits, segments) is not available in the stream.

Scenario 8: Troubleshooting missing data

  • Requirement: a variable is missing in reports.
  • Decision: check the stage of the processing order where the variable is changed.
  • Solution: check the request in the browser (network tab), then check processing rules, VISTA rules, and the report suite settings in that order.
  • Considerations: processing rules apply on save and not to historical data. Check whether the rule was saved and enabled, and whether the rule is in the right report suite.
  • Risks: a later rule can overwrite an earlier rule’s output.

10. Post-implementation validation [General guidance, Verify]

10.1 QA steps

  1. Development: check the data layer values in the console before the tag fires.
  2. Browser network tab: confirm the request is sent to the expected endpoint with the expected variable values.
  3. Experience Platform Debugger: confirm the tags fire on the right events.
  4. Staging: repeat the test with the staging property and report suite.
  5. Production: check a small sample of real hits after publishing. Confirm the report suite receives data.
  6. Report check: compare the expected values with the report for the test period. Allow for processing latency before judging.

10.2 Common failure causes

  • The production tag library is not published, or the environment has the wrong embed code.
  • The data layer value is an object, not a string.
  • A processing rule is saved but not enabled, or is in a different report suite.
  • A later rule or custom script overwrites the variable.
  • Purchase ID or event serialization is blocking repeat events.

12. Practice questions (original)

These questions were written for this guide. Each has one best answer unless it says “choose two.” The rationale explains why the correct answer is correct and why the others are wrong. Answers are based on the documentation in Section 13.

Q1. An online shop uses purchaseID to stop refreshes from inflating orders. A customer returns a year later and the shop sends the same purchase ID. What happens? A. The purchase is counted because the visitor is different. B. The purchase is de-duplicated, because purchase IDs apply to all visitors and last 37 months. C. The purchase is counted once per visit. D. The purchase is de-duplicated for 13 months only. Answer: B. Purchase IDs apply to all visitors and expire after 37 months [Verified]. A is wrong because purchase IDs are not visitor-specific. C is wrong because visits do not scope purchase IDs. D is wrong because the expiry is 37 months, not 13.

Q2. A developer uses a purchase ID made with a random number generator on each confirmation page load. What is the risk? A. Reports will show the purchase twice. B. Each refresh creates a new ID, so duplicates are not removed. C. The purchase ID will be truncated. D. Revenue will be converted to the wrong currency. Answer: B. Adobe warns not to generate purchase IDs with a randomization function [Verified]. A is the symptom, but B names the cause. C is wrong because truncation happens only above 20 bytes. D is unrelated.

Q3. Which statement about event serialization is correct? A. Serialization IDs must be numeric. B. event1:ABC and event2:ABC are deduplicated against each other. C. Serialization IDs expire after 13 months. D. Each event has its own table, so event1:ABC and event2:ABC are both counted. Answer: D. Each event has its own deduplication table [Verified]. A is wrong because IDs can be alphanumeric. B is wrong for the same reason as D. C is wrong because deduplication does not expire [Verified].

Q4. A visitor sends event1:ABC today and sends event1:ABC again two years later. Is the second event counted? A. Yes, because the ID expired after 13 months. B. No, because deduplication does not expire. C. Yes, because the visitor is different. D. No, because the visit timeout applies. Answer: B. Deduplication does not expire [Verified]. A describes a different expiry. C is wrong because deduplication is global across visitors. D is wrong because visit timeout does not affect deduplication.

Q5. A success event has serialization enabled, but the implementation sends no serialization ID. What happens? A. The event is never counted. B. The event is always counted. C. The event is counted once per visit. D. The event is counted once per visitor. Answer: B. Adobe documents that the event is always counted when no ID is present [Verified].

Q6. A product page needs to capture a product’s category, quantity, and price, and attribute the cart addition to the search term. Which is the best approach? A. Store the search term in a prop only. B. Use s.products with product syntax, and a merchandising eVar bound to the product. C. Use a list prop with the price. D. Use a page name for the product. Answer: B. Product strings carry the product fields, and merchandising eVars bind values to the product line item [Verified]. A cannot bind to the product. C does not capture product fields correctly. D is a page dimension, not product data.

Q7. A developer sets s.products through a processing rule. What should the architect say? A. This is supported, but only for the first product. B. This is supported when the rule is in the global report suite. C. Adobe does not support setting the products variable with processing rules. D. This works if the rule is saved and enabled. Answer: C. Adobe documents that processing rules do not support setting the products variable [Verified].

Q8. An architect creates a processing rule today. Which data does it change? A. All historical data in the report suite. B. Only data collected after the rule is saved. C. Data in every report suite in the company. D. Only data in the virtual report suites. Answer: B. Processing rules apply on save and do not apply retroactively [Verified]. A is wrong. C is wrong because a rule applies to one report suite, though it can be copied. D is wrong because virtual reports inherit rules from the parent.

Q9. A rule compares a variable to “home.” Which value matches? A. Only “home” in lowercase. B. Only “Home” in uppercase. C. Both “home” and “Home,” because string comparisons are not case-sensitive. D. Neither, unless the rule is set to case-sensitive. Answer: C. Adobe documents that string comparisons in processing rules are not case-sensitive [Verified]. D is wrong because there is no case-sensitive option for this comparison.

Q10. A report suite needs 160 processing rules. What should the architect do? A. Add all 160 rules; the limit is 500. B. Combine rules where possible, because a report suite supports up to 150 rules. C. Create a second report suite for the rules. D. Use VISTA rules for the remaining 10. Answer: B. Each report suite supports up to 150 processing rules [Verified]. D is not the best first step, because VISTA is a last resort that requires Adobe Professional Services [Verified].

Q11. Which step is the best first choice to exclude bot traffic from reports? A. A processing rule that deletes hits. B. Bot rules, which run before processing rules. C. A VISTA rule. D. A virtual report suite. Answer: B. Bot rules run in the processing order before processing rules [Verified]. Processing rules are not intended to exclude data [Verified]. VISTA is a last resort. Virtual report suites filter views and do not delete data.

Q12. A company wants to copy one hit to another report suite. Which tool supports this? A. Processing rules. B. VISTA rules. C. Classifications. D. Data Sources. Answer: B. VISTA rules can copy a hit from one report suite to another [Verified]. Processing rules operate on one report suite. Classifications do not change report suite data. Data Sources import offline data.

Q13. Currency is set to EUR, and the report suite’s base currency is INR. When does conversion happen? A. Before processing rules. B. After processing rules, using the current day’s exchange rate. C. Never; the hit is stored in EUR. D. At report time, using the exchange rate for the report date. Answer: B. Currency conversion happens after processing rules and uses the current day’s exchange rate [Verified]. D is wrong because conversion is applied at collection time, not at report time [Verified].

Q14. Which stage is the last step that changes IP data, when IP is fully obfuscated? A. Before bot rules. B. Before geolocation lookup. C. After all other processing, including visit and visitor processing. D. Before IP exclusion. Answer: C. Full IP removal is the last step of processing [Verified]. Last-octet obfuscation happens earlier, before lookups.

Q15. A site has a cart addition event and a purchase event. The architect wants to know revenue from search terms. Which is best? A. A prop with the search term. B. An eVar with the search term, allocated and expired to match the purchase. C. A list prop with the search term. D. A visitor container segment. Answer: B. An eVar persists values across hits and credits conversion events. A cannot persist. C is for multiple values per hit. D is a segment, not a variable.

Q16. A client uploads offline transaction data using the Data Sources transaction ID type. The online hit has not yet processed. What happens? A. The row is joined to the online hit when processing finishes. B. The row is rejected. C. The row is treated like a summary data source. D. The row is deleted. Answer: C. If the online data is not processed first, the upload is treated like a summary data source [Verified].

Q17. How long does a transaction ID stay valid for a data source join? A. 13 months. B. 25 months. C. 37 months. D. It does not expire. Answer: B. Transaction IDs expire after 25 months [Verified]. C is the purchase ID expiry, not the transaction ID expiry.

Q18. A data source row and the online hit both contain the dimension “region.” Which value is used? A. The online value. B. The offline value. C. Both values are shown. D. Neither; the row is dropped. Answer: B. If a dimension is present in both, the offline value is used [Verified].

Q19. A media company wants news page view data in its own data lake within seconds, at hit level. Which option fits? A. Report Builder. B. Data Warehouse. C. Livestream API. D. Customer Attributes. Answer: C. Livestream API provides hit-level partially processed data within about 30 seconds [Verified]. Report Builder is summarized and not hit-level. Data Warehouse is a scheduled export. Customer Attributes is for loosely tied user data.

Q20. An architect needs the IP address and the Experience Cloud Visitor ID, which are not visible in the reporting interface. Which tool gives access? A. Data Warehouse. B. Report Builder. C. Customer Attributes. D. Data Sources. Answer: A. Adobe lists hidden variables such as IP address and Experience Cloud ID as a reason to use Data Warehouse [Verified].

Q21. A virtual report suite is created for one brand. Which statement is correct? A. Data can be uploaded directly to the virtual report suite. B. It inherits most settings, such as processing rules and classifications, from the parent. C. It has its own separate processing rules. D. It deletes data for the brand’s customers when requested. Answer: B. Virtual report suites inherit most settings from the parent [Verified]. A is wrong because data cannot be uploaded to a virtual report suite [Verified]. C is wrong for the same reason as B. D is wrong because data deletion is handled by data governance [Verified].

Q22. A virtual report suite needs a 60-minute visit timeout while the parent uses 30 minutes. What is the best approach? A. Change the timeout on the parent, which changes the existing data. B. Change the visit timeout on the virtual report suite, which is non-destructive and applies in Workspace. C. Create a processing rule to change visits. D. Use a VISTA rule. Answer: B. The visit timeout on a virtual report suite is non-destructive and applies in Analysis Workspace [Verified].

Q23. A form collects a customer’s email address in an eVar. Which label should the architect use? A. A sensitive data label. B. An identity label (I1 or I2), if the value is used in privacy requests. C. No label, because eVars cannot be labeled. D. A governance label on the purchase event. Answer: B. Identity labels categorize data that can identify a person [Verified]. Governance labels cannot be set on events [Verified].

Q24. A customer asks for their data to be deleted. Which tool should the architect use? A. Virtual report suite. B. Privacy Service API. C. Processing rule. D. Report Builder. Answer: B. Privacy Service handles access, delete, and opt-out requests [Verified].

Q25. The Privacy Service UI does not support one request type. Which request is it? A. Access. B. Delete. C. Opt-out. D. Status lookup. Answer: C. The Privacy Service UI supports access and delete requests. Opt-out requests must go through the API [Verified].

Q26. A launch page needs the Tags embed code. Where should it go? A. At the bottom of the body only. B. In the head, as one asynchronous embed code. C. In a separate file loaded after the page. D. In every script tag on the page. Answer: B. Adobe documents one asynchronous embed code in the head. The synchronous version uses two embed codes [Verified].

Q27. A data element returns “[object Object]”. What is the likely cause? A. The tag library is not published. B. The data element is reading an object, not a string. Read a specific property instead. C. The browser blocks the request. D. The report suite is in the wrong time zone. Answer: B. The return value shows that the data element is reading an object. Reading a property returns a string [General guidance, Verify].

Q28. A visitor moves from site A to site B, and cookies are blocked for third-party domains. Which method keeps the same visitor identity? A. Rely on browser caching. B. Use Visitor.appendVisitorIDsTo on links to site B. C. Set the same page name on both sites. D. Use a campaign code only. Answer: B. appendVisitorIDsTo appends the visitor ID to the URL [Verified]. A is not a method. C and D do not carry identity.

Q29. A single-page application changes routes without reloading. What should the architect do? A. Rely on the page view tag, which fires on each route change. B. Trigger a page view or custom event on each route change, with the page name updated. C. Use the virtual report suite. D. Track only on full reloads. Answer: B. Route changes do not reload the page, so tracking must be triggered by the route change [General guidance, Verify].

Q30. A visitor views ten pages in one visit. Marketing needs the number of visits in which the visitor viewed the home page and then ran a search, in that order. Which segment is correct? A. A hit segment for the search event. B. A sequential segment with a visit container. C. A visitor container segment on the home page. D. A calculated metric with no segment. Answer: B. Sequential segments require order, and the visit container scopes the sequence to one visit [General guidance, Verify].

Q31. A percentage of return visits that searched from the home page is needed as a trended metric. Which setup is best? A. A calculated metric dividing the count with the segment by the count of home page visits, with the same segment logic on both sides. B. A standard metric with no segment. C. A count of all page views. D. A row count of search events. Answer: A. A rate needs matching logic on numerator and denominator [General guidance, Verify]. B and C are not rates. D counts rows rather than unique visits.

Q32. A team wants to count the number of different products bought by a customer, not the number of purchases. Which metric is correct? A. Row count. B. A unique (distinct) count of products. C. A sum of quantities. D. Visits. Answer: B. Distinct counts answer “how many different X” [General guidance, Verify].

Q33. Which report suite setting is needed before event serialization works? A. Classifications enabled. B. The event’s Unique Event Recording set to Use Event ID. C. Virtual report suite created. D. Data Warehouse enabled. Answer: B. Event serialization requires the event’s Unique Event Recording setting to be set to Use Event ID [Verified].

Q34. A purchase event and an event serialization ID are both set on the same purchase. Which approach is recommended? A. Use event serialization on the purchase event. B. Use purchaseID on the purchase event. C. Use neither. D. Use the page name. Answer: B. Adobe recommends purchaseID for purchase deduplication [Verified].

Q35. Which is the best way to build a month-to-date revenue view for a single brand inside a global report suite? A. Create a new report suite for the brand. B. Create a virtual report suite with a brand segment, and assign it to the brand’s permission group. C. Create a processing rule that copies revenue into a new eVar. D. Export Data Feeds and filter them. Answer: B. A virtual report suite applies a segment to the parent and can be assigned to permission groups [Verified]. A creates a separate report suite. C does not solve access. D works, but is not the architectural choice for an access and view requirement.

Q36. An architect must send a hit with a currency different from the report suite’s currency. What must the architect know about the reported revenue? A. The revenue is stored in the original currency, not converted. B. The revenue is converted to the report suite’s currency at the current day’s exchange rate. C. The revenue is converted at the report date’s rate. D. The revenue is ignored. Answer: B. Conversion uses the current day’s exchange rate [Verified].

Q37. Which tool should carry a rule that copies an eVar value into a prop at collection time? A. A processing rule, because it modifies variables as they are collected. B. A classification, because it changes the report suite data. C. A data source, because it imports data. D. A marketing channel rule, because it changes channels. Answer: A. Processing rules modify data as it is collected [Verified]. B is wrong because classifications do not change underlying report suite data [Verified]. C is wrong because data sources import data. D is wrong because marketing channel rules only classify channels.

Q38. Classification data is edited in the interface. What happens to the underlying data? A. It is changed permanently. B. It is unchanged, because classifications create dimensions based on rules or uploads. C. It is deleted. D. It is copied to a new report suite. Answer: B. Classifications do not change the underlying report suite data [Verified].

Q39. A tag property is published to production, but no data appears in the production report suite. What should the architect check first? A. The browser’s network request for the production embed code and the production environment. B. Whether virtual report suites are enabled. C. Whether the data source is set. D. Whether the marketing channels are set. Answer: A. Confirm the production embed is loaded and the request is sent [General guidance, Verify]. The other options do not directly affect whether production hits are sent.

Q40. A processing rule overwrites prop5 correctly, but a later rule overwrites it again. What is the cause? A. The processing rule is not saved. B. A later rule overwrites the earlier rule’s output, because rules run in order and every hit runs through every rule. C. Processing rules cannot modify props. D. Data Warehouse is not enabled. Answer: B. Rules run in order, and a later rule can overwrite an earlier one [Verified]. C is wrong because props can be modified [Verified].

15. Corrections to earlier notes

The earlier study guide contained the following errors. This version replaces them.

  • Processing rule string comparisons are not case-sensitive. The earlier guide said they were.
  • Question 1 (37 months for purchase ID) is correct. The earlier review flagged it wrongly.
  • VISTA is a last-resort tool that needs Adobe Professional Services. It is not simply “legacy.”
  • Full-processing data sources were discontinued. Only summary and transaction ID types are offered.
  • Transaction IDs expire after 25 months.
  • Event serialization does not expire, and deduplication is global across visitors.
  • Data Warehouse, Data Feeds, and Livestream each have different use cases. Livestream is the documented near-real-time hit-level option.
