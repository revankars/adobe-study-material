2. Discovery (18%)

2.1 Auditing a site

A site audit confirms what is already being collected before any new tracking is designed. Check:

  • Which report suites receive data, and whether they are global, individual, or virtual.
  • Which variables and events are set on each page type (home, product, cart, checkout, confirmation, search results).
  • Whether the page name, page URL, and campaign variables are populated and consistent.
  • Whether the debugger and network requests show the expected values on each page General guidance, Verify against your organization’s setup.
2.2 Business requirements to measurement
  1. Start with the business goal. Example: “Grow online revenue from returning customers.”
  2. Define KPIs. Example: revenue per visit, return visit rate, conversion rate.
  3. Map each KPI to a metric or dimension. Example: revenue per visit uses the Revenue metric divided by Visits.
  4. Map each metric to a variable or event. Example: “Return visit” needs a visitor-level definition, and “conversion” needs a success event.
  5. Document the measurement framework so the tagging engineer and the developer can implement it.
2.3 Measurement frameworks

A measurement framework links each business objective to KPIs, dimensions, metrics, variables, and the data collection method. Keep it in one table so every stakeholder can review it.

3. Solution design (54%)

3.1 Adobe Analytics architecture and report suites

Global versus individual report suites General guidance, Verify

  • A global report suite collects data from several sites or apps into one place.
  • Individual report suites keep each site separate.
  • Rollups combine several report suites for reporting without changing collection.

Virtual report suites Verified

  • A virtual report suite is a segment applied to a parent report suite.
  • It inherits most settings from the parent, including eVar settings, processing rules, and classifications. You change those settings on the parent, not on the virtual report suite.
  • It has its own name, components, and permissions, and can be assigned to permission groups.
  • You can change the visit timeout on a virtual report suite. The change is non-destructive and applies in Analysis Workspace only.
  • You cannot upload data to a virtual report suite.
  • Virtual report suites do not delete data. Deletion is handled through data governance (Section 6).

Choosing global versus virtual General guidance, Verify

Use one global report suite with virtual report suites when several teams need different slices of the same data. Use separate report suites when the sites need independent settings, such as different eVar definitions or time zones.

3.2 Variables and metrics
Variable types
Variable Scope Typical use
eVar (conversion variable) Persists across hits according to allocation and expiration Campaign, search term, logged-in status, customer segment
prop (traffic variable) Per hit, no persistence by default Page section, content type, pathing
Success event Counts occurrences Purchase, add to cart, form submission, newsletter sign-up
List prop or list eVar Several values in one hit, each reported separately Multiple newsletters, multiple categories, multiple colors
Merchandising eVar Binds to product line items (product syntax) or to the event or order (conversion syntax) Product-level attribution such as search term to cart addition
Counter Counts occurrences of a value Number of search results, number of pages viewed
eVar settings
  • Allocation: Most Recent credits the last value before the success event. Original Value credits the first value set.
  • Expiration: hit, visit, visitor, a specific event, or a time period. Choose expiration to match the business question.
  • Allocation changes affect how data is interpreted. Check Adobe’s current guidance before changing allocation on a live report suite Verify.
Success events and serialization Verified
  • Event serialization prevents duplicate events from being counted. Enable it in the report suite’s success event settings, then send an ID with the event.
  • Each event has its own table. event1:ABC and event2:ABC are both counted.
  • Deduplication is global across visitors. If visitor A sends event1:ABC and visitor B later sends the same ID, B’s event is ignored.
  • Deduplication does not expire.
  • If an event has serialization enabled but no ID, the event is always counted.
  • Serialization IDs must be alphanumeric and up to 20 bytes. Longer values are truncated to 20 bytes.
  • Data sources do not support event serialization.

For the purchase event, use the purchaseID variable instead of event serialization.

purchaseID Verified
  • Prevents hits with the same purchase from inflating reports (for example, a page refresh on the confirmation page).
  • Purchase IDs apply to all visitors and expire after 37 months.
  • When a purchase is recognized as a duplicate, conversion data (eVars and events) does not appear in reporting. In data feeds, the duplicate_purchase column is set to 1.
  • Use only alphanumeric characters. Values longer than 20 bytes are truncated, and truncated duplicates are also deduplicated.
  • Do not generate purchase IDs with a random function.
Campaign tracking General guidance, Verify
  • s.campaign stores the tracking code. Use s.Util.getQueryParam() or the getQueryParam plug-in to read it from the URL.
  • Campaign persistence (once per visit or once per visitor) controls instance counts. Confirm the persistence setting in your report suite before answering questions about counts.
3.3 Product strings (s.products)

Structure: category;product;quantity;price;events;merchandising eVars, with a comma between products.

  • Each field is separated by a semicolon. Keep the delimiter even when a field is empty.
  • Multiple products are separated by a comma.
  • Merchandising eVars use product or conversion syntax. Product syntax binds to the product line item. Conversion syntax binds to the order or event.
  • Adobe does not support setting the products variable with processing rules Verified.

Example (illustrative)

s.products = ";Running Shoes;1;120.00,;Socks;2;15.00";

Use the documented structure for your implementation. Confirm exact syntax for merchandising eVars and events against the Implementation Guide Verify.

3.4 Data collection methods
Adobe Experience Platform Tags (formerly Adobe Launch)
  • Place one single asynchronous embed code in the <head> of each page that loads the property Verified.
  • The asynchronous embed is the default. The synchronous version uses two embed codes (one in the head and one before </body>) Verified.
  • Data elements are referenced with %name% syntax General guidance, Verify.
  • _satellite.track() sends a custom event from code General guidance, Verify.
  • If a data element returns [object Object], the data element is reading an object. Read a specific property instead of the whole object General guidance, Verify.

AppMeasurement Adobe Experience Platform Web SDK

Adobe describes both as client-side collection methods that feed the processing pipeline. The processing order described in Section 5 applies to both.

Cross-domain tracking Verified
  • When browsers block third-party cookies, the ID service cannot recognize a visitor who moves to a different domain.
  • Visitor.appendVisitorIDsTo(url) appends the Experience Cloud Visitor ID (MID) to a link, so the destination domain can recognize the visitor.
  • You must own both the source and destination domains and have implemented the ID service.
  • Cross-domain tracking does not work if the ECID was rejected earlier.
Asynchronous content General guidance, Verify

Content that loads after the page load should be tracked by listening for a specific JavaScript event (for example, a custom event raised when the content is inserted). Do not rely on a single page-load call at the bottom of the page.

Single-page applications (SPA) General guidance, Verify

Route changes do not reload the page, so the page view tag does not fire. Track each virtual page view with a custom event or a page view call triggered by the route change. Set the page name and page URL for each route.

Mobile apps General guidance, Verify

Mobile apps use the Adobe Mobile SDK. Visit definition settings (background hits, start a new visit on app launch) control how sessions are counted.

3.5 Technical specifications

A technical specification gives the tagging engineer and the developer what they need to implement and test the tracking. Each specification should include:

  1. Business requirement: what the business needs to measure and why.
  2. Tracking requirement: the metric, dimension, or event to capture.
  3. Data layer definition: the field names, data types, and where the value comes from.
  4. Variable mapping: which Analytics variable receives each data layer field, and the variable type and allocation.
  5. Trigger condition: the page load, link click, or event that fires the tracking.
  6. Expected values: sample values for each variable.
  7. Implementation instructions: where in the tag property or code the change goes.
  8. Acceptance criteria: what must be true for the implementation to be accepted.
  9. QA steps: how to test in development, staging, and production.

4. Report suite administration Verified where noted

4.1 Processing rules Verified
  • Processing rules modify data as it is collected, before it is written to the report suite.
  • They run in order, from rule 1. Every hit runs through every rule. There are no early exits, so the conditions must cover every hit.
  • A report suite can contain up to 150 rules. Each rule can contain up to 30 conditions.
  • Rules apply on save. They do not apply retroactively to data already collected.
  • Rules apply to one report suite. You can copy them to other report suites after they are created.
  • String comparisons are not case-sensitive.
  • A later rule can overwrite the result of an earlier rule. A value overwritten in rule 1 is not available to later rules.
  • Excluding data is not an intended feature of processing rules. Use bot rules, IP exclusion, or VISTA rules instead Verified.
  • Context data variables that are not mapped to another variable are permanently lost.
  • Test in a development report suite before enabling rules in production.
4.2 VISTA rules Verified
  • VISTA rules are a form of custom data modification that runs between data collection and processing.
  • VISTA rules can copy a hit from one report suite to another, and can modify variables conditionally.
  • VISTA rules require a paid engagement with Adobe Professional Services to create and maintain.
  • Adobe recommends VISTA only as a last resort. Use processing rules, bot rules, virtual report suites, or implementation changes first.
  • VISTA rules only affect data as it is collected. They do not change existing data.
4.3 Processing order Verified

Use this order to decide where a fix should go and why data looks the way it does:

  1. Dynamic variables are resolved.
  2. IP obfuscation (last octet) is applied.
  3. Lookup tables (for example, Browser) are matched.
  4. IP exclusion is applied.
  5. Bot rules are applied.
  6. Geolocation dimensions (for example, Countries) are populated.
  7. Processing rules are applied, including mapping of context data variables.
  8. VISTA rules run (usually after processing rules, but this depends on the organization).
  9. Currency conversion uses the current day’s exchange rate if the hit’s currency differs from the report suite currency.
  10. Zip code is populated based on report suite settings.
  11. Visit and visitor definition is applied. Visit number is calculated.
  12. Event deduplication checks purchase IDs and event serialization IDs.
  13. Visit-level marketing channel rules populate the marketing channel dimensions.
  14. Variable persistence (eVar expiration and allocation) is determined.
  15. Transaction ID snapshot is stored when a new transaction ID is present.
  16. IP obfuscation (remove IP) is applied after all other processing.

What this means for exam questions

  • Processing rules run after bot rules and IP exclusion, so bot traffic can be excluded before a rule changes the data.
  • Currency conversion happens after processing rules.
  • Full IP removal happens last.
  • Marketing channel rules are applied after processing rules at the visit level.
4.4 Marketing channels Verified
  • Marketing channel rules are evaluated at the visit level, and each hit is checked against them.
  • Changing the order of marketing channel processing rules affects new data from the time you save the change. It does not reprocess historical data.
4.5 Currency Verified
  • If a hit’s currency differs from the report suite’s base currency, currency variables are converted using the current day’s exchange rate.
4.6 Time zones and IP settings General guidance, Verify

Set the report suite time zone before back-filling data. Check bot rules and IP exclusion lists whenever you launch a new site.

5. Segments and calculated metrics General guidance, Verify unless noted

5.1 Segment containers
  • Hit container: matches individual hits (for example, a page view of a specific page).
  • Visit container: matches all hits within a visit. Use this for “visited X and then Y in the same visit.”
  • Visitor container: matches all hits for a visitor across visits. Use this for “visited X at any time.”
  • Choose the container that matches the business question. A hit-level segment cannot answer a visit-level question.
5.2 Sequential segments

Sequential segments require events in a specific order (for example, a search followed by a product view within the same visit). Set the container and the sequence in the segment builder.

5.3 Calculated metrics
  • A calculated metric uses a formula over standard metrics (for example, Orders divided by Visits).
  • Percentages of return visits or conversion rates are calculated metrics, usually one count divided by another.
  • Use the same segment logic on the numerator and denominator when building a percentage. Otherwise the result is not a true rate.
  • Use unique (distinct) counts for “how many different X,” not row counts.

6. Data governance and privacy Verified where noted

6.1 Data labels Verified

Adobe Analytics has three label groups for variables:

  • Identity labels (I1, I2): categorize data that can identify or contact a specific person. Use I labels on eVars that store personal identifiers.
  • Sensitive data labels (S1, S2): categorize sensitive data, such as precise geographic location (S1) or broad geographic data (S2).
  • Data governance labels: support privacy requests and contractual conditions. Some labels require an ID-PERSON label set on a variable in the same report suite. They cannot be set on events, sales eVars, or classifications.
  • Access and delete labels: indicate whether a variable’s data is returned in an access request or anonymized in a delete request.
6.2 Privacy Service Verified
  • Privacy Service provides an API and a user interface for access, delete, and opt-out requests.
  • Each request must include at least one unique identity value for the customer.
  • Adobe Analytics requests are processed through Privacy Service. Integrated applications respond within 30 days.
  • The Privacy Service UI supports access and delete requests. Opt-out requests must be made through the API.
6.3 Consent and opt-in General guidance, Verify

Block data collection until consent is given. Confirm the current consent mechanism in Adobe’s documentation for your Experience Cloud setup before implementing.

6.4 PII in URLs General guidance, Verify

Personal data in query strings (for example, an email address) is captured in the page URL. Overwrite or rewrite the page URL variable to remove it before the hit is sent.

6.5 Data minimization and retention General guidance, Verify

Collect only the variables the business requires. Set retention and deletion processes with the privacy team.

9. Architecture scenarios

For each scenario, the business requirement, architecture decision, recommended solution, implementation considerations, and risks are listed.

Scenario 1: Enterprise website with several brands
  • Requirement: a global view of all brands, plus brand-level access for each team.
  • Decision: one global report suite with a brand prop or eVar, and one virtual report suite per brand.
  • Solution: send all brands to the global report suite. Build a segment per brand and assign each virtual report suite to the matching permission group.
  • Considerations: virtual report suites inherit settings from the parent, so brand-specific eVar changes must be made on the parent.

Scenario 2: E-commerce measurement framework
  • Requirement: measure revenue, product views, cart additions, and purchases, and attribute cart additions to search terms.

Scenario 6: Online and offline data integration

Scenario 7: Near-real-time data to an internal data lake

2. Data collection: Data Feed vs. Data Warehouse

Both Data Feeds and Data Warehouse extract Adobe Analytics data, but they serve different purposes.

2.1 Data Feed

Data Feed is the most granular way to extract Adobe Analytics data. It provides raw, hit-level data, generally in a columnar format, which you export to external storage and process with your own infrastructure.

Typical use cases
  • Building a custom data warehouse.
  • Performing hit-level analysis.
  • Integrating Analytics data with Snowflake, Databricks, or other platforms.
  • Building custom attribution models.
  • Analyzing individual visitor interactions.
  • Creating custom reporting outside Adobe Analytics.

5. Metrics, metric types, and attribution

This section is about the difference between participation and allocation.

5.1 Participation vs. linear allocation

Participation gives credit to every eligible dimension item that participated in the conversion journey. If a visitor reads Blog A, Blog B, and Blog C before purchasing, all three can receive credit for the purchase. This is useful for understanding all content that contributed to a conversion.

Linear allocation distributes conversion credit equally across eligible items in the attribution window, so each blog receives 33.33% and the total is 100%.

7. Duplicate AppMeasurement.js tags

If the same tracking implementation executes twice, you may see duplicate page-view calls, duplicate custom events, inflated page views and visit-related activity, duplicate interaction tracking, inconsistent visitor or session behavior if the implementations differ, and increased network traffic.

A common cause is a page that loads AppMeasurement directly while the tag manager also loads another implementation. If both execute the same call, Adobe may receive two page-view hits.

How to troubleshoot
  1. Open Chrome Developer Tools and go to the Network tab.
  2. Filter for Adobe Analytics collection requests and reload the page.
  3. Identify duplicate requests and compare their payloads and timestamps.
  4. Inspect both the tag manager and the direct page implementation.
Correct principleEnsure that only the intended tracking implementation executes each measurement call.

8. Alerts in Adobe Analytics

You mentioned an alert that sends an SMS when visits increase or decrease by more than 25%.

8.1 Creating an alert
  1. Open Adobe Analytics and the relevant Workspace project, or create a new one.
  2. Select the Visits metric and apply any segment or reporting scope required.
  3. Open the Alerts interface from the component or project workflow and create a new alert.
  4. Select Visits as the metric and configure the threshold condition.
  5. Set the frequency and evaluation period.
  6. Configure the recipients and available notification channels, then save.
8.2 Configuring a 25% threshold

A percentage threshold needs a comparison baseline. Distinguish between an absolute threshold (Visits exceed 10,000) and a percentage threshold (Visits increase by 25% compared with the selected baseline). The baseline, comparison period, and frequency must be selected in the alert configuration.

Worked example: Yesterday's Visits = 10,000 and today's = 13,000. (13,000 − 10,000) ÷ 10,000 × 100 = +30%, so the condition is met. If today's Visits are 7,000, the change is −30%, which also meets the condition.
TrapAn alert for Visits greater than 25 is not the same as an alert for Visits changing by more than 25%.
8.3 SMS notifications

SMS availability depends on the applicable alert interface, account configuration, and supported notification options. Do not assume that entering a phone number automatically enables SMS. For exam questions, distinguish the alert condition from the delivery mechanism.

8.4 Anomaly Detection

Anomaly Detection identifies statistically unusual changes in metrics, such as unexpected purchase increases or decreases. It does not independently diagnose duplicate tracking or incorrect implementation.

11. The s.products variable

The s.products variable captures product-related information for product-level reporting and commerce tracking, including category, product, quantity, price, merchandising eVars, and product-related events.

// Product view
s.products = ";Product A";
s.events = "prodView";
s.t();

// Purchase of two units at a total line-item price of 100.00
s.events = "purchase";
s.products = ";Product A;2;100.00";

General syntax: category;product;quantity;price;events;eVars

Multiple products are separated by commas:

s.products = ";Product A;2;100.00,;Product B;1;50.00";

Keep product names consistent, make quantity and price reflect the intended transaction, confirm the purchase event is implemented correctly, and follow the delimiter structure exactly.

Inspect purchase calls in the Network tab and check for duplicate firing. Validate order IDs and transaction identifiers, then review the purchase implementation and the s.products variable. Check processing rules, VISTA rules, and report suite configuration. Compare metrics in Workspace using the same date range, segment, and attribution settings, and investigate duplicate tracking from multiple tags.
Q2: What is the best way to troubleshoot an error?
Start with the browser's Developer Tools and Network tab. Inspect the tracking request, parameters, events, report suite ID, response, and any duplicate requests. Then validate processing and reporting.
Q3: How do you limit the size of a beacon request while keeping the data?
Remove redundant variables, avoid sending duplicate values, use concise identifiers, reduce unnecessary custom dimensions, avoid repeatedly transmitting large objects, and send only the values relevant to each interaction. List variables can consolidate values but do not automatically reduce total bytes in every implementation.
Q4: Which variables capture campaign name, campaign type, and visitor data for five homepage campaigns?
Campaign name in eVar1, campaign type in eVar2, and Unique Visitors as the standard metric. You do not need a separate visitor variable. Use the same eVars with different values for all five campaigns rather than creating five eVars. Example: s.eVar1 = "Summer_Sale"; s.eVar2 = "Homepage_Banner"; s.events = "event1"; s.t();

15. Data layer implementation: shopping cart with cart ID

The cart identifier should be available in a structured data layer and mapped to the appropriate Analytics variable. A data layer is a structured JavaScript object that exposes business information to your tag management system.

window.digitalData = {
  page: { pageName: "Product Details", pageType: "Product" },
  cart: {
    cartID: "CART-123456",
    cartTotal: 150.00,
    currency: "USD",
    products: [
      { productID: "PROD-1001", productName: "Running Shoes", quantity: 1, price: 150.00 }
    ]
  },
  event: { eventName: "cartAdd" }
};

Design principles

Use consistent naming, expose business identifiers, support multiple products, include quantity, price, and currency, separate page information from commerce information, and support cart add, checkout, and purchase events. Keep the data layer independent of the tag management system, which can be Adobe Tags, Tealium iQ, or another platform.

Q1. An online shop uses purchaseID to stop refreshes from inflating orders. A customer returns a year later and the shop sends the same purchase ID. What happens? A. The purchase is counted because the visitor is different. B. The purchase is de-duplicated, because purchase IDs apply to all visitors and last 37 months. C. The purchase is counted once per visit. D. The purchase is de-duplicated for 13 months only. Answer: B. Purchase IDs apply to all visitors and expire after 37 months Verified. A is wrong because purchase IDs are not visitor-specific. C is wrong because visits do not scope purchase IDs. D is wrong because the expiry is 37 months, not 13.

Q2. A developer uses a purchase ID made with a random number generator on each confirmation page load. What is the risk? A. Reports will show the purchase twice. B. Each refresh creates a new ID, so duplicates are not removed. C. The purchase ID will be truncated. D. Revenue will be converted to the wrong currency. Answer: B. Adobe warns not to generate purchase IDs with a randomization function Verified. A is the symptom, but B names the cause. C is wrong because truncation happens only above 20 bytes. D is unrelated.

Q3. Which statement about event serialization is correct? A. Serialization IDs must be numeric. B. event1:ABC and event2:ABC are deduplicated against each other. C. Serialization IDs expire after 13 months. D. Each event has its own table, so event1:ABC and event2:ABC are both counted. Answer: D. Each event has its own deduplication table Verified. A is wrong because IDs can be alphanumeric. B is wrong for the same reason as D. C is wrong because deduplication does not expire Verified.

Q4. A visitor sends event1:ABC today and sends event1:ABC again two years later. Is the second event counted? A. Yes, because the ID expired after 13 months. B. No, because deduplication does not expire. C. Yes, because the visitor is different. D. No, because the visit timeout applies. Answer: B. Deduplication does not expire Verified. A describes a different expiry. C is wrong because deduplication is global across visitors. D is wrong because visit timeout does not affect deduplication.

Q5. A success event has serialization enabled, but the implementation sends no serialization ID. What happens? A. The event is never counted. B. The event is always counted. C. The event is counted once per visit. D. The event is counted once per visitor. Answer: B. Adobe documents that the event is always counted when no ID is present Verified.

Q6. A product page needs to capture a product’s category, quantity, and price, and attribute the cart addition to the search term. Which is the best approach? A. Store the search term in a prop only. B. Use s.products with product syntax, and a merchandising eVar bound to the product. C. Use a list prop with the price. D. Use a page name for the product. Answer: B. Product strings carry the product fields, and merchandising eVars bind values to the product line item Verified. A cannot bind to the product. C does not capture product fields correctly. D is a page dimension, not product data.

Q7. A developer sets s.products through a processing rule. What should the architect say? A. This is supported, but only for the first product. B. This is supported when the rule is in the global report suite. C. Adobe does not support setting the products variable with processing rules. D. This works if the rule is saved and enabled. Answer: C. Adobe documents that processing rules do not support setting the products variable Verified.

Q8. An architect creates a processing rule today. Which data does it change? A. All historical data in the report suite. B. Only data collected after the rule is saved. C. Data in every report suite in the company. D. Only data in the virtual report suites. Answer: B. Processing rules apply on save and do not apply retroactively Verified. A is wrong. C is wrong because a rule applies to one report suite, though it can be copied. D is wrong because virtual reports inherit rules from the parent.

Q9. A rule compares a variable to “home.” Which value matches? A. Only “home” in lowercase. B. Only “Home” in uppercase. C. Both “home” and “Home,” because string comparisons are not case-sensitive. D. Neither, unless the rule is set to case-sensitive. Answer: C. Adobe documents that string comparisons in processing rules are not case-sensitive Verified. D is wrong because there is no case-sensitive option for this comparison.

Q10. A report suite needs 160 processing rules. What should the architect do? A. Add all 160 rules; the limit is 500. B. Combine rules where possible, because a report suite supports up to 150 rules. C. Create a second report suite for the rules. D. Use VISTA rules for the remaining 10. Answer: B. Each report suite supports up to 150 processing rules Verified. Q11. Which step is the best first choice to exclude bot traffic from reports? A. A processing rule that deletes hits. B. Bot rules, which run before processing rules. C. A VISTA rule. D. A virtual report suite. Answer: B. Bot rules run in the processing order before processing rules Verified. Processing rules are not intended to exclude data Verified. VISTA is a last resort. VISTA rules can copy a hit from one report suite to another Verified. Processing rules operate on one report suite. Classifications do not change report suite data. Data Sources import offline data.

2. Core concepts and page-load order

at.js is the client library that runs Target requests and applies experiences. It must load early in <HEAD>, after the data layer and VisitorAPI.js.

  1. Data layer in <HEAD> before at.js (Q2).

  2. VisitorAPI.js loads first, creating the Experience Cloud ID (Q11).

  3. Pre-hiding snippet and at.js in <HEAD> so the page is hidden until Target responds (Q49).

  4. The global mbox fires on page load and triggers the execution order below.

Execution order when a Target request (mbox) arrives (documented in How at.js works):

  1. Profile scripts run on Target's server, per request, before audience decisions (Q4).

  2. Profile Store builds the profile from request parameters and script output.

  3. Audiences are qualified from the Audience Library (Target, Analytics, AAM, Experience Cloud).

  4. The highest-priority qualifying activity is selected.

  5. The winning offer is applied. Inline scripts run, then remote scripts load asynchronously.

  6. The pre-hiding snippet is removed and the page is revealed.

Remember: scripts, then audiences, then priority, then offer applied, then page revealed.

at.js functions

  • targetPageParams() supplies page-level parameters to the global mbox before the request is sent.

  • getOffer requests one mbox and returns the offer to your code. It does not display it.

  • getOffers requests several mboxes in one call (the batch version).

  • applyOffer displays an offer you received. Remember: getOffer gets it, applyOffer shows it.

Data collection commands send events and data from code. Single-page apps must fire a new request when the view changes, because no page load happens.

4. Target request (mbox) parameters and multi-tenant at_property

Parameter Purpose
at_property Property token that ties the request to one property (Q17, Q48)
entity.id, entity.categoryId, entity.inventory Product or category data for Recommendations

user.* Attributes set by profile scripts
mbox3rdPartyId Your own customer ID for cross-device matching (Q32)

Multi-tenant

One Target installation can serve several business units. Each business unit has a Workspace, and each Workspace holds properties (sites or apps). Business units never share activities, audiences, or reports.

at_property

at_property holds the property token, a unique ID string for one property. At page level, every page sends the token of the property it belongs to. Target then applies only that property's activities. If the token is missing or wrong, no activities apply (Q17, Q48).

Parameter rules that affect answers

  • Product page entity.categoryId takes a comma-separated list: one product, several categories. Category page recommendation mboxes take one value that must match exactly (Q27).

  • Most predefined entity attributes (for example entity.brand, entity.pageUrl) are single-value only.

  • Use targetPageParams() for page-level data known at load time (Q30).

5. Profile scripts, profile attributes, audiences and debugging

Profile scripts are JavaScript snippets defined in Target. They run on Target's server for every mbox call, before audience evaluation. Their output becomes user.* attributes. Scripts cannot rely on each other, because their execution order is not guaranteed (Q1, Q4).

Profile parameters are values the page sends with the request. They are stored in the profile and need no server-side script.

Splitting audiences so two activities don't overlap: use a profile script to set an attribute that each audience checks (Q5). Traffic Allocation only splits visitors within one activity.

Profile expiration: monthly visitors look new if the profile expires first. Increase the profile expiration above the default 14 days (Q7).

Audience sources

Source What it is
Target audiences Built from mbox parameters and profile attributes (Q16)
Analytics audiences Segments from Adobe Analytics
AAM audiences Segments from Audience Manager, for third-party or anonymous data (Q14)
Experience Cloud audiences Built in the Audience Library (People Core Service) (Q6, Q47)

Debugging: use mboxTrace to compare profile values before and after a profile script runs (Q45, Q46). Running scripts in the browser console before saving is not marked correct in the practice key for Q46, so treat it as Verify.

6. Activities, delivery by URL, AdBox and redirector

Activity types

  • Experience Targeting: one winning experience per visitor, chosen by audience.

  • A/B Test: one variation compared with the control, traffic split evenly.

  • Multivariate test (MVT): tests combinations of several elements at once. Needs more traffic than an A/B test.

  • Automated Personalization: machine learning picks the best offer per visitor.

  • Recommendations: product suggestions from a catalog and criteria.

Delivery by URL sets which pages an activity runs on: URL is (exact match), URL contains, URL starts with, and regex. A rule that is too strict hides the activity in QA (Q41).

AdBox is the no-JavaScript method for ads and offsite content. It returns a different image while the link stays fixed. The Target URL uses the ubox/image path. It has no client-side timeout, so if Target is down, visitors see no content. It cannot show dynamic creative such as an abandoned-cart product (Q3).

Redirector changes the landing page of an ad. Its path is ubox/page. Use it when the destination changes, not the image. Redirectors need allowlisted hosts to avoid open redirect risk.

AdBox Redirector
Changes Image in the ad Landing page
Path ubox/image ubox/page

7. Offers, experiences and VEC

Experience: what the visitor sees, built in the Visual Experience Composer (VEC).

  • HTML offers for web pages, built in VEC.

  • JSON offers for apps or custom rendering. Built in Target, styled by app developers (Q20).

  • Image offers and Experience Fragments from AEM (Q12).

Reading a JSON offer: filter the actions array from adobe.target.getOffer() for actions with setJson set to true, then read the JSON from the content property of that action (Q40). setContent is for HTML offers.

Image swapping in VEC: upload image files to Adobe Experience Cloud Assets Core Service and contact Customer Care for the Scene7 account configuration (Q8).

AEM Experience Fragments to Target needs the Cloud Services for Target configuration in AEM and the AEM Link Externalizer (Q13).

VEC selectors are the CSS selectors that locate page elements. A changed page structure can break them.

Implementation types

  • Client-side (at.js): the browser library. Load early in <HEAD>.

  • SPA: single-page apps must fire a new Target request on each view change.

  • Mobile: VEC in the mobile app supports Experience Targeting and A/B tests (Q28).

8. Recommendations and entity attributes

Recommendations uses a catalog built from feeds, collections, or Analytics classifications. Criteria decide which products are shown. Results are cached at Edge servers, so a no_content response can mean results are not yet cached at the nearest Edge server (Q38).

Where product data comes from

  • Product feeds (Google Product Feeds): reuse organic search product data and automate inclusion (Q26).

  • Feeds entity: product attributes such as profit margin (Q24).

  • Entity inventory: send live inventory with the request, entity.inventory from the data layer, instead of relying on a nightly CSV (Q23).

Category recommendations

  • Product page: entity.categoryId takes a comma-separated list. Commas separate categories, colons separate subcategory levels.

  • Category page: one categoryId only, matching the product page value exactly (Q27).

Catalog link: a fully qualified domain name, including the subdomain, links a request to one product catalog (Q25).

Templates: entity references in Recommendations design templates need a $ in front (Q39).

9. Analytics, reporting and access

  • A4T (Analytics for Target) sends Target results into Analytics. Target conversions appear under the Activity Conversions metric (Q9, Q15). A4T needs at.js and VisitorAPI.js, with at.js loaded after VisitorAPI.js (Q11).

  • Reporting source: choosing Analytics as the source requires membership in the Web Services Access Group in Adobe Analytics. Enterprise permissions alone are not enough (Q37).

  • Hosts separate production traffic from dev and staging in reports (Q19).

  • Bot traffic: Target does not create or retrieve a profile for known bots, and it does not log an activity visit for reporting (Q18).

  • Experience Cloud audience status: check the Audience Library in People Core Service (Q47).

  • Customer identity: AAM segments without slowing the page use Experience Cloud ID Service (Q10).

  • Combining A/B results with Analytics data: implement A4T (Q15).

  • Credit card platinum and anonymous third-party data: Audience Manager (Q14).

10. Mobile, server-side, and the Q1 to Q49 answer key

Mobile and server-side

  • iOS targeted locations: the two primary methods are targetLoadRequest and targetCreateRequestWithName (Q29).

  • Android with AEP Mobile SDK: retrieve a custom visitor ID passed from a CRM with getThirdPartyId() (Q31). getTntId() returns Target's own ID, and Visitor.getInstance(...).getMarketingCloudVisitorID() returns the Experience Cloud ID.

  • Same experience across devices for logged-in users: populate the mbox3rdPartyId parameter with the user's ID, and call the Visitor API setCustomerIDs with the user's ID and authenticated state (Q32).

  • Server-side: if no ID is specified, Target generates a tntId (Q21). aamUUID is an Audience Manager identifier.

Chapter 1: Adobe Target Fundamentals (13%)

1.1 Overview

Adobe Target is Adobe’s personalization and experimentation platform. It delivers content variations (offers) to visitors and measures their effect on business metrics. It sits in the Adobe Experience Cloud alongside Adobe Analytics, Adobe Experience Manager (AEM), and Adobe Experience Platform (AEP).

1.2 Core concepts
Term Meaning
Property / Client code Identifies your Target account and the delivery endpoint (for example, {clientCode}.tt.omtrdc.net).
Workspace A Target area containing activities, audiences, and settings.
Mbox A named container on a page or in an app where Target can deliver content. Mboxes are the main delivery unit in the legacy at.js model.
Offer The content or experience returned for an mbox.
Activity An experiment or personalization definition: its audience, traffic, experiences, and goals.
Experience One variation within an activity, such as control or variant B. Each experience contains one or more offers.
Audience Rules or segments that decide who sees an activity.
Goal / Metric The success measure, such as conversion, revenue, or clicks.
Traffic allocation The share of eligible visitors who enter an activity and the share each experience receives.
Global mbox A default mbox, target-global-mbox, that runs on every page where at.js is loaded. The PDF practice file calls it the auto-created global Target request (mbox).
Order Confirmation mbox A reserved mbox that Target uses on order confirmation pages to send order data for revenue and conversion measurement. Verify the exact name and setup in current docs.
1.3 Activity types
Type Purpose Key point
A/B test Compare discrete experiences Fixed traffic split; reports a winner by statistics
Multivariate (MVT) Test combinations of element changes Needs more traffic than A/B
Experience Targeting (XT) Show different experiences to audience segments No statistical comparison; targets rather than tests
Auto-Target Machine learning picks the best experience per visitor from a set of options Requires enough historical data
Automated Personalization (AP) Machine learning selects the best offer for each visitor from a set of offers Often compared with Auto-Target; verify current behavior
Auto-Allocate Gradually shifts traffic toward the better-performing experience Lets the test optimize itself while it runs

Form-based / Hybrid / Mobile / Email Covered in Chapter 4 Depend on the touchpoint
1.4 Key principles
  • Statistical significance tells you whether a difference is likely real. It doesn’t tell you whether the difference matters. Business significance is a separate decision.
  • Sample ratio mismatch (SRM) happens when the observed traffic split differs from the configured split. SRM usually points to an implementation or delivery problem. Investigate before trusting results.
  • Flicker (flash of original content) happens when the default content renders before Target applies the offer. Mitigate it with the at.js timeout, the body-hiding snippet, or server-side delivery.
1.5 Important exam points
  • Know the difference between a test (A/B, MVT) and targeting (XT).
  • Know which activities need historical data or machine learning.
  • Know that the Global mbox runs without a specific mbox call. Don’t assume it handles conversion data on its own.
1.6 Common mistakes
  • Confusing an mbox (delivery container) with an activity (the experiment definition). One activity can use several mboxes.
  • Assuming traffic allocation equals audience size. Allocation applies to visitors who qualify for the audience.
  • Expecting significance on a low-traffic test within a short window.

Chapter 2: Integrating with Adobe Target (18%)

2.1 Adobe Analytics integration (A4T)

Analytics for Target (A4T) sends Target activity and experience data into Adobe Analytics. Analysts can then report on Target experiences alongside all other dimensions and metrics.

  • Target writes activity and experience values into Analytics variables. The variables are configured in the report suite(s). Verify the mapping in current docs.
  • A4T lets you use Analytics segments and metrics as Target audiences and goals, and Analytics reports show Target outcomes.
  • Conversion counted in Target and in Analytics can differ because of attribution windows, deduplication, and visitor identity. Document which system is the source of truth for each KPI.

Common mistakes: assuming A4T replaces Target’s own reporting; ignoring report suite configuration, since A4T only works for report suites set up for it.

2.2 Adobe Experience Manager (AEM) integration
  • AEM Sites uses Target through the Target integration configured in AEM Cloud Services. Verify current setup steps.
  • AEM can render Target offers as Experience Fragments or as offers mapped to components, so content authors can manage variations inside AEM.
  • The Core Components library includes Target-aware components. Check the current version and whether it’s client-side or server-side rendered.
  • Typical design: AEM renders the default content and Target supplies offers for each mbox. Authors own variations and Target owns decisions.
  • Where rendering happens (server-side in AEM versus client-side in the browser) determines flicker, caching, and how offers are passed in.
  • Caching: if the CDN caches pages, personalized content must bypass the cache or be delivered through a personalization layer.
2.3 Adobe Experience Platform (AEP) and Edge integration
  • Web SDK (Alloy) on the Adobe Experience Platform Edge Network can deliver Target decisions. Edge-based delivery returns personalization decisions (propositions) in the Web SDK response, which then render on the page. Verify field names and the current Edge flow.
  • Data Collection (Tags, formerly Launch) hosts the Target extension. Use it to deploy Target through the tag manager, with environments (development, staging, production).
  • Audiences: AEP audiences (segments from Real-Time CDP) can be used in Target. Activation requires the right permissions and an active connection. Verify the current supported audience sources.
  • Identity: use the same identity (ECID, customer ID) across Edge, Target, and Analytics for consistent visitor identity.
2.4 Other Experience Cloud integrations
  • Adobe Audience Manager (AAM) and Adobe Advertising audiences can be used in Target where supported. Verify availability.
  • Adobe Journey Optimizer and other products can use Target as a decisioning service. Check the current integration path.
  • Customer data: use Target data-sharing rules to define what leaves the browser and what must stay out of it. Privacy settings affect integrations.
2.5 Important exam points
  • A4T reports Target outcomes in Analytics. It doesn’t create Target audiences by itself.
  • AEM integration controls where rendering happens. Know the trade-offs between client-side and server-side rendering.
  • Edge/Web SDK changes how decisions are returned. Know that Edge is the path Adobe is steering toward for new implementations. Verify the current recommendation.
2.6 Common mistakes
  • Confusing audiences (who qualifies) with segments (Analytics filters).
  • Forgetting that identity differences between Analytics and Target lead to mismatched numbers.
  • Assuming an AEM component automatically personalizes. The component must be wired to Target through the configured offers.

Chapter 3: Administration and Governance (6%)

3.1 Roles and access
  • Access is managed through Adobe Admin Console product profiles and Target permissions. Verify the current role model in your organization.
  • Typical roles: administrator (full control), developer (implementation), analyst (reporting), approver (sign-off), and viewer (read-only).
  • Apply least privilege. Separate the people who build activities from the people who approve them and push them live.
3.2 Environments and change control
  • Keep separate development, staging, and production properties, workspaces, or tag environments.
  • Test activities in staging before promoting them. Confirm that the same code and mboxes exist in production.
  • Use approval workflows where available for high-risk changes. Verify current approval features.
3.3 Naming conventions and documentation
  • Use consistent names for mboxes, activities, audiences, and goals. Example: pdp_hero_v2_2026Q4.
  • Record the hypothesis, primary metric, guardrail metrics, dates, owners, and the results decision for each activity.
  • Keep an activity inventory. Retire finished tests so they don’t continue to run and consume traffic.
3.4 Governance concerns
  • Concurrent tests: multiple activities on the same page or audience can interact. Use exclusion groups or mutually exclusive audiences.
  • Traffic budget: limit the share of traffic in experiments to protect the core experience.
  • Privacy and consent: honor consent settings in the tag manager and Target data-sharing configuration. Personal data should not leak into mbox parameters.
  • Data retention and deletion: follow organizational and regulatory rules for visitor data.
3.5 Common mistakes
  • Letting a test run past its decision date.
  • Editing live activities without a test or rollback plan.

Chapter 4: Supported Touchpoints (6%)

4.1 Client-side (web) delivery
  • at.js is the legacy client library. Adobe has moved toward the Web SDK. Verify current library recommendations and version support.
  • The page loads the library, which calls the delivery service for each mbox. Target then applies offers in the browser.
  • Advantages: quick setup, works with most sites. Drawbacks: flicker risk, dependence on browser scripts, and limited visibility into the page.
4.2 Server-side delivery
  • Uses the Delivery API (JSON REST) or Adobe SDKs (Java, Node.js, .NET, and others). Verify the SDKs currently supported.
  • Requests can use execute (decide now) or prefetch (decide ahead of rendering and apply later). The server renders the decided offer.
  • Advantages: no flicker, better for logged-in and complex logic, and secure handling of data. Drawbacks: developer work and a clear mbox-to-page mapping are needed. Caching requires care.
4.3 Mobile apps
  • Target provides mobile SDKs for iOS and Android. Experiences use the same activity model and mboxes or offers. Verify the current mobile library and its relationship to Edge.
  • Consider app versions and offline behavior. Experiences must degrade gracefully when the device is offline.
4.4 Email
  • Target personalization in email is usually delivered by calling the Target API at send time or when the email is opened through a dynamic image or content call. Verify current email integration options.
  • Consider privacy, caching in email clients, and the lack of JavaScript in most email clients.
4.5 APIs
  • Delivery API: runtime decisions for web, server, and apps.
  • Management / Admin APIs: manage activities, audiences, and settings programmatically. Verify endpoints.
  • Recommendations API: returns recommendations (Chapter 5).
4.6 Hybrid implementations
  • A hybrid design uses both client-side and server-side delivery. Example: the server decides the core page variant while the client applies small UI tweaks.
  • The main challenge is consistency: the same visitor should get the same decision on both sides.
4.7 Important exam points and common mistakes
  • Client-side and server-side differ in flicker, latency, data access, and developer effort.
  • Server-side isn’t always better. Client-side is simpler when the page is static and the team has limited developer resources.
  • Email and other non-browser touchpoints can’t run JavaScript.

Chapter 5: Adobe Target Recommendations (11%)

  • Overview: Recommendations return ranked items (products, articles, offers) for a visitor, based on the item catalog, criteria, and algorithm.
  • Catalogs: a catalog holds the items to recommend, with attributes such as ID, name, category, price, image, and availability. Load catalogs by feed upload, API, or connector. Verify the current supported methods. Data quality matters: missing attributes, duplicate IDs, and stale availability are common causes of poor recommendations.
  • Criteria: criteria filter and rank items, for example “same category, in stock, price under $100.” They can also set business rules, such as boosting or excluding items. Criteria are evaluated at request time, so their logic affects performance.
  • Strategies: popularity-based, recently viewed, similar items, and personalized (behavior-based). Verify the current strategy list. Algorithms need data. A new site with little behavior data will get weak personalized results.
  • Configuration: create a recommendation activity, select the catalog and criteria, and map it to an mbox. Request recommendations from the Recommendations API or through the mbox on the page. Test with real catalog data in staging first.

Important exam points: the catalog supplies the items; criteria decide which items qualify and their order. Recommendations depend on catalog quality as much as on the algorithm.

Common mistakes: blaming the algorithm for results that come from bad catalog data; using criteria that exclude all items, which returns empty results.

Chapter 6: Architecture, Design, and Implementation (18%)

6.1 Architecture principles
  1. Separate decisioning from content: Target decides which experience to show. AEM or the site owns the content.
  2. Choose the delivery model deliberately: client-side, server-side, Edge, or hybrid. Base the choice on performance, data needs, and team skills.
  3. Plan the data flow: identify what data Target needs (mbox parameters, profile attributes, audiences) and where it comes from.
  4. Design for measurement: define goals and metrics before building. Check that Analytics and Target share the same definitions.
  5. Plan for failure: define a default experience for when Target doesn’t respond or times out.
6.2 Global mbox
  • target-global-mbox runs on every page where the library is loaded. It serves global activities and sets defaults.
  • Keep it lightweight. Heavy activities or many global offers slow every page. Use specific mboxes for page-level experiences.
  • Common mistake: putting everything in the global mbox, which makes it hard to troubleshoot and manage.
6.3 Order Confirmation mbox
  • A reserved mbox on the order confirmation page sends order data to Target for revenue and conversion goals. Verify the name and parameters in current docs.
  • Confirm the mbox fires exactly once per order. Duplicate firing inflates revenue. Protect against page refreshes and back-button re-fires.
  • Order total, product IDs, and currency must be correct. Check that they match the order system.
6.4 Hybrid implementation design
  • Assign each experience to a delivery method based on need. Example: server-side for logged-in pricing, client-side for layout tests.
  • Keep the visitor identity consistent so the same visitor gets the same decision on both sides.
  • Document which team owns each delivery path.
6.5 Performance and flicker
  • Measure the time added by Target calls.
  • Use timeouts and a default experience for slow responses.
  • Prefer server-side or Edge delivery for above-the-fold content that must not flicker.
6.6 Testing and QA
  • Test each experience in each browser, device, and logged-in state.
  • Verify that the mbox fires, the correct offer renders, and metrics arrive in Target and Analytics.
  • Test the fallback when Target is blocked (ad blockers, consent refusal, network failure).
6.7 Design checklist
6.8 Important exam points and common mistakes
  • Know the purpose and risks of the Global mbox and the Order Confirmation mbox.
  • Know how hybrid designs keep decisions consistent.
  • Common mistakes: forgetting the fallback experience; firing order confirmation logic more than once; designing a hybrid system without a shared identity.

Chapter 7: Troubleshooting (28%)

Troubleshooting is the largest domain. Practice the workflow below until you can follow it without notes.

7.1 Troubleshooting workflow
  1. Define the symptom precisely: no offer, wrong offer, flicker, missing metrics, or traffic mismatch.
  2. Check scope: one page, one browser, one audience, or everywhere?
  3. Check delivery: did the library load? Did the mbox request fire? What was the response?
  4. Check targeting: does the visitor qualify for the audience? Is traffic allocated?
  5. Check the activity: is it live? Is the date range correct? Are the experiences and offers active?
  6. Check measurement: are goals and metrics firing? Do Analytics and Target agree within tolerance?
  7. Fix, retest, and document.
7.2 Debugging tools
  • Target/Experience Cloud debugger browser extension and Target’s built-in debugging. Verify current tool names.
  • Browser developer tools: the network tab for Target requests, the console for errors, and cookies for mbox identifiers.
  • Debug parameters and trace options (for example, mboxTrace in legacy at.js). Verify.
7.3 Mbox errors
Symptom Likely cause Check
Mbox never fires Library didn’t load, blocked script, consent refusal Network tab, consent state, console errors
Mbox fires but no offer Visitor doesn’t qualify, activity not live, no default content Audience, activity status, offer status

7.4 Reading Target requests and responses
  • Request: contains the client code, mbox name, visitor identifiers, page parameters, and context (device, location, and similar).
  • Response: contains the mbox name, the offer selected, the activity and experience IDs, and metadata.
  • The exam often asks you to identify a missing parameter, a wrong mbox name, or a response that shows the visitor was excluded.

Illustrative request (structure only; field names simplified):

    "mboxes": [
      { "index": 0, "name": "pdp-hero", "parameters": { "productId": "123" } }
    ]
  }
}

  "execute": {
    "mboxes": [
      {
        "index": 0,
        "name": "pdp-hero",

7.5 Activity configuration problems
  • Wrong audience: the audience rules don’t match the intended visitors.
  • Traffic too low: the allocation or audience size is too small for a result.
  • Overlapping activities: another activity on the same mbox or page takes priority.
  • Dates: the activity starts or ends at the wrong time (check time zones).
  • Goals: the primary metric is not firing or is mapped to the wrong event.
7.6 Integration problems
  • Analytics mismatch: check report suite configuration, variable mapping, attribution windows, and time zones.
  • AEM rendering: check that offers are mapped to the right components and that caching isn’t serving the same page to everyone.
  • Edge/Web SDK: check the Edge configuration, extension version, and identity.
  • Audience sync: check the source audience is active, has the correct size, and is connected.
7.7 Recommendations problems
  • Empty results: check criteria (overly restrictive) and catalog (missing or stale items).
  • Irrelevant results: check catalog attributes and the chosen strategy.
  • Slow responses: check the number of items and criteria complexity.
7.8 Worked troubleshooting scenario

Symptom: a product-page hero test shows the default content for all visitors in production, but the offer appears in staging.

  1. Confirm the production activity is live and dated correctly.
  2. Check whether the production page loads the same library and mbox name as staging. A typo in the mbox name is a common cause.
  3. Check the network request in production. If there’s no request, the library or the tag isn’t firing.
  4. If the request fires but returns default content, check the audience and traffic allocation.
  5. Check consent settings. If visitors have declined consent, Target may not deliver.
  6. Fix the root cause, retest in production with a test account, and document the change.
7.9 Important exam points and common mistakes
  • Work from the symptom to the layer (delivery, targeting, activity, measurement) instead of guessing.
  • Know how to read a response and what an empty options list means.
  • Most “no offer” issues come from audience, status, or delivery problems, not from the algorithm.
  • Common mistakes: changing configuration before confirming what the request and response show; ignoring consent state when debugging; assuming a test is broken when the audience is simply too narrow.

Chapter 8: Quick-Reference Notes

8.1 Definitions
  • Mbox: named delivery container on a page or in an app.
  • Offer: content returned for an mbox.
  • Activity: experiment or personalization definition.
  • Experience: one variation in an activity.
  • Global mbox: target-global-mbox, the default mbox on pages with the library.
  • Order Confirmation mbox: reserved mbox for order data. Verify name.
  • Prefetch / execute: server-side request types (decide later versus decide now).
8.2 Distinctions
Pair Difference
A/B vs. XT Test with significance versus targeting without comparison
Auto-Target vs. Auto-Allocate Per-visitor selection versus traffic shift over time
Audience vs. Analytics segment Target qualification rules versus Analytics reporting filter
Client-side vs. server-side Flicker and browser visibility versus no flicker and developer effort
Catalog vs. criteria Items versus rules that filter and rank them
Execute vs. prefetch Decide now versus decide before rendering
AdBox vs. Redirector Image changes with fixed link versus landing page changes
getOffer vs. applyOffer Retrieves the offer versus displays it
Profile parameters vs. profile scripts Sent with the request versus computed on Target’s server
Data providers vs. targetPageParams() Asynchronous data with content hiding versus synchronous page parameters
8.3 Configuration considerations
  • Client code and environment must match the delivery endpoint.
  • at_property must be present at page level in multi-tenant setups.
  • Timeouts and default content protect against slow responses.
  • Consent settings affect whether delivery and measurement occur.
  • Identity must be consistent across Target, Analytics, and Edge.
  • at.js must load early in HEAD with the pre-hiding snippet, and the data layer must come before it.
8.4 Best practices
  • Separate environments and test in staging.
  • Name everything consistently and document each activity.
  • Keep the Global mbox lightweight.
  • Guard the Order Confirmation mbox against duplicate firing.
  • Retire finished activities.
  • Send live values (inventory, price, conversions) with the request rather than relying on nightly feeds.
8.5 Commonly misunderstood concepts
  • The Global mbox doesn’t replace specific mboxes.
  • Traffic allocation applies to qualified visitors only.
  • Traffic Allocation splits visitors within one activity. A profile script attribute splits visitors across activities.
  • Analytics and Target numbers are expected to differ somewhat.
  • Empty recommendations usually mean criteria or catalog problems. A no_content response can mean results aren’t cached yet at the Edge.

1.7 A/B Testing Best Practices
The Golden Rules
  1. Wait for Calculated Sample Size - Most critical rule. Prevents false positives.
  2. Maintain 95%+ Confidence - Only 5% false positive risk
  3. Avoid Peeking - Multiple checks inflate false positive risk
  4. Account for Novelty Effect - New designs perform better initially
  5. Identify Confounds - External events can skew results
🔴 Common Pitfalls:
  • Peeking at results (increases false positives from 5% to 20%+)
  • Stopping early when lift looks good (before sample size)
  • Not accounting for novelty effect (new designs initially outperform)
  • Testing without calculating sample size first
  • Confusing percentage points with relative lift

3.1 Understanding Statistical Concepts
Conversion Rate
Formula: (Conversions / Visitors) × 100
Example: 50 conversions / 1,000 visitors = 5%
Lift
Formula: (Variation% - Control%) / Control% × 100
Example: (6% - 5%) / 5% × 100 = 20% lift
⚠️ Common Confusion: 20% lift in relative terms ≠ 20 percentage points
20% relative lift = 1 percentage point absolute difference (5% → 6%)
Confidence and Significance
Confidence Level False Positive Risk Action
95%+ Confidence 5% (acceptable) DECLARE WINNER
80-94% Confidence 6-20% (high risk) Continue testing
<80% Confidence >20% (very high) Much more data needed
Sample Size Importance: You MUST reach calculated sample size before declaring winner, even if confidence seems high at 85-90%.
3.2 Automated Personalization Reporting
Report 1: Activity Level Report
  • Shows: Control (random) vs. Targeted (AI)
  • Answers: "Is personalization working?"
Report 2: Offer Level Report
  • Shows: Each offer's Random vs. Smart performance
  • Key: Compare same offer (Random vs. Smart), NOT different offers
Report 3: Automated Segments Report
  • Shows: Auto-discovered visitor groups
  • Reveals: Which segments prefer which offers
Report 4: Important Attributes Report
  • Shows: Which attributes ML used most
  • CRITICAL MISUNDERSTANDING: This is FREQUENCY of use, NOT causation
🔴 Important Attributes Mistake:
❌ "Device Type causes 28% of conversions"
✅ "Algorithm used Device Type in 28% of decisions"
3.3 Multivariate Testing Reporting
Experience Performance Report
  • Shows each element combination's performance
  • Comparison of all combinations side-by-side
Element Contribution Analysis
  • Breaks down impact of individual elements
  • Shows which variables matter most
Bonferroni Correction
  • What it does: Adjusts significance threshold for multiple comparisons
  • Why: Testing many elements inflates false positive risk
  • Solution: Stricter threshold per comparison
3.4 Interpreting Confidence Intervals
Example:
Variation: 6.2% ± 0.4%
95% Confidence Interval: 5.8% - 6.6%
Means: 95% confident true rate is between 5.8% - 6.6%
Overlapping vs. Non-Overlapping Intervals
  • Intervals OVERLAP: No significant difference (continue testing)
  • Intervals DON'T OVERLAP: Significant difference (safe to declare winner)
Domain 3 Summary
  • Understand conversion rate, lift, confidence calculations
  • Know 95%+ confidence requirement for declaring winner

Critical Exam Concept: QA Preview Modes

You've just identified an important exam question we need to cover deeply. Let me explain all QA/Preview settings in Adobe Target.

What is QA Mode?

QA (Quality Assurance) Mode in Adobe Target allows you to:

  • Preview activities before going live
  • See how experiences will appear
  • Test without affecting real data/reporting
  • Validate audience targeting
  • Check experience delivery

The 3 Main QA/Preview Options

Option 1: "Show Default Content for All Other Activities"

Setting: ON or OFF

What it does:

  • ON = Preview ONLY your activity in isolation (ignore all other live activities)
  • OFF = Preview your activity WITH other live activities included (realistic view)

Use case:

  • ON: "Does my activity's content work in isolation?"
  • OFF: "How does my activity look alongside other live activities?"

Example:

You have Activity A (button color) and Activity B (banner text) running on homepage

Preview with "Show default content" ON:
├─ See only: Banner with your test button color
├─ Other activities: Ignored
└─ View: Isolated, clean

Preview with "Show default content" OFF:
├─ See: Banner with your test button color + Activity B's banner text
├─ Other activities: Included (with collision/priority applied)
└─ View: Realistic production scenario
Option 2: "Match Audience Rules to See Experiences"

Setting: ON or OFF

What it does:

  • ON = Preview shows activity ONLY if you match all audience rules
  • OFF = Preview shows activity regardless of whether you qualify for audiences

Use case:

  • ON: "Will only qualified visitors see this experience?"
  • OFF: "Let me see the experience even if I don't match the audience"

Example:

Activity audience rules:
├─ Country = United States
├─ Device Type = Mobile
└─ Visitor Type = Returning

Preview with "Match audience rules" ON:
├─ If you're accessing from US on mobile as returning → See activity ✓
├─ If you're accessing from Canada → Don't see activity ✗
├─ If you're on desktop → Don't see activity ✗
└─ View: Only see if you fully qualify

Preview with "Match audience rules" OFF:
├─ You see activity regardless of:
│  ├─ Where you're accessing from
│  ├─ Device type
│  └─ Visitor status
└─ View: Always see the experience to test it

WHY THIS MATTERS:

  • Ensures audience rules are working correctly
  • Validates that the right visitors see the right experiences
  • Catches audience misconfiguration before launch
Option 3: Activity Assignment Method (Less common but worth knowing)

Some preview modes let you control:

  • Direct URL = Use special URL parameters to preview
  • QA Link = Generate a unique QA link to share
  • Bookmarklet = Use browser bookmarklet for quick preview toggle

You just want to see if your offer/experience content looks good.

Best Settings:

  • Match audience rules: OFF (don't block you with audience rules)

Why:

  • ON = see only your content

  • Focus on: Does the experience look right?

You want to see exactly what a qualified visitor will see in production.

Best Settings:

Journey Types & Entry Points

1. Unitary Event Journey
Trigger: Customer performs an action (click, purchase, form submission)
Timing: Real-time, immediate
Reentrance: 5-minute block (default)
Event payload limit: 64 KB

Best for: Immediate reactions, real-time personalization

Example: Customer abandons cart → email within 15 minutes
Key guardrails:
  • 5-minute reentrance block prevents duplicate messages
  • 64 KB event payload limit (exceeding drops event silently)
  • 1 MB journey instance limit (data accumulation during execution)
  • Cannot coexist with business events in same journey
2. Business Event Journey
Trigger: External system sends an event (not customer action)
Timing: Scheduled or batch
Best for: Aggregated data, scheduled sends
Example: Daily purchase summary email at midnight
Key guardrails:
  • Cannot coexist with unitary events in same journey
  • Cannot coexist with audience qualification
3. Read Audience Journey
Trigger: Scheduled batch read of an audience
Timing: Daily, weekly schedule or triggered by business event
Best for: Batch campaigns, audience-wide initiatives
Example: Every Monday 9 AM, read all VIP customers and send weekly digest
Key guardrails:
  • 5 concurrent instances max (organization-wide) - Stagger 5-10 minutes apart
  • 12-hour processing timeout
  • 20K profiles/sec sandbox throughput
  • One audience per journey
  • Cannot use with Campaign Standard activities
4. Audience Qualification Journey
Trigger: Customer enters or exits an audience in real-time
Timing: Real-time as they qualify/disqualify
Activation delay: Up to 10 minutes
Example: Churn score changes → immediately trigger retention journey

Capping & Ranking Logic

How Capping Works
Capping is PER-OFFER, not decision-level
Example:
Offer A: "Robo-Advisor Service" (priority 1, capped at 3/month)
Offer B: "Managed Portfolio" (priority 2, capped at 3/month)
Offer C: "Self-Directed Trading" (priority 3, capped at 3/month)

Customer has received Offer A 3 times this month (capped)
System evaluates: A is capped, skip it
System evaluates: B hasn't reached cap → deliver B
(Does NOT deliver fallback)
Key Rule: When top-priority offer is capped → system selects next ranked uncapped offer. Does NOT fail decision.

Schemas: Profile vs. Event

Memory Trick
PROFILE = "WHO is the customer?" (Static attributes)
EVENT = "WHAT did they do?" + "WHEN?" (Time-series actions)
Profile Schema (XDM Individual Profile)
Purpose: Stores customer attributes (WHO they are)
Data type: Personal info — name, email, age, preferences, loyalty tier
When enabled for profile: Profile data stored in Unified Profile Service (real-time access)
Example fields: firstName, lastName, email, phone, loyaltyTier, lastPurchaseDate
Event Schema (XDM ExperienceEvent)
Purpose: Stores what customers did (behavioral events)
Data type: Time-series events — purchase, click, view, search
When enabled for profile: Event data stored and linked to customer profiles
Example fields: eventType, timestamp, productViewed, purchaseAmount, pageURL

Datasets

Datasets Enabled for Profile
  • ✅ Data ingested into Unified Profile Service (real-time)
  • ✅ Available for real-time personalization in journeys
  • ✅ Can be referenced in journey conditions
  • ⚠️ Counts against engageable profile quota (costs money)
Datasets NOT Enabled for Profile
  • ❌ Data stays in Data Lake only (not real-time)
  • ❌ Cannot be accessed instantly in journeys
  • ❌ Can be queried/analyzed but not for real-time personalization
  • ✅ Does NOT count against engageable profile quota (no cost)
Exam Pattern
"Marketer wants to use purchase history in journey condition. Dataset enabled for profile?"
Answer: YES, must be enabled for profile

Identities

Authenticated Identities (Known Customers)
  • Email: john@example.com
  • CRM ID: CUST-12345
  • Mobile AAID/IDFA: Unique mobile device ID
  • Custom ID: Your proprietary customer ID
Pseudonymous Identities (Anonymous/Unknown Visitors)
  • ECID (Experience Cloud ID): Adobe's auto-generated ID for unknown browsers
  • Used for: Tracking anonymous website visitors
  • Gets merged: When visitor logs in, ECID + email link together
Identity Merging
Scenario:
Day 1, 2 PM: Anonymous visitor (ECID-12345) views products, adds to cart
Day 1, 3 PM: Same person logs in (email: john@example.com, CRM ID: CUST-54321)
System links: ECID-12345 + email + CRM ID → same profile
ALL historical data merges automatically

Journey condition "if customer viewed products + added to cart in last 24 hours"
System finds ALL merged data → triggers journey ✓
Engageable Profile Impact
  • ✅ Authenticated identities (email, CRM ID) = count as engageable
  • ✅ Pseudonymous identities (ECID) = count as engageable too
  • 💡 Solution: Set TTL (Time-To-Live) on pseudonymous profiles to auto-delete
  • 💡 Recommendation: 14-day TTL for pseudonymous profiles

Schemas (The Data Blueprint)

Profile Schema (XDM Individual Profile)

Purpose: Stores customer attributes (WHO they are)

Data type: Personal info — name, email, age, preferences, loyalty tier

When enabled for profile: Profile data stored in Unified Profile Service (real-time access)

Real-time access: Can be accessed instantly in journeys

Example fields: firstName, lastName, email, phone, loyaltyTier, lastPurchaseDate

Key rule: Attributes that describe the customer

Event Schema (XDM ExperienceEvent)

Purpose: Stores what customers did (behavioral events)

Data type: Time-series events — purchase, click, view, search

When enabled for profile: Event data stored and linked to customer profiles

Real-time access: Events can trigger journeys in real-time

Example fields: eventType, timestamp, productViewed, purchaseAmount, pageURL

Key rule: Actions with timestamps, what happened WHEN

Schema Distinction Memory Trick
PROFILE = "WHO is the customer?" (Static attributes)
EVENT = "WHAT did they do?" + "WHEN?" (Time-series actions)

Datasets (The Data Containers)

Datasets Enabled for Profile
  • Data ingested into Unified Profile Service (real-time profile)
  • Available for real-time personalization in journeys
  • Can be referenced in journey conditions and personalization fields
  • Counts against engageable profile quota (costs money)
  • Example: Customer behavior, purchase history, preference updates
Datasets NOT Enabled for Profile
  • Data stays in Data Lake only (not real-time profile)
  • Cannot be accessed instantly in journeys
  • Can be queried/analyzed but not for real-time personalization
  • Does NOT count against engageable profile quota (no cost)
  • Example: Historical data for analysis, logs, archive

Exam pattern: "Marketer wants to use purchase history in journey condition. Dataset enabled for profile?" → YES

Identities (How We Know Who Customers Are)

Authenticated Identities (Known Customers)
  • Email: john@example.com
  • CRM ID: CUST-12345
  • Mobile AAID/IDFA: Unique mobile device ID
  • Custom ID: Your proprietary customer ID
Pseudonymous Identities (Anonymous/Unknown Visitors)
  • ECID (Experience Cloud ID): Adobe's auto-generated ID for unknown browsers
  • Used for: Tracking anonymous website visitors before login
  • Gets merged with authenticated ID: When visitor logs in, ECID + email link together
Identity Merging
Before login: Visitor is ECID (pseudonymous)
  └─ All behavior linked to ECID-12345

Login event: Visitor enters email john@example.com
  └─ ECID-12345 + Email + CRM ID all link to same profile
  └─ ALL historical data (clicks, views, carts) auto-merge

Journey condition runs: "If customer viewed products + added to cart"
  └─ System finds historical behavior from ECID time
  └─ Triggers journey with merged data

Engageable profile impact:

  • Authenticated identities (email, CRM ID) = count as engageable profiles
  • Pseudonymous identities (ECID) = count as engageable profiles too
  • Solution: Set TTL (Time-To-Live) on pseudonymous profiles to auto-delete inactive ones
  • Recommendation: 14-day TTL for pseudonymous profiles

Audience Types

Segment Builder (Rule-Based Audiences)
  • How: Drag-and-drop conditions (age > 25 AND location = CA AND purchase > $100)
  • Timing: Batch evaluation (typically daily) OR streamed (real-time)
  • Use case: Standard segmentation
  • Example: "Customers who spent > $500 in last 30 days"
Audience Composition (Orchestrated Audiences)
  • How: Combine multiple audiences with logic (Audience A + Audience B - Audience C)
  • Timing: Batch evaluation
  • Use case: Complex audience combinations
  • Example: "(VIP customers) + (recently inactive) - (already contacted)"
  • Limit: Max 50 published compositions per sandbox
Streamed vs. Batch Audiences
Aspect Streamed Batch
Real-time update? YES (immediately) NO (daily)
When evaluated? Real-time as rules change Once per day
Use in journey? Audience Qualification (real-time trigger) Read Audience (scheduled batch)
Recommendation Use for real-time logic Use for scheduled campaigns

Exam pattern: "Real-time journey trigger when audience changes" → streamed audience + Audience Qualification activity

DECISION TREES

Tier 1: Most Tested Guardrails

1. The 50-Activity Limit
  • What: Maximum 50 activities per journey
  • When applied: At publish time
  • What fails: Publishing blocked with error
  • Solution: Split into sub-journeys using jump activities
  • Exam trigger: "Journey won't publish" or "Too many activities"
  • Key rule: Cannot increase limit; must split
2. The 5-Minute Reentrance Block (Unitary Events)
  • What: Profile cannot re-enter same unitary event journey for 5 minutes
  • Example: Event fires at 12:01 PM → journey starts. Same event at 12:03 PM → blocked until 12:06 PM
  • Why: Prevents duplicate messages
  • Exam trigger: "Why isn't customer getting second email?" or "Profile triggered twice but got one message"
  • Key rule: This is automatic; customer cannot bypass it
3. The 64 KB Event Payload Limit
  • What: Event entering journey cannot exceed 64 KB (uncompressed JSON)
  • When applied: When event enters journey (at start activity)
  • What happens: Event silently dropped → profile never enters → no log entry
  • Symptom: Zero profiles entering despite events being sent
  • Exam trigger: "Why are NO profiles entering the journey?"
  • Key rule: 64 KB applies ONLY at entry; different from 1 MB instance limit
4. The 1 MB Journey Instance Limit
  • What: All data accumulated during journey execution ≤ 1 MB
  • When applied: During journey execution (mid-journey)
  • What happens: Profile marked ERROR status → exits journey
  • Symptom: SOME profiles error (usually those with more data), SOME complete
  • Data that counts: Event payload + profile attributes + API responses + email content
  • Recommendation: Keep initial event < 800 KB for buffer
  • Exam trigger: "500 of 10,000 profiles errored. All errors are high-value accounts" → 1 MB limit
  • Key rule: Selective profile failures point to this limit
5. The 200 Active Journeys Limit (Production) / 100 (Development)
  • What: Maximum 200 live/paused/closed journeys in production
  • When applied: At publish time
  • Solution: Pause or delete old journeys
  • Exam trigger: "Cannot publish journey" or "Active journey limit reached"
6. The 5 Concurrent Read Audience Instances
  • What: Only 5 Read Audience journeys running simultaneously across entire organization
  • When applied: At publish time
  • Solution: Stagger start times 5-10 minutes apart
  • Exam trigger: "Why does Team 6's Read Audience journey fail to publish when Teams 1-5 succeeded?"
  • Key rule: Organization-wide limit, not per-sandbox
7. The 12-Hour Read Audience Processing Timeout
  • What: Read Audience jobs must complete within 12 hours
  • What happens: Jobs not processed in 12 hours auto-deleted → journey doesn't run
  • Solution: Ensure audience size processes within 12 hours; split if needed
  • Exam trigger: "Read Audience job didn't execute" or "Journey ran but no profiles"
8. The 2 MB Email Message Content Size
  • What: Final email content (after backend processing) ≤ 2 MB
  • Recommendation: Keep authored content < 1 MB to allow 300-400 KB processing buffer
  • When applied: At publish time
  • What fails: Journey publication blocked if exceeded
  • Exam trigger: "Journey won't publish due to content size"
9. Custom Action Capping: 300K calls/min or 150K calls/30 sec
  • Fast endpoints (< 0.75 sec response): 300,000 calls per minute
  • Slow endpoints (> 0.75 sec response): 150,000 calls per 30 seconds
  • Sliding window applied per sandbox, per endpoint
  • Exam trigger: "Company has 500K profiles wanting to call endpoint" → must throttle
10. Fragment Size Limits
  • Any fragment (visual or expression): 700 KB max
  • Count: up to 60 unique fragments per content variant (warning at 45); 120 across all variants of a message
  • Exam trigger: "Fragment won't save, exceeds size limit"
11. Business Events Cannot Coexist with Unitary Events
  • Rule: Same journey cannot have both business event AND unitary event triggering
  • BUT: Different journeys CAN have different event types
  • Exam trigger: "Can we use business event in Journey A and unitary in Journey B?" → YES
12. Audience Qualification: 10-Minute Activation Delay
  • What: Up to 10 minutes for audience qualification to start listening
  • Exam trigger: "Audience activated but journey didn't start immediately"
13. Audience Compositions: 50 Max Per Sandbox
  • What: Up to 50 published audience compositions per sandbox (Federated compositions are not counted)
  • Solution: Delete old ones to create new ones
14. Event Reference Limit: 1 Event → 25 Journeys Max
  • What: Single event can be used by maximum 25 journeys simultaneously
  • When exceeded: Cannot publish additional journeys using that event
15. Schema Reference Limit: 1 Schema → 100 Events Max
  • What: Single XDM schema can be referenced by maximum 100 events
  • When exceeded: Cannot publish journeys with events using that schema
