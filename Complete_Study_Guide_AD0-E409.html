1. How to use this guide

Read sections 2 to 9 in order, then use section 10 to check each question. Work through the 3-day plan in section 11. Verify exact parameter names and at.js function signatures in the Adobe documentation before the exam, because they change between versions.

2. Core concepts and page-load order

at.js is the client library that runs Target requests and applies experiences. It must load early in <HEAD>, after the data layer and VisitorAPI.js.

  1. Data layer in <HEAD> before at.js (Q2).

  2. VisitorAPI.js loads first, creating the Experience Cloud ID (Q11).

  3. Pre-hiding snippet and at.js in <HEAD> so the page is hidden until Target responds (Q49).

  4. The global mbox fires on page load and triggers the execution order below.

Execution order when a Target request (mbox) arrives (documented in How at.js works):

  1. Profile scripts run on Target's server, per request, before audience decisions (Q4).

  2. Profile Store builds the profile from request parameters and script output.

  3. Audiences are qualified from the Audience Library (Target, Analytics, AAM, Experience Cloud).

  4. The highest-priority qualifying activity is selected.

  5. The winning offer is applied. Inline scripts run, then remote scripts load asynchronously.

  6. The pre-hiding snippet is removed and the page is revealed.

Remember: scripts, then audiences, then priority, then offer applied, then page revealed.

3. Methods to get data into Target

The key question for each method: where does the data come from, and is it stored in the visitor profile?

Method Stored in profile Use when Remember
Page parameters (mbox parameters) No Describes the page or request (category, product ID, page type) Per request, not per visitor
In-page profile attributes (mbox profile attributes) Yes Visitor data on the page, such as loyalty tier Sent with the mbox and saved
Script profile attributes Yes Value computed on Target's server Runs before audience evaluation
Data Providers Depends Third-party data must load before render Content stays hidden until it resolves
Bulk Profile Update API Yes Many visitors updated from a CSV Batch
Single Profile Update API Yes One visitor updated by API call Real-time, one visitor
Customer Attributes Yes Profile data uploaded by file to Experience Cloud File-based, not page-based

at.js functions

  • targetPageParams() supplies page-level parameters to the global mbox before the request is sent.

  • getOffer requests one mbox and returns the offer to your code. It does not display it.

  • getOffers requests several mboxes in one call (the batch version).

  • applyOffer displays an offer you received. Remember: getOffer gets it, applyOffer shows it.

Data collection commands send events and data from code. Single-page apps must fire a new request when the view changes, because no page load happens.

4. Target request (mbox) parameters and multi-tenant at_property

Parameter Purpose
at_property Property token that ties the request to one property (Q17, Q48)
entity.id, entity.categoryId, entity.inventory Product or category data for Recommendations
profile.* Visitor data sent from the page
user.* Attributes set by profile scripts
mbox3rdPartyId Your own customer ID for cross-device matching (Q32)
tntId Target's visitor ID, generated if you don't supply one (Q21)

Multi-tenant

One Target installation can serve several business units. Each business unit has a Workspace, and each Workspace holds properties (sites or apps). Business units never share activities, audiences, or reports.

at_property

at_property holds the property token, a unique ID string for one property. At page level, every page sends the token of the property it belongs to. Target then applies only that property's activities. If the token is missing or wrong, no activities apply (Q17, Q48).

Parameter rules that affect answers

  • Product page entity.categoryId takes a comma-separated list: one product, several categories. Category page recommendation mboxes take one value that must match exactly (Q27).

  • Most predefined entity attributes (for example entity.brand, entity.pageUrl) are single-value only.

  • Use targetPageParams() for page-level data known at load time (Q30).

5. Profile scripts, profile attributes, audiences and debugging

Profile scripts are JavaScript snippets defined in Target. They run on Target's server for every mbox call, before audience evaluation. Their output becomes user.* attributes. Scripts cannot rely on each other, because their execution order is not guaranteed (Q1, Q4).

Profile parameters are values the page sends with the request. They are stored in the profile and need no server-side script.

Splitting audiences so two activities don't overlap: use a profile script to set an attribute that each audience checks (Q5). Traffic Allocation only splits visitors within one activity.

Profile expiration: monthly visitors look new if the profile expires first. Increase the profile expiration above the default 14 days (Q7).

Audience sources

Source What it is
Target audiences Built from mbox parameters and profile attributes (Q16)
Analytics audiences Segments from Adobe Analytics
AAM audiences Segments from Audience Manager, for third-party or anonymous data (Q14)
Experience Cloud audiences Built in the Audience Library (People Core Service) (Q6, Q47)

Debugging: use mboxTrace to compare profile values before and after a profile script runs (Q45, Q46). Running scripts in the browser console before saving is not marked correct in the practice key for Q46, so treat it as Verify.

6. Activities, delivery by URL, AdBox and redirector

Activity types

  • Experience Targeting: one winning experience per visitor, chosen by audience.

  • A/B Test: one variation compared with the control, traffic split evenly.

  • Multivariate test (MVT): tests combinations of several elements at once. Needs more traffic than an A/B test.

  • Automated Personalization: machine learning picks the best offer per visitor.

  • Recommendations: product suggestions from a catalog and criteria.

Delivery by URL sets which pages an activity runs on: URL is (exact match), URL contains, URL starts with, and regex. A rule that is too strict hides the activity in QA (Q41).

AdBox is the no-JavaScript method for ads and offsite content. It returns a different image while the link stays fixed. The Target URL uses the ubox/image path. It has no client-side timeout, so if Target is down, visitors see no content. It cannot show dynamic creative such as an abandoned-cart product (Q3).

Redirector changes the landing page of an ad. Its path is ubox/page. Use it when the destination changes, not the image. Redirectors need allowlisted hosts to avoid open redirect risk.

AdBox Redirector
Changes Image in the ad Landing page
Path ubox/image ubox/page

7. Offers, experiences and VEC

Experience: what the visitor sees, built in the Visual Experience Composer (VEC).

  • HTML offers for web pages, built in VEC.

  • JSON offers for apps or custom rendering. Built in Target, styled by app developers (Q20).

  • Image offers and Experience Fragments from AEM (Q12).

Reading a JSON offer: filter the actions array from adobe.target.getOffer() for actions with setJson set to true, then read the JSON from the content property of that action (Q40). setContent is for HTML offers.

Image swapping in VEC: upload image files to Adobe Experience Cloud Assets Core Service and contact Customer Care for the Scene7 account configuration (Q8).

AEM Experience Fragments to Target needs the Cloud Services for Target configuration in AEM and the AEM Link Externalizer (Q13).

VEC selectors are the CSS selectors that locate page elements. A changed page structure can break them.

Implementation types

  • Client-side (at.js): the browser library. Load early in <HEAD>.

  • SPA: single-page apps must fire a new Target request on each view change.

  • Mobile: VEC in the mobile app supports Experience Targeting and A/B tests (Q28).

8. Recommendations and entity attributes

Recommendations uses a catalog built from feeds, collections, or Analytics classifications. Criteria decide which products are shown. Results are cached at Edge servers, so a no_content response can mean results are not yet cached at the nearest Edge server (Q38).

Where product data comes from

  • Product feeds (Google Product Feeds): reuse organic search product data and automate inclusion (Q26).

  • Feeds entity: product attributes such as profit margin (Q24).

  • Entity inventory: send live inventory with the request, entity.inventory from the data layer, instead of relying on a nightly CSV (Q23).

Category recommendations

  • Product page: entity.categoryId takes a comma-separated list. Commas separate categories, colons separate subcategory levels.

  • Category page: one categoryId only, matching the product page value exactly (Q27).

Catalog link: a fully qualified domain name, including the subdomain, links a request to one product catalog (Q25).

Templates: entity references in Recommendations design templates need a $ in front (Q39).

9. Analytics, reporting and access

  • A4T (Analytics for Target) sends Target results into Analytics. Target conversions appear under the Activity Conversions metric (Q9, Q15). A4T needs at.js and VisitorAPI.js, with at.js loaded after VisitorAPI.js (Q11).

  • Reporting source: choosing Analytics as the source requires membership in the Web Services Access Group in Adobe Analytics. Enterprise permissions alone are not enough (Q37).

  • Hosts separate production traffic from dev and staging in reports (Q19).

  • Bot traffic: Target does not create or retrieve a profile for known bots, and it does not log an activity visit for reporting (Q18).

  • Experience Cloud audience status: check the Audience Library in People Core Service (Q47).

  • Customer identity: AAM segments without slowing the page use Experience Cloud ID Service (Q10).

  • Combining A/B results with Analytics data: implement A4T (Q15).

  • Credit card platinum and anonymous third-party data: Audience Manager (Q14).

10. Mobile, server-side, and the Q1 to Q49 answer key

Mobile and server-side

  • iOS targeted locations: the two primary methods are targetLoadRequest and targetCreateRequestWithName (Q29).

  • Android with AEP Mobile SDK: retrieve a custom visitor ID passed from a CRM with getThirdPartyId() (Q31). getTntId() returns Target's own ID, and Visitor.getInstance(...).getMarketingCloudVisitorID() returns the Experience Cloud ID.

  • Same experience across devices for logged-in users: populate the mbox3rdPartyId parameter with the user's ID, and call the Visitor API setCustomerIDs with the user's ID and authenticated state (Q32).

  • Server-side: if no ID is specified, Target generates a tntId (Q21). aamUUID is an Audience Manager identifier.

Chapter 1: Adobe Target Fundamentals (13%)

1.1 Overview

Adobe Target is Adobe’s personalization and experimentation platform. It delivers content variations (offers) to visitors and measures their effect on business metrics. It sits in the Adobe Experience Cloud alongside Adobe Analytics, Adobe Experience Manager (AEM), and Adobe Experience Platform (AEP).

1.2 Core concepts
Term Meaning
Property / Client code Identifies your Target account and the delivery endpoint (for example, {clientCode}.tt.omtrdc.net).
Workspace A Target area containing activities, audiences, and settings.
Mbox A named container on a page or in an app where Target can deliver content. Mboxes are the main delivery unit in the legacy at.js model.
Offer The content or experience returned for an mbox.
Activity An experiment or personalization definition: its audience, traffic, experiences, and goals.
Experience One variation within an activity, such as control or variant B. Each experience contains one or more offers.
Audience Rules or segments that decide who sees an activity.
Goal / Metric The success measure, such as conversion, revenue, or clicks.
Traffic allocation The share of eligible visitors who enter an activity and the share each experience receives.
Global mbox A default mbox, target-global-mbox, that runs on every page where at.js is loaded. The PDF practice file calls it the auto-created global Target request (mbox).
Order Confirmation mbox A reserved mbox that Target uses on order confirmation pages to send order data for revenue and conversion measurement. Verify the exact name and setup in current docs.
1.3 Activity types
Type Purpose Key point
A/B test Compare discrete experiences Fixed traffic split; reports a winner by statistics
Multivariate (MVT) Test combinations of element changes Needs more traffic than A/B
Experience Targeting (XT) Show different experiences to audience segments No statistical comparison; targets rather than tests
Auto-Target Machine learning picks the best experience per visitor from a set of options Requires enough historical data
Automated Personalization (AP) Machine learning selects the best offer for each visitor from a set of offers Often compared with Auto-Target; verify current behavior
Auto-Allocate Gradually shifts traffic toward the better-performing experience Lets the test optimize itself while it runs
Recommendations Returns ranked product or content items (Chapter 5) Uses catalogs and criteria
Form-based / Hybrid / Mobile / Email Covered in Chapter 4 Depend on the touchpoint
1.4 Key principles
  • Statistical significance tells you whether a difference is likely real. It doesn’t tell you whether the difference matters. Business significance is a separate decision.
  • Sample ratio mismatch (SRM) happens when the observed traffic split differs from the configured split. SRM usually points to an implementation or delivery problem. Investigate before trusting results.
  • Flicker (flash of original content) happens when the default content renders before Target applies the offer. Mitigate it with the at.js timeout, the body-hiding snippet, or server-side delivery.
1.5 Important exam points
  • Know the difference between a test (A/B, MVT) and targeting (XT).
  • Know which activities need historical data or machine learning.
  • Know that the Global mbox runs without a specific mbox call. Don’t assume it handles conversion data on its own.
1.6 Common mistakes
  • Confusing an mbox (delivery container) with an activity (the experiment definition). One activity can use several mboxes.
  • Assuming traffic allocation equals audience size. Allocation applies to visitors who qualify for the audience.
  • Expecting significance on a low-traffic test within a short window.

Chapter 2: Integrating with Adobe Target (18%)

2.1 Adobe Analytics integration (A4T)

Analytics for Target (A4T) sends Target activity and experience data into Adobe Analytics. Analysts can then report on Target experiences alongside all other dimensions and metrics.

  • Target writes activity and experience values into Analytics variables. The variables are configured in the report suite(s). Verify the mapping in current docs.
  • A4T lets you use Analytics segments and metrics as Target audiences and goals, and Analytics reports show Target outcomes.
  • Conversion counted in Target and in Analytics can differ because of attribution windows, deduplication, and visitor identity. Document which system is the source of truth for each KPI.

Common mistakes: assuming A4T replaces Target’s own reporting; ignoring report suite configuration, since A4T only works for report suites set up for it.

2.2 Adobe Experience Manager (AEM) integration
  • AEM Sites uses Target through the Target integration configured in AEM Cloud Services. Verify current setup steps.
  • AEM can render Target offers as Experience Fragments or as offers mapped to components, so content authors can manage variations inside AEM.
  • The Core Components library includes Target-aware components. Check the current version and whether it’s client-side or server-side rendered.
  • Typical design: AEM renders the default content and Target supplies offers for each mbox. Authors own variations and Target owns decisions.
  • Where rendering happens (server-side in AEM versus client-side in the browser) determines flicker, caching, and how offers are passed in.
  • Caching: if the CDN caches pages, personalized content must bypass the cache or be delivered through a personalization layer.
2.3 Adobe Experience Platform (AEP) and Edge integration
  • Web SDK (Alloy) on the Adobe Experience Platform Edge Network can deliver Target decisions. Edge-based delivery returns personalization decisions (propositions) in the Web SDK response, which then render on the page. Verify field names and the current Edge flow.
  • Data Collection (Tags, formerly Launch) hosts the Target extension. Use it to deploy Target through the tag manager, with environments (development, staging, production).
  • Audiences: AEP audiences (segments from Real-Time CDP) can be used in Target. Activation requires the right permissions and an active connection. Verify the current supported audience sources.
  • Identity: use the same identity (ECID, customer ID) across Edge, Target, and Analytics for consistent visitor identity.
2.4 Other Experience Cloud integrations
  • Adobe Audience Manager (AAM) and Adobe Advertising audiences can be used in Target where supported. Verify availability.
  • Adobe Journey Optimizer and other products can use Target as a decisioning service. Check the current integration path.
  • Customer data: use Target data-sharing rules to define what leaves the browser and what must stay out of it. Privacy settings affect integrations.
2.5 Important exam points
  • A4T reports Target outcomes in Analytics. It doesn’t create Target audiences by itself.
  • AEM integration controls where rendering happens. Know the trade-offs between client-side and server-side rendering.
  • Edge/Web SDK changes how decisions are returned. Know that Edge is the path Adobe is steering toward for new implementations. Verify the current recommendation.
2.6 Common mistakes
  • Confusing audiences (who qualifies) with segments (Analytics filters).
  • Forgetting that identity differences between Analytics and Target lead to mismatched numbers.
  • Assuming an AEM component automatically personalizes. The component must be wired to Target through the configured offers.

Chapter 3: Administration and Governance (6%)

3.1 Roles and access
  • Access is managed through Adobe Admin Console product profiles and Target permissions. Verify the current role model in your organization.
  • Typical roles: administrator (full control), developer (implementation), analyst (reporting), approver (sign-off), and viewer (read-only).
  • Apply least privilege. Separate the people who build activities from the people who approve them and push them live.
3.2 Environments and change control
  • Keep separate development, staging, and production properties, workspaces, or tag environments.
  • Test activities in staging before promoting them. Confirm that the same code and mboxes exist in production.
  • Use approval workflows where available for high-risk changes. Verify current approval features.
3.3 Naming conventions and documentation
  • Use consistent names for mboxes, activities, audiences, and goals. Example: pdp_hero_v2_2026Q4.
  • Record the hypothesis, primary metric, guardrail metrics, dates, owners, and the results decision for each activity.
  • Keep an activity inventory. Retire finished tests so they don’t continue to run and consume traffic.
3.4 Governance concerns
  • Concurrent tests: multiple activities on the same page or audience can interact. Use exclusion groups or mutually exclusive audiences.
  • Traffic budget: limit the share of traffic in experiments to protect the core experience.
  • Privacy and consent: honor consent settings in the tag manager and Target data-sharing configuration. Personal data should not leak into mbox parameters.
  • Data retention and deletion: follow organizational and regulatory rules for visitor data.
3.5 Common mistakes
  • Letting a test run past its decision date.
  • Editing live activities without a test or rollback plan.

Chapter 4: Supported Touchpoints (6%)

4.1 Client-side (web) delivery
  • at.js is the legacy client library. Adobe has moved toward the Web SDK. Verify current library recommendations and version support.
  • The page loads the library, which calls the delivery service for each mbox. Target then applies offers in the browser.
  • Advantages: quick setup, works with most sites. Drawbacks: flicker risk, dependence on browser scripts, and limited visibility into the page.
4.2 Server-side delivery
  • Uses the Delivery API (JSON REST) or Adobe SDKs (Java, Node.js, .NET, and others). Verify the SDKs currently supported.
  • Requests can use execute (decide now) or prefetch (decide ahead of rendering and apply later). The server renders the decided offer.
  • Advantages: no flicker, better for logged-in and complex logic, and secure handling of data. Drawbacks: developer work and a clear mbox-to-page mapping are needed. Caching requires care.
4.3 Mobile apps
  • Target provides mobile SDKs for iOS and Android. Experiences use the same activity model and mboxes or offers. Verify the current mobile library and its relationship to Edge.
  • Consider app versions and offline behavior. Experiences must degrade gracefully when the device is offline.
4.4 Email
  • Target personalization in email is usually delivered by calling the Target API at send time or when the email is opened through a dynamic image or content call. Verify current email integration options.
  • Consider privacy, caching in email clients, and the lack of JavaScript in most email clients.
4.5 APIs
  • Delivery API: runtime decisions for web, server, and apps.
  • Management / Admin APIs: manage activities, audiences, and settings programmatically. Verify endpoints.
  • Recommendations API: returns recommendations (Chapter 5).
4.6 Hybrid implementations
  • A hybrid design uses both client-side and server-side delivery. Example: the server decides the core page variant while the client applies small UI tweaks.
  • The main challenge is consistency: the same visitor should get the same decision on both sides.
4.7 Important exam points and common mistakes
  • Client-side and server-side differ in flicker, latency, data access, and developer effort.
  • Server-side isn’t always better. Client-side is simpler when the page is static and the team has limited developer resources.
  • Email and other non-browser touchpoints can’t run JavaScript.

Chapter 5: Adobe Target Recommendations (11%)

  • Overview: Recommendations return ranked items (products, articles, offers) for a visitor, based on the item catalog, criteria, and algorithm.
  • Catalogs: a catalog holds the items to recommend, with attributes such as ID, name, category, price, image, and availability. Load catalogs by feed upload, API, or connector. Verify the current supported methods. Data quality matters: missing attributes, duplicate IDs, and stale availability are common causes of poor recommendations.
  • Criteria: criteria filter and rank items, for example “same category, in stock, price under $100.” They can also set business rules, such as boosting or excluding items. Criteria are evaluated at request time, so their logic affects performance.
  • Strategies: popularity-based, recently viewed, similar items, and personalized (behavior-based). Verify the current strategy list. Algorithms need data. A new site with little behavior data will get weak personalized results.
  • Configuration: create a recommendation activity, select the catalog and criteria, and map it to an mbox. Request recommendations from the Recommendations API or through the mbox on the page. Test with real catalog data in staging first.

Important exam points: the catalog supplies the items; criteria decide which items qualify and their order. Recommendations depend on catalog quality as much as on the algorithm.

Common mistakes: blaming the algorithm for results that come from bad catalog data; using criteria that exclude all items, which returns empty results.

Chapter 6: Architecture, Design, and Implementation (18%)

6.1 Architecture principles
  1. Separate decisioning from content: Target decides which experience to show. AEM or the site owns the content.
  2. Choose the delivery model deliberately: client-side, server-side, Edge, or hybrid. Base the choice on performance, data needs, and team skills.
  3. Plan the data flow: identify what data Target needs (mbox parameters, profile attributes, audiences) and where it comes from.
  4. Design for measurement: define goals and metrics before building. Check that Analytics and Target share the same definitions.
  5. Plan for failure: define a default experience for when Target doesn’t respond or times out.
6.2 Global mbox
  • target-global-mbox runs on every page where the library is loaded. It serves global activities and sets defaults.
  • Keep it lightweight. Heavy activities or many global offers slow every page. Use specific mboxes for page-level experiences.
  • Common mistake: putting everything in the global mbox, which makes it hard to troubleshoot and manage.
6.3 Order Confirmation mbox
  • A reserved mbox on the order confirmation page sends order data to Target for revenue and conversion goals. Verify the name and parameters in current docs.
  • Confirm the mbox fires exactly once per order. Duplicate firing inflates revenue. Protect against page refreshes and back-button re-fires.
  • Order total, product IDs, and currency must be correct. Check that they match the order system.
6.4 Hybrid implementation design
  • Assign each experience to a delivery method based on need. Example: server-side for logged-in pricing, client-side for layout tests.
  • Keep the visitor identity consistent so the same visitor gets the same decision on both sides.
  • Document which team owns each delivery path.
6.5 Performance and flicker
  • Measure the time added by Target calls.
  • Use timeouts and a default experience for slow responses.
  • Prefer server-side or Edge delivery for above-the-fold content that must not flicker.
6.6 Testing and QA
  • Test each experience in each browser, device, and logged-in state.
  • Verify that the mbox fires, the correct offer renders, and metrics arrive in Target and Analytics.
  • Test the fallback when Target is blocked (ad blockers, consent refusal, network failure).
6.7 Design checklist
6.8 Important exam points and common mistakes
  • Know the purpose and risks of the Global mbox and the Order Confirmation mbox.
  • Know how hybrid designs keep decisions consistent.
  • Common mistakes: forgetting the fallback experience; firing order confirmation logic more than once; designing a hybrid system without a shared identity.

Chapter 7: Troubleshooting (28%)

Troubleshooting is the largest domain. Practice the workflow below until you can follow it without notes.

7.1 Troubleshooting workflow
  1. Define the symptom precisely: no offer, wrong offer, flicker, missing metrics, or traffic mismatch.
  2. Check scope: one page, one browser, one audience, or everywhere?
  3. Check delivery: did the library load? Did the mbox request fire? What was the response?
  4. Check targeting: does the visitor qualify for the audience? Is traffic allocated?
  5. Check the activity: is it live? Is the date range correct? Are the experiences and offers active?
  6. Check measurement: are goals and metrics firing? Do Analytics and Target agree within tolerance?
  7. Fix, retest, and document.
7.2 Debugging tools
  • Target/Experience Cloud debugger browser extension and Target’s built-in debugging. Verify current tool names.
  • Browser developer tools: the network tab for Target requests, the console for errors, and cookies for mbox identifiers.
  • Debug parameters and trace options (for example, mboxTrace in legacy at.js). Verify.
7.3 Mbox errors
Symptom Likely cause Check
Mbox never fires Library didn’t load, blocked script, consent refusal Network tab, consent state, console errors
Mbox fires but no offer Visitor doesn’t qualify, activity not live, no default content Audience, activity status, offer status
Default content shows, expected offer doesn’t Audience mismatch, traffic allocation, timeout Activity audience, allocation, response time
Flicker Client-side rendering after page paint Timeout setting, body-hiding snippet, delivery method
Duplicate offers or double counting Mbox defined twice, tag fired twice Page source, tag manager triggers
Errors in console Syntax or configuration issue Console messages, library version
7.4 Reading Target requests and responses
  • Request: contains the client code, mbox name, visitor identifiers, page parameters, and context (device, location, and similar).
  • Response: contains the mbox name, the offer selected, the activity and experience IDs, and metadata.
  • The exam often asks you to identify a missing parameter, a wrong mbox name, or a response that shows the visitor was excluded.

Illustrative request (structure only; field names simplified):

{
  "context": { "channel": "web", "address": { "url": "https://www.example.com/product/123" } },
  "execute": {
    "mboxes": [
      { "index": 0, "name": "pdp-hero", "parameters": { "productId": "123" } }
    ]
  }
}

Illustrative response structure:

{
  "execute": {
    "mboxes": [
      {
        "index": 0,
        "name": "pdp-hero",
        "options": [
          { "type": "html", "content": "<div>...</div>", "eventToken": "..." }
        ]
      }
    ]
  }
}

If options is empty or only contains default content, the visitor may not qualify or the activity may not be live. Verify the exact response schema in current docs.

7.5 Activity configuration problems
  • Wrong audience: the audience rules don’t match the intended visitors.
  • Traffic too low: the allocation or audience size is too small for a result.
  • Overlapping activities: another activity on the same mbox or page takes priority.
  • Dates: the activity starts or ends at the wrong time (check time zones).
  • Goals: the primary metric is not firing or is mapped to the wrong event.
7.6 Integration problems
  • Analytics mismatch: check report suite configuration, variable mapping, attribution windows, and time zones.
  • AEM rendering: check that offers are mapped to the right components and that caching isn’t serving the same page to everyone.
  • Edge/Web SDK: check the Edge configuration, extension version, and identity.
  • Audience sync: check the source audience is active, has the correct size, and is connected.
7.7 Recommendations problems
  • Empty results: check criteria (overly restrictive) and catalog (missing or stale items).
  • Irrelevant results: check catalog attributes and the chosen strategy.
  • Slow responses: check the number of items and criteria complexity.
7.8 Worked troubleshooting scenario

Symptom: a product-page hero test shows the default content for all visitors in production, but the offer appears in staging.

  1. Confirm the production activity is live and dated correctly.
  2. Check whether the production page loads the same library and mbox name as staging. A typo in the mbox name is a common cause.
  3. Check the network request in production. If there’s no request, the library or the tag isn’t firing.
  4. If the request fires but returns default content, check the audience and traffic allocation.
  5. Check consent settings. If visitors have declined consent, Target may not deliver.
  6. Fix the root cause, retest in production with a test account, and document the change.
7.9 Important exam points and common mistakes
  • Work from the symptom to the layer (delivery, targeting, activity, measurement) instead of guessing.
  • Know how to read a response and what an empty options list means.
  • Most “no offer” issues come from audience, status, or delivery problems, not from the algorithm.
  • Common mistakes: changing configuration before confirming what the request and response show; ignoring consent state when debugging; assuming a test is broken when the audience is simply too narrow.

Chapter 8: Quick-Reference Notes

8.1 Definitions
  • Mbox: named delivery container on a page or in an app.
  • Offer: content returned for an mbox.
  • Activity: experiment or personalization definition.
  • Experience: one variation in an activity.
  • Global mbox: target-global-mbox, the default mbox on pages with the library.
  • Order Confirmation mbox: reserved mbox for order data. Verify name.
  • Prefetch / execute: server-side request types (decide later versus decide now).
8.2 Distinctions
Pair Difference
A/B vs. XT Test with significance versus targeting without comparison
Auto-Target vs. Auto-Allocate Per-visitor selection versus traffic shift over time
Audience vs. Analytics segment Target qualification rules versus Analytics reporting filter
Client-side vs. server-side Flicker and browser visibility versus no flicker and developer effort
Catalog vs. criteria Items versus rules that filter and rank them
Execute vs. prefetch Decide now versus decide before rendering
AdBox vs. Redirector Image changes with fixed link versus landing page changes
getOffer vs. applyOffer Retrieves the offer versus displays it
Profile parameters vs. profile scripts Sent with the request versus computed on Target’s server
Data providers vs. targetPageParams() Asynchronous data with content hiding versus synchronous page parameters
8.3 Configuration considerations
  • Client code and environment must match the delivery endpoint.
  • at_property must be present at page level in multi-tenant setups.
  • Timeouts and default content protect against slow responses.
  • Consent settings affect whether delivery and measurement occur.
  • Identity must be consistent across Target, Analytics, and Edge.
  • at.js must load early in HEAD with the pre-hiding snippet, and the data layer must come before it.
8.4 Best practices
  • Separate environments and test in staging.
  • Name everything consistently and document each activity.
  • Keep the Global mbox lightweight.
  • Guard the Order Confirmation mbox against duplicate firing.
  • Retire finished activities.
  • Send live values (inventory, price, conversions) with the request rather than relying on nightly feeds.
8.5 Commonly misunderstood concepts
  • The Global mbox doesn’t replace specific mboxes.
  • Traffic allocation applies to qualified visitors only.
  • Traffic Allocation splits visitors within one activity. A profile script attribute splits visitors across activities.
  • Analytics and Target numbers are expected to differ somewhat.
  • Empty recommendations usually mean criteria or catalog problems. A no_content response can mean results aren’t cached yet at the Edge.

Chapter 9: Independent Practice Exam

Note: these questions are independently created for practice. They are not actual or leaked Adobe exam questions. They are separate from the 49 questions in Part 5.

Q1 (Fundamentals). Which activity type shows different experiences to audience segments without statistically comparing outcomes? A. A/B test B. Multivariate test C. Experience Targeting D. Auto-Allocate

Q2 (Fundamentals). A test reports a traffic split that differs noticeably from the configured split. What is the most likely issue to investigate first? A. Statistical power B. Sample ratio mismatch C. Goal definition D. Recommendation criteria

Q3 (Integrations). What does Analytics for Target (A4T) primarily provide? A. Creation of Target audiences from Analytics data B. Reporting of Target activity and experience data in Adobe Analytics C. Replacement of Target’s delivery engine D. Automatic AEM component rendering

Q4 (Governance). Why should development, staging, and production activities be separated? A. To reduce license cost B. To test changes before they affect live visitors C. To increase traffic allocation D. To avoid using audiences

Q5 (Touchpoints). Which delivery method is most likely to avoid visible flicker for above-the-fold content? A. Client-side at.js with default timeout B. Server-side delivery with the decision made before rendering C. Email delivery at send time D. Client-side tags with no body-hiding

Q6 (Recommendations). A recommendation mbox returns no items for any visitor. Which check is the most appropriate first step? A. Change the algorithm B. Review criteria and catalog data C. Increase traffic allocation D. Rename the mbox

Q7 (Architecture). Why should the Global mbox be kept lightweight? A. It runs on every page where the library is loaded, so heavy logic slows every page B. It cannot hold any offers C. It only works for mobile apps D. It replaces AEM

Q8 (Architecture). An order confirmation page is sometimes refreshed by customers. What is the main risk for the Order Confirmation mbox? A. Lower traffic allocation B. Duplicate revenue and conversion counts C. Audience mismatch D. Flicker

Q9 (Troubleshooting). A visitor sees default content, but the activity is live and the audience matches. The mbox request fires and returns empty options. What is the most likely next check? A. Whether the page’s font loads B. The activity’s traffic allocation and audience matching for that visitor C. The Analytics report suite name D. The Recommendations catalog

Q10 (Troubleshooting). Production shows no mbox request at all, while staging works. Which area should you check first? A. The algorithm settings B. Whether the library and tag load on production, and any consent or script blocking C. The traffic split D. The goal definitions

Q11 (Scenario). A retailer wants logged-in pricing personalized without flicker, and layout tests that don’t need server data. Which design is most appropriate? A. Client-side only for everything B. Hybrid: server-side for pricing, client-side for layout tests, with a shared visitor identity C. Email delivery for both D. Global mbox for everything

Q12 (Scenario). A team reports that Target conversions are 15% higher than Analytics orders for the same period. What should you check first? A. Rewrite the activity B. Compare attribution windows, deduplication, identity, and time zones between the systems C. Stop the test D. Change the algorithm

Answer key

Q1: C. Experience Targeting shows different experiences to segments and doesn’t compare them statistically. A/B and MVT are tests. Auto-Allocate shifts traffic within a test.

Q2: B. A traffic split that differs from configuration is a sample ratio mismatch, which usually points to implementation or delivery problems. Statistical power and goals don’t change the actual split, and recommendation criteria don’t apply.

Q3: B. A4T sends Target data into Analytics for reporting. It doesn’t create Target audiences by itself, replace delivery, or render AEM components.

Q4: B. Separate environments let teams test changes before they affect live visitors. Cost, traffic allocation, and audiences aren’t the purpose.

Q5: B. Server-side delivery with the decision made before rendering avoids the browser-side swap that causes flicker.

Q6: B. Empty recommendations usually come from criteria that exclude everything or from catalog problems.

Q7: A. The Global mbox runs on every page where the library loads. Heavy logic there adds cost to every page.

Q8: B. Refreshes or back-button returns can re-fire the Order Confirmation mbox, causing duplicate revenue and conversions.

Q9: B. Once the activity is live and the mbox responds with empty options, check whether the visitor is in the allocated traffic and matches the audience.

Q10: B. No request at all means delivery isn’t happening. Check that the library and tag load on production and that consent or script blocking isn’t stopping them.

Q11: B. Server-side handles logged-in pricing without flicker. Client-side handles simple layout tests cheaply. A shared identity keeps decisions consistent.

Q12: B. Mismatches between Target and Analytics usually come from attribution windows, deduplication, identity differences, and time zones. Check these before changing or stopping the test.
